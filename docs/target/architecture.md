# Целевая архитектура портала

Как устроен портал, чтобы закрыть 34 возможности MVP (REF-CAP) и не
закрыть дорогу возможностям «позже». Стек и принципы уже заданы:
конституция, ADR-0001 (Django + HTMX + PostgreSQL), ADR-0003 (поиск, файлы,
списки, почта), ADR-0004 (порядок срезов). Здесь — как это складывается
вместе. Детали моделей и маршрутов — в plan.md каждого среза.

## Размещение

Одна виртуальная машина Debian в ресурсах общества. Все компоненты — в
Docker Compose. В интернет портал публикует штатный администратор своим
обратным прокси с TLS (REQ-CTX).

```
 интернет ──► прокси администратора (TLS) ──► nginx ─┬─► web (ASGI: HTTP + WebSocket)
                                                    └─► /protected/ (файлы, X-Accel-Redirect)
 web ──┬─► postgres (данные, полнотекстовый поиск)
       ├─► redis (очереди RQ, слой Channels, кэш, счётчики попыток входа)
       └─► том media (вложения)
 worker (RQ) ──► postgres, redis, media, clamav, почтовый сервер (SMTP), Telegram/MAX
 scheduler (RQ) ──► каждую минуту: опрос IMAP; по ночам: сроки хранения, очистка
 clamav (clamd) ◄── worker: проверка каждого вложения
```

| Контейнер | Что делает |
|---|---|
| nginx | статика, внутренняя отдача файлов по `X-Accel-Redirect`, проксирование HTTP и WebSocket в web |
| web | Django на ASGI-сервере (uvicorn): страницы, фрагменты HTMX, WebSocket (Channels) |
| worker | задания RQ: разбор писем, отправка почты и уведомлений, проверка файлов, выгрузки |
| scheduler | расписание RQ: опрос IMAP раз в минуту, ночные задания |
| postgres | PostgreSQL 17: данные, JSONB, полнотекстовые индексы |
| redis | Redis: очереди RQ, слой каналов Channels, кэш, счётчики django-axes |
| clamav | антивирус clamd, базы сигнатур обновляются сами |

Тома: `pgdata`, `media`, `backups` (ночной `pg_dump`), базы ClamAV.
Резервные копии томов `backups` и `media` администратор уносит на локальное
и сетевое хранилище внутри периметра.

## Модули — приложения Django

По инварианту «модуль-приложение»: каждый модуль — отдельное приложение с
публичным интерфейсом `services.py`. Чужие модели напрямую не
импортируются; реакции на события других модулей — через сигналы ядра.

| Приложение | Что внутри | Возможности MVP | Срез |
|---|---|---|---|
| `core` | учётные записи, роли и права (как данные), двухфакторная авторизация, политика паролей, устройства и история входов, журнал аудита, настройки портала, файлы и их проверка, шина событий | CAP-01…04, 13, 16, 83, 84, 62 (хранилище файлов) | 001, 003 |
| `org` | дерево подразделений и команд, членство (в том числе совместительство), руководители и заместители, увольнение, рабочий календарь | CAP-06, 08, 71, 75, 77, 79 | 002 |
| `servicedesk` | заявки, очереди, категории, критичности, справочники, история, закрытие, заявители (без учётной записи) | CAP-22…28, 32, 33, 37 | 003 |
| `integrations` | адаптеры внешних систем: `mail` (IMAP и SMTP), `telegram`, `max`; позже — `zabbix`, `asdob` | CAP-22, 24, 39 | 003, 004 |
| `notify` | уведомления на портале и почтой, настройки каналов у пользователя, приглашения | CAP-14, 78 | 004 |
| `knowledge` | статьи, рубрики, теги, версии, обсуждение | CAP-63 | 005 |
| `search` | сквозной поиск: опрашивает `services.search()` модулей и склеивает выдачу | CAP-15 | 005 |
| `lists` | универсальные списки: схема полей, записи в JSONB, выгрузка в Excel | CAP-105 | 006 |
| `feed` | записи, адресаты, комментарии, «Мне нравится», упоминания, важное | CAP-51 | 007 |
| `messenger` | личные и групповые чаты, чаты отделов, файлы, прочтение | CAP-52, 82 | 008 |

Возможности «позже» встают в эти же приложения (SLA и канбан заявок — в
`servicedesk`, Zabbix и АСДОБ — в `integrations`) или в новые (`tasks`,
`calendar`, `disk`). Общий движок стадий с триггерами и роботами (CAP-72,
CAP-74, CAP-104) — отдельное приложение, когда до него дойдёт.

## Сквозные механизмы

**События и журнал.** Сервис модуля, меняющий данные, публикует событие
ядра («заявка создана», «ответственный сменён»). На событие подписаны
журнал аудита, уведомления и живые обновления. Журнал — таблица,
которую роль приложения в базе может только дополнять: прав `UPDATE` и
`DELETE` на неё нет (инвариант «аудит-изменений»). В записи — кто, когда,
действие, объект, было и стало (JSONB), адрес IP.

**Права.** Роли и наборы прав — данные в базе, их меняет администратор
(инвариант «настройка-без-кода»). Каждый маршрут объявляет нужное право.
Видимость конкретного объекта (заявка видна участникам её очереди, статья —
по правам рубрики) проверяет сервис модуля, в том числе внутри поискового
запроса.

**Вход.** Свои учётные записи. Пароль проверяется по политике: длина и
состав, запрет повтора, при желании срок действия. Второй фактор —
обязательный TOTP (django-otp) с резервными кодами. django-axes считает
неудачные попытки и блокирует перебор. Каждый вход записывается в историю:
устройство, браузер, адрес IP, время. При входе с нового устройства
пользователь получает письмо. Приглашение по почте (срез 004) ведёт на
одноразовую страницу: код из ссылки обменивается на сессию POST-запросом,
пароль и второй фактор задаются сразу (инвариант «секреты-в-url»).

**Заявитель без учётной записи.** Это отдельная сущность `servicedesk`:
адрес, ФИО, подразделение, если оно известно. Учётной записью портала
заявитель не является и в портал не входит. Принимаются только адреса из
списка корпоративных доменов — это настройка.

**Путь письма в заявку.**
1. Раз в минуту scheduler ставит задание: забрать непрочитанные письма из
   ящика заявок по IMAP.
2. Письмо сохраняется целиком (RFC 822) и записывается как «входящее
   письмо», и только потом разбирается.
3. Отправитель не из корпоративного домена — письмо отклоняется и
   остаётся в журнале входящих. Отвечать ли ему, решает спека среза 003.
4. Номер в теме `[#123]` или заголовки `In-Reply-To` / `References`
   указывают на заявку — письмо становится её комментарием. Иначе
   создаётся новая заявка.
5. Вложения уходят на проверку ClamAV. Письмо помечается обработанным.

Сбой на любом шаге не теряет письмо: оно уже сохранено, задание
повторяется.

**Исходящая почта.** Ответ исполнителя ставит задание RQ. Письмо уходит по
SMTP с номером заявки в теме и собственным `Message-ID`. Повторы идут с
нарастающей паузой, результат записывается в журнал доставки.

**Уведомления.** Событие → `notify` → каналы, выбранные пользователем: на
портале (запись в базе и толчок по WebSocket), почтой, в Telegram или MAX.
В мессенджеры уходят только событие и ссылка, без ФИО и текста заявки
(инвариант «пдн-152фз»). Пользователь привязывает Telegram или MAX
одноразовым кодом из профиля.

**Живые обновления.** Channels со слоем каналов на Redis. Группы: у
пользователя (счётчики, уведомления), у чата, у ленты. Сервер шлёт готовые
фрагменты HTML, страница вставляет их средствами HTMX (расширение `ws`),
отдельного состояния на клиенте нет (инвариант «стек-интерфейс»).

**Файлы.** Загрузка → временный файл → запись со статусом «проверяется» →
задание ClamAV → «чистый» или «карантин». Выдача только чистого файла и
только после проверки права: web отвечает `X-Accel-Redirect`, nginx отдаёт
файл из внутреннего расположения. Ограничения по размеру и типу — в
TGT-NFR.

**Поиск.** У каждой сущности, по которой ищут, есть столбец `tsvector`
(конфигурация `russian`) с GIN-индексом. Столбец обновляется триггером
базы или в сервисе при сохранении. `search` вызывает `services.search()`
включённых модулей и склеивает выдачу. Права проверяются внутри запроса
модуля (ADR-0003).

**Универсальные списки.** Список — это схема полей (JSON) и записи
(JSONB с GIN-индексом). Типы полей: текст, число, дата, справочник,
сотрудник, подразделение, файл. «Оборудование» и «Лицензии» создаются
миграцией данных при установке.

**Оргструктура.** Дерево подразделений и команд хранится материализованным
путём. Членство — отдельная связь «сотрудник — подразделение», поэтому
совместительство поддерживается с первого дня. Роли «руководитель» и
«заместитель» — атрибут членства. Увольнение — состояние учётной записи:
вход закрыт, человек уходит из структуры, его заявки, записи и сообщения
остаются и подписаны его именем.

## Безопасность и персональные данные

- Всё, что видно из интернета: страница входа, открытая форма заявки,
  страницы приглашения и восстановления пароля. Остальное требует входа и
  второго фактора.
- Секреты только в окружении (`.env` вне git) — инварианты
  «секреты-вне-кода» и «секреты-в-url».
- Фильтр веб-атак, если он нужен, ставится на прокси администратора, а
  не внутри портала (CAP-85 — «не нужно» как функция портала).
- ПДн заявителей: минимум полей, согласие на форме и в автоответе, сроки
  хранения — настройка, очистку выполняет ночное задание (TGT-NFR).

## Что остаётся спекам и планам

Точные модели, маршруты, тексты писем и экраны — в `specs/NNN-*/`. Приёмы
интерфейса Битрикса (слайдер карточки, левое меню, счётчики) опишет REF-UX
по снимкам демо-стенда к срезу 001.
