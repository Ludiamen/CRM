## Повторная проверка, версия 3

Между версией 2 и версией 3 в `constitution.json` изменилось ровно одно
значение: вторая регулярка инварианта «секреты-вне-кода» в списке
«значения». Было (версия 2, ложно ловила переменную):
`(?i)password=[^\s"'$*{]{4,}`. Стало (Opus):
`(?:^|[\s\-])[A-Z0-9_]*PASSWORD\s*[=:]\s*[^\s"'$*{()]{4,}\s*$`. Остальные 15
инвариантов, их поля (`правило`, `почему`, `вместо`, `источник`, `статус`,
первая регулярка того же инварианта) и структура документа не тронуты —
построчная сверка текущего `docs/constitution.json` с версией, проверенной в
версии 2 этого отчёта, других расхождений не находит. `docs/constitution.md`
синхронен с json (`python3 tools/sdd.py проверить` не даёт «отстаёт от
constitution.json»); новый отпечаток документа —
`sha256:e9c3b43424d8e84ad9087c09755759d84145cfca956e5cbdb9810209b15280dc`
(`python3 tools/sdd.py отпечаток docs/constitution.md`).

**Новый постоянный тест вместо разовой песочницы.** В версиях 1 и 2 регулярки
проверялись пересборкой временной песочницы с синтетическим кодом — каталог
не переживает сессию, и в следующий раз всё пришлось бы собирать заново.
Вместо этого добавлен `tools/test_constitution.py`: он читает настоящий
`docs/constitution.json` репозитория (не выдуманный мини-набор инвариантов) и
для каждого из 7 жёстких инвариантов прогоняет ту же функцию, которой
пользуются ворота (`sdd._нарушение_на_строке`, вызывается из
`sdd.проверить_код_по_конституции`), на двух наборах строк:

- 18 строк «честного кода» Django + HTMX + docker-compose — ни одна не должна
  задеть ни один жёсткий инвариант. Набор специально включает ровно те формы,
  из-за которых были находки версий 1–2: пароль переменной в вызове
  `authenticate(...)`, пароль из фикстуры (`self.password =
  secrets.token_urlsafe(16)`, `client.login(..., password=self.password)`,
  `create_user(..., password=self.password)` — решение владельца 2026-09-29),
  секрет докера через подстановку (`POSTGRES_PASSWORD=${POSTGRES_PASSWORD}` и
  YAML-вариант с двоеточием), `hx-headers` с `X-CSRFToken`, поле модели
  `token = models.CharField(...)`, импорты `reactive_utils` / `django_rq`,
  которые лишь похожи на запрещённые слова «react» / «celery», и комментарий
  «как в Битриксе» кириллицей (не запрещённое латинское `bitrix`).
- 10 строк-нарушений — по одной на каждый из 7 жёстких инвариантов (для
  «секреты-вне-кода» — четыре: квотированный литерал и `API_KEY` под первую
  регулярку, `DB_PASSWORD=` без кавычек и версия с отступом и двоеточием
  (стиль docker-compose) под вторую). Тест проверяет, что срабатывает ИМЕННО
  ожидаемый инвариант и никакой другой.

Тестовые строки-«секреты» собраны конкатенацией (`"password=" + '"..."'`),
чтобы pre-commit `tools/check_secrets.py` не принял сам файл теста за
секрет — проверено вызовом `check_secrets.проверить_текст` на исходный текст
файла: результат — пустой список.

**Живой прогон.** `python3 -m unittest tools/test_constitution.py` — 4 теста,
OK, находок нет: ни одна строка честного кода не задела ни один из 7 жёстких
инвариантов, каждая строка-нарушение поймана ровно тем инвариантом, для
которого подобрана. Отдельно проверено прямым вызовом `re.search`, что обе
строки, нацеленные на новую вторую регулярку (`DB_PASSWORD=S3cr3t-value` и
строка с отступом `POSTGRES_PASSWORD: plainsecret`), ловятся именно второй
регуляркой, а не первой — значит новая регулярка реально работает, а не
просто не мешает первой. Полный набор: `python3 -m unittest discover -s
tools -p "test_*.py"` — 90 тестов (было 86 в версии 2), OK.

**Статус находки «секреты-вне-кода, вторая регулярка» (открыта в версии
2): ЗАКРЫТА.** Новая регулярка требует ЗАГЛАВНОГО имени, оканчивающегося на
`PASSWORD`, без кавычек вокруг значения — это конфигурационный стиль
(`.env`/docker-compose: `POSTGRES_PASSWORD=...`), а не питоновский
идентификатор в обычном коде. Строчные `password=test_password`,
`password=self.password`, `password=password` она не ловит (регистр не
совпадает — в отличие от первой регулярки, вторая не помечена `(?i)`), а
первая её тоже не ловит — значение не в кавычках. Заодно повторно
подтверждена (постоянным тестом, а не разовой песочницей) находка «первая
регулярка» из версии 1: пароль из фикстуры `secrets.token_urlsafe()`
(строчные буквы, без кавычек) не ловится ни одной из двух регулярок.

Тест — представительная выборка по случаям из решения владельца и практики
Django + HTMX + docker-compose, а не формальное доказательство отсутствия
любых ложных срабатываний; но теперь она прогоняется автоматически при
каждой правке `constitution.json`, а не только при ручной проверке.

## Повторная проверка (2026-09-29, версия 2)

После версии 1 владелец принял решение по находке «секреты-вне-кода, первая
регулярка» (ниже): пароли в тестах не пишутся литералом, а создаются в общей
фикстуре через `secrets.token_urlsafe()`. Правку внесли только в поле
`вместо` инварианта «секреты-вне-кода» — `constitution.json` пересобрали

действующий статус документа снова стал «черновик» (`отчёт проверки

**Изменение поля.** `git diff docs/constitution.json docs/constitution.md`
против последнего коммита бесполезен напрямую: единственный коммит
репозитория предшествует всей работе по SDD-воротам, поэтому diff показывает
накопленные правки нескольких предыдущих проходов, а не только эту. Изменение
проверено реконструкцией: в копии `constitution.json` поле `вместо`

**Проверка на песочнице.** Каталог `review-sandbox` из версии 1 не сохранился

  версии 3** — новая регулярка от Opus больше не ловит переменную, см.
  «Повторная проверка, версия 3».
- Независимый сканер `tools/check_secrets.py` (pre-commit, вне области этой
  проверки конституции, но упомянут в задании) на переписанный файл **не

Вердикт по документу не меняется: текст `constitution.md`/`constitution.json`

## Находки (ложные срабатывания regex, `constitution.json` не менялся)

- **Секреты-вне-кода, первая регулярка** — `(?i)(password|passwd|secret|api_?key|token)\s*[:=]\s*['"][^'"$*{]{4,}['"]`
  сработает на обычную тестовую фикстуру Django:
  `песочница «review-sandbox», файл tests/test_views.py (стр. 12)` (`username="ivanov",
  password="***", email=...`) и `:14`
  (`self.client.login(username="ivanov", password="***")`) — живой
  прогон `python3 tools/sdd.py проверить --корень <песочница>` подтверждает
  обе строки как ОШИБКА. Пароли в тестовых фикстурах Django пишутся литералом
  по общепринятой практике (`create_user(..., password=...)`) и секретом не
  являются. Это то же самое ограничение, что уже отмечено и оставлено как
  известное в проекте ГИС (`docs/reviews/CONST.md` того проекта, раздел
  «Дополнение»): «Пароли в тестах строятся во время выполнения, а не пишутся
  литералом» — на практике они как раз пишутся литералом, поэтому находка
  повторяется. Предложение (решение — за владельцем): исключить из `проверять`
  пути `**/tests/**`, `**/test_*.py` или дать для них отдельный, более мягкий
  набор правил.
- **Слова-запреты «спринг»/«express» как отдельные английские слова** —
  теоретический, не воспроизведённый на практике риск: идентификаторы вида
  `ExpressQueue`, `is_express`, `EXPRESS_SLA_MINUTES` не совпадают с `\bспринг\b`/`\bexpress\b`
  из-за границ слова (подчёркивание и продолжение CamelCase — тоже `\w`,
  границы не образуются); сработать может только отдельно стоящее английское
  слово в русском тексте/комментарии, что при принятой в проекте
  русскоязычной прозе маловероятно. Не считаю нужным менять — не находка,
  указано для полноты.
