### M-03 — открыто частично, Medium: пропуски считаются только при наличии предыдущей строки

**Файл:** `backend/apps/lists/services/schedule.py:93–109`.

### C-02 / Critical — legacy-маскирование обходит ранний return

### H-07 / High — проверка правки раньше идемпотентного ответа

**Файлы:** `backend/apps/lists/views/records.py:343–347,358–361,370–375,403–404`,
`backend/apps/lists/views/board.py:69–75`.

Новая форма проверяет `can_edit_record()` **до** вызова `transitions.move()`.
Допустимый сценарий: сотрудник правит стадию A, читает, но не правит B; первый POST A→B проходит.
Повтор того же POST уже видит текущую B и получает 403 в представлении, не доходя до StageMove.
По контракту после проверки текущего чтения должен возвращаться сохранённый результат; правка
новой текущей стадии не является условием повторной доставки.
Ограничение GET-формы правкой допустимо; порядок проверки POST должен сохранять идемпотентность службы.

Также обработчики HTML-конфликтов всё ещё вызывают `_form_page()`/`_card_page()`/`render_page()`
без status=409; изменение JSON-ответа доски не исправляет этот путь NFR-751.
Ранний `stage_of()` на POST новой формы действительно удалён, то есть повтор по удалённой цели
теперь может дойти до службы, **если** его не остановит указанная проверка правки.

**expected проверен отдельно:** `backend/apps/lists/services/transitions.py:30–40,107–108`
приводит цифры к int, пустую строку и None к None. Представления используют текущую стадию только
при отсутствии параметра, не при `expected=""`. Числовая стадия совпадает со строковым ID; явное
ожидание «без стадии» при назначенной стадии даёт StageChanged. Версия проверяется раньше ожидания.
Новый обход stale-version в этой нормализации не найден.

### H-10 / High — длинный отказ не помещается в reason и отменяет сохранение failed

**Файлы:** `backend/apps/lists/services/schedule.py:99–129`,
`backend/apps/lists/models.py:477`,
`backend/apps/lists/services/errors.py:34–36`,
`backend/apps/lists/services/records.py:67–75,258–264`.

а не неограниченная конкатенация сообщений формы. Добавить тест с множеством ошибок обычных полей
и убедиться, что failed сохраняется, карточки нет, следующий тик не пытается создавать её снова.

**H-10 / High — нет savepoint вокруг подготовки запуска.**
`backend/apps/lists/services/schedule.py:81–93,116–123`.

речь о восстанавливаемой ошибке запроса в работоспособном соединении.

## Critical: раскрытие скрытых записей

### C-01. Скачать файл скрытой стадии можно по прямому адресу

**Файлы:** `backend/apps/lists/views/files.py:87–93`,
`backend/apps/lists/services/access.py:135–141`.

`download()` вызывает `access.get_record()`, который проверяет только чтение списка, а затем отдаёт
чистый файл. `can_read_record()` не вызывается. Читатель списка, исключённый из прав стадии, получает
содержимое файла по известным номеру записи и ID файла, хотя карточка этой записи отвечает 404.
Нарушены FR-861 и CONTRACT-015 §4/6.

**Исправление:** центральное получение записи должно проверять стадию; отдельно проверить скачивание,
прикрепление и удаление скрытой/архивной записи. У последних двух чтение также должно предшествовать
`RecordArchived` и правке: сейчас возможны 403 или HTML карточки скрытой архивной записи
(`services/files.py:35–43`, `views/files.py:35–53`).

### C-02. История доступной записи раскрывает названия ссылок на скрытую стадию

**Файлы:** `backend/apps/lists/services/history.py:38–53,66–84`,
`backend/apps/lists/views/records.py:357–367`.

История хранит готовые строки показа ссылочного поля. `for_viewer()` скрывает их только при отсутствии
чтения **целевого списка**, не стадии конкретной записи. Сценарий: управляющий сохраняет ссылку на запись,
затем права стадии исключают читателя; читатель открывает историю исходной доступной записи и получает
название и номер скрытой цели в `before/after`. Изменение `values.display()` не исправляет уже сохранённые
строки истории. Нарушены FR-861 и T-15020.

**Исправление:** обеспечить возможность проверить текущую доступность целей исторических ссылок;
не считать проверку списка достаточной. Добавить отрицательный тест после отзыва прав стадии.

### C-03. Карточка заявки продолжает показывать скрытые записи и позволяет отвязать их

**Файлы:** `backend/apps/lists/services/tickets.py:58–64,80–82,133–142`,
`backend/templates/lists/_ticket_section.html:6–8`.

Исправлены `pick()` и `link()`, но `_links()` фильтрует только список. Уже привязанная запись скрытой
стадии выводится с названием и ссылкой в заявке. `unlink()` также проверяет только список, позволяя
изменить связь скрытой записи по известному ID. Нарушены FR-861 и T-15020.

**Исправление:** применить права записи к выдаче существующих связей и к отвязке, не только к поиску
новой связи.

## High: обязательные исправления

### H-01. Уникальность раскрывает номер и адрес скрытого владельца

**Файлы:** `backend/apps/lists/services/records.py:84–97`,
`backend/apps/lists/services/unique.py:51–58`.

При создании/правке с занятым уникальным значением отказ содержит `owner.number` и URL без проверки

уже раскрывает её идентификатор. Предпросмотр импорта исправлен отдельно и эту ветку не закрывает.
Нарушен CONTRACT-015 §3 (`unique_taken` без номера и ссылки скрытого владельца).

**Исправление:** оставить проверку глобальной уникальности, но разделить внутреннего владельца и
разрешённые смотрящему параметры ошибки; проверить предварительный отказ и конфликт ограничения БД.

### H-02. Подделанный POST и импорт позволяют выбрать скрытую запись в ссылочное поле

**Файл:** `backend/apps/lists/services/values.py:204–225,311–339,387–403`.

`_all_selectable()` проверяет чтение списка и существование записи, но не стадию. `_import_record()`
и пакетный `import_lookups()` также включают все неархивные записи целевого читаемого списка.
Поэтому скрытая в подсказке запись всё равно принимается по ID через форму, а по номеру/названию — через
импорт. Это также оракул существования скрытой записи. Нарушены CONTRACT-015 §4 и T-15020.

**Исправление:** применять единое условие стадии и при серверной валидации, и при сборке импортных
справочников; сохранить отдельно прежнее правило допустимости уже сохранённой ссылки.

### H-03. Обычная правка не проверяет обязательные поля текущей стадии

**Файл:** `backend/apps/lists/services/records.py:181–208`.

После разбора значений проверяются только `Field.required` и уникальность; `ProcessStageField`
не проверяется вообще. Можно очистить обязательное на стадии поле и успешно сохранить запись.
Также запись, помещённая на стадию массовым включением, может пройти ближайшую правку с пустыми
обязательными полями. Нарушены FR-867/869 и CONTRACT-015 §6.

**Исправление:** проверять итоговые значения и фактические файлы текущей стадии до записи и до возврата
«без изменений». Тестировать очистку, отсутствующее значение, прежнее заполненное значение и файл.

### H-04. Переход с изменением полей обходит уникальность, поиск и историю полей

**Файл:** `backend/apps/lists/services/transitions.py:38–54,104–145`.

`move(values=…, title=…)` непосредственно сохраняет `Record.values/title`. В отличие от `records.save()`,
не вызывает проверку/синхронизацию `UniqueValue`, обновление поискового вектора и построение изменений
полей истории. Присланное значение уникального поля может дублировать чужое, а индекс уникальности
останется со старым значением; поиск останется по прежним данным. История содержит стадию и, возможно,
название, но не изменённые пользовательские поля. `_effective()` также не проверяет обычное
`Field.required`. Нарушены прежние гарантии списка, FR-868/887.

**Исправление:** использовать общий путь валидации и сохранения итогового состояния, включая уникальность,
вектор и историю, в одной транзакции перехода.

### H-05. Выключение процесса не выключает его влияние на операции записи

**Файлы:** `backend/apps/lists/services/process.py:80–82`,
`backend/apps/lists/services/records.py:146–150`,
`backend/apps/lists/services/archive.py:66–75`,
`backend/apps/lists/services/imports.py:274–279,300–311`,
`backend/apps/lists/services/files.py:105–111`,
`backend/apps/lists/services/transitions.py:94–130`.

`first_open()` не учитывает `enabled`; создание, импорт и восстановление присваивают стадии даже
выключенного процесса. Удаление последнего файла и импортная правка продолжают применять требования
стадии после выключения. Служба перехода и POST-маршруты также не отклоняют выключенный процесс.
Например, выключив процесс, нельзя удалить файл, обязательный только в его стадии.
Нарушены FR-855/856, ADR-0022 §9 и CONTRACT-015 §6.

**Исправление:** явно отделить сохранённую конфигурацию стадий от действующего процесса; проверять
`enabled` внутри транзакционных операций, а не только при показе кнопок.

### H-06. Вместо формы перехода реализована только отправка целевой стадии

**Файлы:** `backend/apps/lists/views/records.py:335–350`,
`backend/templates/lists/_record_stage.html:9–19`,
`backend/apps/lists/urls.py:56`.

Маршрут принимает только POST; обработчик не передаёт `values` в `transitions.move()`. При
`StageRequired` возвращается карточка с общим отказом, а не форма ввода с подсветкой обязательных полей.
Нет способа одним действием заполнить поля и перейти, как требует FR-868; это прямо заявлено в T-15023.

**Исправление:** реализовать GET/POST формы перехода, итоговые значения, ошибки по полям и сохранение
введённого. Отдельно проверить обязательное поле текущей и целевой стадии.

### H-07. HTTP-контракт перехода не обеспечивает заявленные повторы и ответы

**Файлы:** `backend/apps/lists/views/board.py:61–77`,
`backend/apps/lists/views/records.py:343–350`.

Оба представления загружают цель через `stage_of()` **до** поиска `StageMove`: повтор после удаления
опустевшей целевой стадии получает 404 вместо сохранённого результата. Успех с
`Accept: application/json` на доске даёт redirect, а не JSON/200; карточка при конфликте версии возвращает
200 с карточкой, а не 409. `expected` из клиента не используется — подставляется текущая стадия
загруженной записи. Сервисные тесты не доказывают контракт двадцати POST из NFR-751.

**Исправление:** передавать числовой ключ цели до загрузки FK, возвращать согласованный результат по
формату запроса, различать конфликт и успех; проверять клиентскую ожидаемую стадию.

### H-08. Сохранение настройки стадии частично коммитится; создание игнорирует права и поля

**Файл:** `backend/apps/lists/views/settings.py:634–642,648–660`.

Форма новой стадии содержит права и обязательные поля, но `stage_new()` сохраняет только название/вид,
остальное молча теряется. При правке три службы коммитятся по отдельности: `update_stage()`,
`save_stage_access()`, затем `save_stage_fields()`. Если поле скрыто или явный набор прав пуст,
пользователь получает отказ, но название/вид и иногда права уже изменены. Например, отзыв прав
зафиксируется даже при отказе сохранения набора полей. Нарушены ожидаемая атомарность настройки и T-15011.

**Исправление:** единая транзакционная операция сохранения стадии с валидацией всего ввода; применять
выбранные права и поля при создании. Проверять отсутствие любых изменений после отказа.

### H-09. Плановый запуск использует конфигурацию без замка и может создать запись после выключения

**Файл:** `backend/apps/lists/services/schedule.py:78–105,124–130`.

`tick()` загружает `process_row`, затем `launch()` проверяет его старое `enabled` и получает первую стадию
без замка списка. Разделяемый замок берётся только внутри `create_system()`, где процесс уже не
перечитывается. Между этими действиями управляющий может выключить процесс/изменить обязательные поля/
удалить пустую стадию. После выключения возможна запись по старой конфигурации; удалённая стадия даёт
ошибку FK вместо корректного пропуска. Уникальность периода от этого не защищает.

**Исправление:** под общим порядком замков перечитывать процесс, стадию и требования; сериализовать
решение о запуске с настройкой процесса, не меняя правило «строка запуска первой».

### H-10. Ошибки запуска оставляют `skipped` без причины вместо `failed`

**Файл:** `backend/apps/lists/services/schedule.py:80–85,103–114`.

Строка `skipped` уже создана, а `_defaults()` и поиск стадии выполняются вне защищённой точки
сохранения/обработчика. Внутри создания ловятся только `ListsError` и `IntegrityError`.
Например, ошибка `vectors.refresh()` или другая неожиданная ошибка создания откатывает карточку,
выходит из `tick()` и оставляет первоначальный `skipped` без причины и события ошибки.
Следующий тик пропускает этот период по существующей строке. Нарушены FR-877/878 и CONTRACT-015 §7.

**Исправление:** гарантировать финальный статус и безопасную причину для ошибок подготовки/создания;
не сохранять сырой текст исключения БД в пользовательский аудит. Тестировать искусственный сбой
создания и отсутствие повторной попытки в том же периоде.

### H-11. Кэш прав до замка позволяет переход после конкурентного отзыва доступа

**Файлы:** `backend/apps/lists/views/board.py:58–64`,
`backend/apps/lists/views/records.py:340–347`,
`backend/apps/lists/services/access.py:152–163`,
`backend/apps/lists/services/transitions.py:77–99`.

Представление проверяет чтение до замка и заполняет `user._lists_stage_scope`. Затем управляющий может

замок, но повторная проверка чтения/правки использует старый кэш. Следовательно, проверка после
`select_for_update` не обязательно проверяет **актуальные** права; возможен переход или выдача результата
повтора после отзыва. Нарушены FR-872 и CONTRACT-015 §5.

**Исправление:** обеспечить актуальность прав, прочитанных в защищённой секции, включая права списка;
добавить двухтранзакционный тест с барьером между предварительной проверкой и замком.

### M-01. Ключ периода недели/месяца не соответствует началу периода

**Файл:** `backend/apps/lists/services/schedule.py:25–48,99–101`.

Для недели `period_start()` возвращает последнее наступление настроенного дня, не понедельник;
для месяца `due()` заменяет первое число на день запуска и возвращает его как ключ. Например,
месячный запуск 15 декабря получает ключ 15 декабря, а не 1 декабря. Изменение дня расписания в том же
месяце/неделе позволяет создать второй запуск того же периода. Для недельного расписания до
назначенного дня новой недели выбирается прежняя дата — возможен запуск предыдущего периода.
Дата в шаблоне также берётся из ключа, а не из московской даты фактического создания.

**Исправление:** разделить стабильный ключ календарного периода, момент срока и дату подстановки.
Тестировать смену дня внутри периода, границы недели/месяца и задержанный тик.

### M-02. Умолчания ссылочных полей передаются как подписи, а не значения формы

**Файлы:** `backend/apps/lists/services/schedule.py:51–62`,
`backend/apps/lists/services/records.py:243–245`,
`backend/apps/lists/services/values.py:181–201`.

`_defaults()` использует `values.display()`: например, умолчание поля выбора становится названием
варианта. `create_system()` разбирает его с `source="form"`, где ожидаются числовые ID. Такой
корректно настроенный процесс не создаёт запись, хотя умолчание существует. Это касается choice/person/
unit/record. `_can_fill()` проверяет только наличие текста, а не пригодность итогового значения.

**Исправление:** передавать канонические значения через подходящий общий парсер, а не текст показа;
проверить умолчания всех типов, включая `False`, ноль и множественный выбор.

### M-03. Учёт пропущенных периодов и подписи новых действий журнала отсутствуют

**Файлы:** `backend/apps/lists/services/schedule.py:121–137`,

В `tick()` нет расчёта числа пропущенных периодов и события `lists.process_launch_missed`.
После простоя создаётся текущий запуск, но обязательное сообщение FR-878/NFR-752 не появляется.

**Исправление:** закончить предусмотренный планом журнал и добавить проверки авторов, подписей и
отсутствия названий записей/значений полей.

### M-04. Доска нарушает SQL-бюджет: запрос на каждую стадию

**Файлы:** `backend/apps/lists/services/board.py:22–32`,
`backend/apps/lists/views/board.py:30–35`.

Вместо предусмотренной планом оконной выборки выполняются отдельные запросы карточек каждой видимой
стадии. При прогретых правах управляющего сама `columns()` делает **S + 2** SELECT:
счётчики, стадии, S выборок карточек; при наличии «Без стадии» — ещё один. При десяти стадиях это уже
12/13 SELECT службы, а полный GET дополнительно загружает список, процесс, поля и контекст страницы:
лимит доски ≤12 запросов не выдерживается даже по нижней границе. Для обычного сотрудника добавляется
расчёт прав стадий. В новых тестах нет `assertNumQueries`/`EXPLAIN`.

**Исправление:** предусмотренная планом оконная выборка и измерение полного запроса с непрогретыми
правами. **p95 не измерялся**: из числа запросов нельзя честно вывести выполнение/провал порога 500 мс,
но SQL-критерий NFR-750 уже нарушен.

### M-05. Доска не доводит до пользователя отказы и не реализует добавление следующей страницы

**Файлы:** `backend/templates/lists/board/_column.html:9,15–16`,
`backend/static/lists/lists-board.js:10–17,30–37`,
`backend/apps/lists/views/board.py:65–71`.

Все карточки `draggable="true"`, в том числе у читателя и при запрете правки стадии.
При отказе сервер возвращает страницу с alert **вне** `[data-lists-board]`, а JS вставляет только
этот узел: сообщение теряется. «Показать ещё» — обычная ссылка на фрагмент, без HTMX и без обработчика
JS: пользователь покидает доску и видит одну колонку вместо добавления карточек.
При уже имеющемся `offset` он также дублируется в `board_params`, что мешает дальнейшей пагинации.
Нарушены FR-880/881.

**Исправление:** вычислять доступность переноса по записи, сохранять видимый контейнер ошибок,
реализовать явное добавление следующей страницы без ухода с доски.

### M-06. Удаление роли/узла не учитывает права стадий

**Файлы:** `backend/apps/lists/services/links.py:104–125`,
`backend/apps/lists/models.py:401–403`.

`unit_usage()` и `role_usage()` по-прежнему проверяют только `Access`, не `ProcessStageAccess`.
Узел, используемый исключительно правами стадии, не получает причину запрета удаления
(его ID не FK). Для роли FK PROTECT не заменяет предусмотренное понятное объяснение службы.
T-15020 прямо требует обе проверки.

**Исправление:** включить права стадий в обе точки usage; тестировать роль/узел, используемые только
стадией, без прав списка и без ссылочных значений.

## Что подтверждено и что реально покрывают тесты

- Основная формула `can_read_record`/`can_edit_record` сначала проверяет список, затем стадию:
  права стадии действительно не расширяют права списка. Управляющий обходит ограничения, выключенный
  процесс даёт `stage_scope=None`. Пустой набор и цепочка подразделений реализованы.
- Табличная выборка применяет `record_condition`; исправлены точные результаты и векторная ветка
  сквозного поиска, подсказки выбора и фильтра, показ текущих ссылочных значений, этикетки,
  фильтрация «Закреплённого» для постороннего смотрящего. Это не закрывает C-01…C-03 и H-01/H-02.
- Предпросмотр импорта при скрытом владельце уникального значения выдаёт ошибку без `number`,
  а подтверждение повторно проверяет право владельца; `create_locked(stage=…)` существует.
  При импортной правке проверяются требования стадии, но не только при включённом процессе.
- В переходе порядок кода: замок списка → `FOR UPDATE` записи → чтение → повтор → версия →
  ожидаемая стадия → цель и права → поля. Главная проблема актуальности чтения — H-11.
  `StageMove` имеет числовой `to_stage_key`, снимки названий и уникальный тройной ключ.
  Строка записи сериализует конкурентные переходы. Ветка `IntegrityError` не перечитывает сохранённый
  результат и ловит любую ошибку ограничения, но достижимость этой ветки при штатной row-lock
  сериализации отдельно не доказана; это не включено в число находок.
- Удаление последнего обязательного файла проверяется под замком записи; восстановление сохраняет
  имеющуюся стадию и назначает первую при NULL. Ошибка выключенного процесса — H-05.
- Расписание использует `Europe/Moscow`; строка запуска создаётся до карточки, уникальность периода
  есть; повтор обычного дневного тика не создаёт вторую карточку. Cron зарегистрирован в `maintenance`,
  `* * * * *`, `lists_process_launch`, timeout 300. `test_lists_deploy` обновлён на 33 регистрации и
  две функции `apps.lists.tasks`, с проверкой параметров.
- Модели/миграция только добавляют сущности/поле/индексы, без создания процессов и стадий по умолчанию.
  Индексы `(list, stage)`, `(process, order)`, ключи переходов и запусков присутствуют.
  Миграция не менялась в проверяемых пяти коммитах.

В снимке шесть `test_lists_process*.py`: **42 тестовые функции** —
10 настройка, 9 права, 12 переход, 3 обязательные поля/файлы/архив, 4 доска, 4 расписание.
Это число определений, не число успешно выполненных тестов.

Существенные пробелы:

- Нет `test_lists_process_grid.py` и `test_lists_process_journal.py`, предусмотренных красным этапом B.
- В `test_lists_process_access.py:151–167` проверены только таблица, карточка и её история;
  отсутствуют проверки истории ссылок, скачивания файлов, существующих связей заявки, уникальности,
  импортных справочников и поддельного ссылочного POST.

  процесса при обязательном файле.
- В `test_lists_process_move.py` нет двадцати конкурентных POST, конкурентного отзыва права,
  проверки порядка «чтение до повтора», смены полей с уникальностью/поиском, HTTP-повтора после удаления
  цели и проверки отсутствия названия/значений в аудите. Удалённая цель проверяется только службой с
  сохранённым Python-объектом, поэтому тест не замечает ранний `stage_of()` представления.
- `test_lists_process_board.py` не проверяет 51-ю запись, добавление следующей страницы, запрет drag,

- В расписании проверены только дневной срок, успешный повтор, выключение и незаполненное поле:
  нет недели/месяца, смены часового пояса на границе суток, failed, умолчаний ссылок, простоя,

  процессе. `test_reader_cannot_attach_file` проверяет только запрет правки **списка**, не стадии.
  `assert second_file.pk` не проверяет поведение; оно лишь подтверждает ID созданной фикстуры.
  Это слабые/неполные проверки, а не основание объявлять весь набор тавтологичным.

## Инварианты и процесс

- Изменённое приложение — только `lists`; вне него поведение добавляется регистрацией в `config/cron.py`.
  Новых зависимостей, движка полей, глобальных прав, событий автоматики/согласований нет.
- В рассмотренных путях применяется Django ORM; SQL advisory-lock параметризован. Новые внешние каналы
  и передача ПДн не добавлены; явных секретов в просмотренном diff не обнаружено.
- Событие перехода пишет только идентификаторы стадии/списка/номер, не название записи и не значения.
  Однако требование «нет утечек» в целом не выполнено из-за перечисленных обходов видимости;
  отсутствие ПДн в любых ошибках запуска динамически не доказано.
- В коммите `00c970d` уже реализованы части этапов 4/5, хотя обязательная независимая проверка
  этапов 1–3 ещё запрашивается. Это отклонение от последовательных ворот TASKS-015; ранняя реализация
  не равна приёмке T-15030…T-15044. Отсутствующую таблицу/выгрузку стадии не записываю отдельным
  дефектом этапа 3: это ещё предусмотренная планом работа T-15032/T-15033.
