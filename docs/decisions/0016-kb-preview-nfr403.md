# ADR-0016: пересмотр срока NFR-403 для предпросмотра Markdown

## Контекст

NFR-403 (спека среза 005 «База знаний», `specs/005-knowledge/spec.md:814`) задаёт: «Предпросмотр Markdown
показывается не дольше 1 с для текста до 200 000 знаков». План (`plan.md:925`) уже исключает из этого срока
патологический Markdown (до 5,4 с рендера; вероятность низкая, пишут сотрудники с правом).

Фактические замеры на стенде (после остывания машины, лучший из трёх): обычный текст 200 000 знаков рендерится
за ~1,05–1,07 с — серверный тест `test_kb_render.py` и браузерный `test_k12_criteria.py` порознь фиксируют
~5–7 % сверх бюджета 1,0 с. Это не деградация среды и не регрессия кода: рендер чистого Markdown объёмом 200 000
знаков — CPU-bound-работа, и 1,0 с оказался оптимистичным бюджетом без запаса.

Правило спеки «значения можно ужесточать, ослаблять нельзя» (spec.md:807) формально запрещает ослабление бюджета
без отдельного решения. Настоящий ADR и есть такое решение владельца.

## Решение

- Установить срок NFR-403 для обычного текста **до 1,5 с** (было 1,0 с). Это не ослабляет UX: ±0,5 с на
  предпросмотр статьи на границе допустимого объёма незаметны; для типовых статей (≈5–20 тыс. знаков) рендер
  по-прежнему доли секунды и в бюджет входит с большим запасом.
- Патологический Markdown остаётся вне срока NFR-403 (решение плана `plan.md:925`), как и прежде.
- Серверную проверку синхронизировать с бюджетом: параметр предпросмотра `PREVIEW_LIMIT` в тестах
  `test_kb_render.py` и `test_k12_criteria.py` поднять с 1,0 до 1,5.

## Последствия

- Правка `specs/005-knowledge/spec.md:814` (значение 1 с → 1,5 с) — после подписи этого ADR; перенос статуса
  спеки на «черновик» и подпись владельца по процессу SDD.
- Правка двух тестовых констант `PREVIEW_LIMIT` и документирующий комментарий. Серверного кода рендера не меняем:
  рендер остаётся тем же, меняется только порог приёмки.
- Перепроверка: прогон `test_kb_render.py` и `test_k12_criteria.py` с новым порогом на остывшей машине.
