# Процесс SDD в проекте портала ИТ-отдела

Портал ИТ-отдела — собственная система по образцу «1С-Битрикс: Корпоративный
портал» (коробочная версия): сервис-деск для заявок сотрудников общества плюс
рабочее пространство отдела (задачи и проекты, оргструктура, лента, календарь,
база знаний). Разработка ведётся от спецификаций (Spec-Driven Development): код
появляется только под утверждённый план, план — только под утверждённую
спецификацию, а спецификация — только в рамках утверждённой конституции.

Подход перенесён из агента миграции (AI-Advent-Challenge, День 20) через проект
ГИС, где он уже отработан: инварианты с полями «почему» и «вместо», ворота
стадий с подписью и отпечатком, сверка плана с фактом. Раскладка документов —
как в GitHub Spec Kit (constitution → spec → plan → tasks).

Главное отличие от ГИС: старой системы нет. Место описания legacy (as-is)
занимают два слоя — **эталон** (что и как делает Битрикс КП, со ссылками на
источники) и **требования** ИТ-отдела (что нужно именно нам, включая то,
чего в Битриксе нет: Zabbix, АСДОБ).

## Артефакты

```

  constitution.json      те же принципы в формате инвариантов Дня 20 — для проверки кодом
  sdd-process.md         этот документ
  glossary.md            словарь предметной области
  decisions/NNNN-*.md    журнал архитектурных решений (ADR)
  requirements/          исходные условия и собственные требования ИТ-отдела (REQ-*)
  reference/             эталон: Битрикс КП
    sources.md           реестр источников SRC-NN (страницы документации, снимки демо)
    modules/<код>.md     опись одного модуля эталона
    ui-patterns.md       приёмы интерфейса UX-NN
    capabilities.md      карта возможностей CAP-NN с решением владельца
  target/                to-be: архитектура, нефункциональные требования, модульная схема

```

## Жизненный цикл документа

```
черновик ──► на-проверке ──► утверждён ──► заменён
    ▲              │               │
    └──────────────┴── правка ─────┘   (отпечаток не совпал — подпись слетает сама)
```

| Переход | Условие (проверяет `tools/sdd.py`) | Кто |
|---|---|---|
| черновик → на-проверке | есть отчёт проверки `docs/reviews/<id>.md` с отпечатком текущего текста | модель-проверяющий |
| на-проверке → утверждён | нет маркеров `[НУЖНО УТОЧНИТЬ]`; все документы из `зависит_от` утверждены; документ-основа из `основан_на` не менялся после планирования; ссылки на код `путь:строка` существуют; каждый источник `SRC-NN` есть в реестре; подпись человека с отпечатком текущего текста | только человек (`sdd.py подписать` отказывает, если запущена из-под Claude Code — переменная `CLAUDECODE`) |
| утверждён → заменён | правка поля `статус` руками; `sdd.py` этот переход не проверяет | человек |

**Отпечаток** — sha256 тела документа без frontmatter. Подпись относится к тому
тексту, под которым её поставили: стоит тексту измениться, и `sdd.py проверить`
показывает «подпись устарела», а документ снова считается черновиком.

**Модель документ не утверждает.** Она может довести его до «на-проверке» и
приложить отчёт, но строку `подпись:` ставит человек.

## Frontmatter

```
---
id: SPEC-001
вид: спека                  конституция | процесс | adr | эталон | требования | архитектура | спека | план | задачи | отчёт
статус: черновик            черновик | на-проверке | утверждён | заменён
версия: 1
зависит_от: CONST, REF-CAP, REQ-CTX
основан_на: SPEC-001 sha256:…    (у плана и задач: на каком тексте основы они построены)
проверяет: CONST sha256:…        (только у отчётов: id и отпечаток проверяемого документа)
подпись: Максим | 2026-09-29T12:00+03:00 | sha256:…
---
```

Формат плоский — «ключ: значение», без вложенности: его разбирает стандартная
библиотека Python, и его легко читать глазами.

## Идентификаторы

| Префикс | Что | Где живёт |
|---|---|---|
| `CONST`, `SDD-PROCESS` | конституция, процесс | docs/ |
| `ADR-NNNN` | архитектурное решение | docs/decisions/ |
| `REQ-CTX` | исходные условия проекта | docs/requirements/context.md |
| `REQ-NNN` | собственное требование ИТ-отдела | docs/requirements/ |
| `Q-NNN` | открытый вопрос владельцу | docs/requirements/context.md |
| `REF-SRC` / `SRC-NN` | реестр источников / один источник | docs/reference/sources.md |
| `REF-MOD-<КОД>` | опись модуля эталона | docs/reference/modules/ |
| `REF-UX` / `UX-NN` | приёмы интерфейса / один приём | docs/reference/ui-patterns.md |
| `REF-CAP` / `CAP-NN` | карта возможностей / одна возможность | docs/reference/capabilities.md |
| `TGT-*` | документ to-be | docs/target/ |
| `SPEC-NNN`, `PLAN-NNN`, `TASKS-NNN` | спека, план, задачи среза | specs/NNN-*/ |
| `FR-NNN` / `NFR-NNN` | требование среза | specs/NNN-*/spec.md |
| `T-NNN` | задача | specs/NNN-*/tasks.md |
| `REV-<id>` | отчёт проверки документа `<id>` | docs/reviews/<id>.md |

Цепочка трассировки: `SRC-NN → CAP-NN → FR-NNN → T-NNN → тест`. В карте
возможностей у каждой строки есть колонка «Решение» — `MVP`, `позже` или
`не нужно`; решение ставит владелец. `sdd.py проверить` печатает, сколько
возможностей MVP уже покрыто спеками и какие нет, и предупреждает, если спека
берётся за возможность «не нужно» или за CAP, которого нет в карте.

## Эталон: как описывается Битрикс КП

- **Каждое утверждение опирается на источник.** Источник — страница
  официальной документации 1С-Битрикс (URL и дата обращения) или снимок экрана
  демо-установки; он регистрируется в `sources.md` как `SRC-NN`. Утверждение
  «по памяти» в эталон не входит: вместо него ставится `[НУЖНО УТОЧНИТЬ: …]`.
- **Описывается поведение, а не реализация** (инвариант «эталон-не-копия»):
  что видит пользователь, какие у него права, что происходит после действия.
- **Подробно — только то, что вошло в MVP.** Карта возможностей охватывает все
  модули; подробная опись нужна только модулям, чьи возможности вошли в MVP.
  Модуль «позже» описывается подробно, когда его возможности берутся в срез.
- **Демо-установка** коробки — отдельный шаг с согласия владельца
  (скачивание дистрибутива, пробный период 30 дней). Снимки экрана — источники
  `SRC-NN` для приёмов интерфейса.

## Разделение работы между моделями

Правило из Дня 20 («модели по точкам вызова выбраны по замеру, а не по
ярлыку») применено к исполнителям Claude Code:

| Работа | Исполнитель | Почему |
|---|---|---|
| Сбор источников по документации, опись модуля по шаблону, снимки экранов демо, сверка ссылок `SRC`/`CAP`/`путь:строка`, формат | Haiku | механика и большой объём чтения |
| Проверка описи Haiku по источникам (каждое утверждение — открыть ссылку), черновики спек, код и тесты по утверждённому плану, проход в браузере | Sonnet | понимание по средней цене |
| Конституция, ADR, карта возможностей и предложение MVP, архитектура, планы, проверка на воротах, сводка | Opus | решения, где ошибка дорогая |
| Решения по карте возможностей, утверждение документов | человек | ответственность за решение |

Черновик Haiku никогда не идёт на подпись напрямую: между ними всегда стоит
проверочный проход Sonnet или Opus. Основание — замеры:
- в ГИС из пяти проверенных утверждений первой инвентаризации Haiku два
  оказались неверными, расшифровку «ЭЗУ» он придумал, а опись эндпойнтов
  написал по памяти, пропустив 7 контроллеров из 36;
- здесь, на шаблонах документов, Haiku в трёх файлах из шести допустил
  ошибку: вписал в план интеграции, которых нет в решениях (LDAP, 1С),
  поставил в `зависит_от` спеки не документы, а коды возможностей
  (`CAP-NN, REQ-NNN` — ворота отклонили бы их как ненайденные) и оставил
  формулировку учебного курса («регрессия предыдущих дней»).

Параллельные исполнители запускаются небольшими партиями: восемь Sonnet
одновременно в ГИС упёрлись в лимит сессии.

## Порядок работы

1. **Основа** — конституция, процесс, ADR-0001 (стек), ADR-0002 (процесс),
   исходные условия `REQ-CTX`. Утверждаются первыми: от них зависит всё
   остальное.
2. **Эталон** — реестр источников, опись модулей Битрикс КП, приёмы
   интерфейса, карта возможностей. Владелец ставит решение каждой возможности:
   MVP / позже / не нужно.
3. **Требования ИТ-отдела** — роли, очереди и SLA, каналы заявителей,
   интеграции (почта, Telegram/MAX, Zabbix, АСДОБ), объёмы.
4. **To-be** — архитектура, нефункциональные требования, модульная схема,
   порядок срезов (ADR).
5. **Срезы** — `specs/NNN-*/`: spec → plan → tasks → код → проход в браузере →
   отчёт проверки, каждый шаг через ворота.
