# Конституция портала ИТ-отдела

Это правила, которые не пересматриваются от среза к срезу. Спека, план или код,
которые им противоречат, не проходят ворота: жёсткие правила проверяет
`tools/sdd.py`, смысловые — проверяющий на воротах, а подпись ставит человек.

Источник правды — `docs/constitution.json` (формат инвариантов агента Дня 20:
правило, почему, вместо, значения). Раздел ниже собирается из него командой
`python3 tools/sdd.py собрать-конституцию`, руками его не правят.

Все принципы ниже выбраны владельцем 2026-09-29 из предложенных вариантов.
Новый принцип добавляется со статусом «предложен»; пока такие есть,
конституцию не утвердить — каждый нужно либо принять, либо убрать.

Проверка кода по жёстким правилам идёт по каталогам `backend/`, `frontend/`
и `deploy/`, кроме `backend/static/vendor/`: там лежат сторонние библиотеки,
перенесённые без правок, с версиями и sha256 в `VERSIONS.md`. Правила этой
конституции относятся к нашему коду, а не к чужому (решение владельца
2026-10-01, версия 2).

## Стек

### стек-бэкенд — принят
Сервер — только Django: фоновые задачи на RQ, живые обновления на Channels. Посторонние веб-фреймворки и очереди не предлагать и не подключать.

- **Почему:** один стек с проектами Газоwiki и ГИС: один человек сопровождает все три, а встроенная админка Django сама закрывает справочники и настройки (инвариант «настройка-без-кода»)
- **Вместо:** Django 5.x; django-rq поверх Redis для фона; Django Channels для чата и живой ленты; DRF — только там, где API нужен интеграции
- **Проверка:** запрет-слов: `fastapi`, `flask`, `laravel`, `symfony`, `express`, `nestjs`, `rails`, `spring`, `celery`
- **Источник:** ADR-0001

### стек-интерфейс — принят
Интерфейс собирается на сервере: шаблоны Django + HTMX, небольшие вставки Alpine.js. SPA-фреймворки не подключаются.

- **Почему:** второй стек (сборка, состояние на клиенте, дублирование проверок прав) удвоил бы объём кода для портала на ~100 рабочих мест; интерактивность Битрикса (канбан, живая лента, слайдер карточки) достижима фрагментами HTMX и WebSocket
- **Вместо:** шаблоны Django + HTMX (hx-get/hx-post/hx-swap, hx-ext=ws), Alpine.js для локального состояния, Bootstrap 5 со своей темой, SortableJS для перетаскивания
- **Проверка:** запрет-слов: `react`, `vue`, `angular`, `svelte`, `nuxt`, `nextjs`
- **Источник:** ADR-0001

### бд — принят
База данных — только PostgreSQL, в том числе в тестах.

- **Почему:** полнотекстовый поиск по-русски, JSONB для настраиваемых полей, row-level блокировки очередей заявок — всё это есть только в PostgreSQL; тесты на другой СУБД проверяли бы не ту систему
- **Вместо:** PostgreSQL 17 (django.db.backends.postgresql), тестовая база — тоже PostgreSQL в контейнере
- **Проверка:** запрет-слов: `mysql`, `mariadb`, `mongodb`, `sqlite3`, `oracle`, `mssql`
- **Источник:** ADR-0001

### бесплатные-компоненты — принят
Компоненты — с открытой лицензией, без платы за рабочее место. Платный компонент попадает в проект только отдельным ADR с пометкой «платно» и ценой.

- **Почему:** портал строится как собственная замена коробочному Битриксу; зависимость от платной лицензии возвращает ту же проблему, от которой уходим
- **Вместо:** открытые библиотеки (MIT/BSD/Apache/LGPL/GPL — лицензия записывается в plan.md среза); если бесплатной замены нет — ADR с альтернативами и ценой
- **Проверка:** на воротах, проверяющим
- **Источник:** решение владельца 2026-09-29 (как в Газоwiki)

## Архитектура

### модуль-приложение — принят
Каждый модуль портала (заявки, задачи, лента, диск, …) — отдельное приложение Django. Модули связаны через сервисный слой и события, а не прямым импортом чужих моделей; модуль можно выключить, не сломав остальные.

- **Почему:** Битрикс КП — это десятки модулей, и портал будет расти так же; без границ между модулями каждый новый срез задевает все старые, а выключить ненужное невозможно
- **Вместо:** apps/<модуль>/services.py — публичный интерфейс модуля; сигналы/события для реакций других модулей; общие сущности (сотрудник, подразделение, файл, комментарий) — в ядре
- **Проверка:** на воротах, проверяющим
- **Источник:** решение владельца 2026-09-29

### настройка-без-кода — принят
Очереди, категории заявок, SLA, рабочий календарь, маршруты согласования, роли и справочники — данные, которые администратор меняет в интерфейсе, а не константы в коде.

- **Почему:** в Битриксе это настраивается мышью, и ИТ-отдел ждёт того же; значение, зашитое в код, превращает каждую смену регламента в релиз
- **Вместо:** модели-справочники с админкой Django или своим разделом «Настройки»; в коде — только значения по умолчанию для первой установки (миграции данных)
- **Проверка:** на воротах, проверяющим
- **Источник:** решение владельца 2026-09-29 (как в Газоwiki)

### интеграции-через-адаптеры — принят
Каждая внешняя система (почта, Telegram/MAX, Zabbix, АСДОБ) подключается своим адаптером через очередь с повтором. Отказ внешней системы не теряет заявку и не роняет портал.

- **Почему:** почта — основной канал заявителей без учётной записи: потерянное письмо — потерянная заявка; синхронный вызов внешней системы из запроса пользователя вешает страницу, пока та недоступна
- **Вместо:** apps/integrations/<система>/ с единым интерфейсом адаптера; входящее — сначала сохраняется, потом разбирается; исходящее — задание RQ с повторами и журналом доставки
- **Проверка:** на воротах, проверяющим
- **Источник:** решение владельца 2026-09-29

## Бизнес-правило

### аудит-изменений — принят
Изменения заявок, задач, прав и настроек журналируются: кто, когда, что было, что стало. Журнал только дописывается.

- **Почему:** споры «кто закрыл заявку» и «кто дал права» решаются журналом, а не памятью; журнал, который можно править, ничего не доказывает
- **Вместо:** таблица событий, куда пишут сервисы модулей (без UPDATE/DELETE у роли приложения); история в карточке заявки и задачи строится из неё
- **Проверка:** на воротах, проверяющим
- **Источник:** решение владельца 2026-09-29

## Безопасность

### секреты-вне-кода — принят
Пароли, ключи API, токены ботов и SECRET_KEY не хранятся в коде и конфигах репозитория — только в окружении.

- **Почему:** портал смотрит в интернет: ключ, однажды попавший в git, живёт во всех клонах; в ГИС секреты пришлось вырезать фильтром из истории
- **Вместо:** переменные окружения / .env вне git (django-environ), в репозитории — .env.example с заглушками; pre-commit tools/check_secrets.py; в тестах пароль не пишется литералом, а создаётся в общей фикстуре (secrets.token_urlsafe()) — решение владельца 2026-09-29 после ложного срабатывания на тестовый пароль, записанный литералом
- **Проверка:** запрет-регулярок: `(?i)(password|passwd|secret|api_?key|token)\s*[:=]\s*['"][^'"$*{]{4,}['"]`, `(?:^|[\s\-])[A-Z0-9_]*PASSWORD\s*[=:]\s*[^\s"'$*{()]{4,}\s*$`
- **Источник:** проект ГИС (инвариант «секреты-вне-кода»)

### секреты-в-url — принят
Секреты и одноразовые коды не передаются в URL — только в теле запроса, заголовке или сессии.

- **Почему:** URL оседают в логах nginx, истории браузера и заголовке Referer; ссылки из писем пересылаются дальше
- **Вместо:** сессия или заголовок Authorization; одноразовая ссылка (приглашение сотрудника, сброс пароля) — код, который обменивается на сессию POST-запросом
- **Проверка:** запрет-регулярок: `[?&](password|passwd|pwd|pass|token|secret|api_?key)=`, `://[^/\s]+:[^/@\s]+@`
- **Источник:** проект ГИС (инвариант «секреты-в-url»)

### sql-только-параметры — принят
SQL строится только ORM или параметризованным запросом; подстановка ввода в текст SQL запрещена.

- **Почему:** портал принимает текст от заявителей без учётной записи — через открытую форму в интернете и письма; это прямой путь к инъекции
- **Вместо:** Django ORM; сырой SQL — cursor.execute(sql, params) с плейсхолдерами %s; имена полей сортировки и фильтров — только из белого списка
- **Проверка:** запрет-регулярок: `\.(execute|raw|extra)\(\s*f["']`, `\.(execute|raw)\([^)]*["']\s*%\s*[(\w]`, `\.(execute|raw)\([^)]*["']\s*\+\s*\w`, `\.(execute|raw|extra)\([^)]*\.format\(`
- **Источник:** проект ГИС (инвариант «sql-только-параметры»)

### двухфакторная-авторизация — принят
Двухфакторная авторизация обязательна для каждой учётной записи портала; вход защищён от перебора паролей.

- **Почему:** портал доступен из интернета, а учётные записи есть только у сотрудников ИТ и администраторов — все они видят чужие заявки и персональные данные заявителей
- **Вместо:** TOTP (django-otp) с резервными кодами; ограничение попыток входа и блокировка по IP/учётной записи (django-axes); заявители учётных записей не имеют и в портал не входят: заявку подают письмом или формой, ответы получают письмами
- **Проверка:** на воротах, проверяющим
- **Источник:** решение владельца 2026-09-29

### пдн-152фз — принят
Персональные данные обрабатываются по 152-ФЗ: минимум полей, согласие заявителя, срок хранения. Во внешние каналы (Telegram, MAX) уходят только событие и ссылка — без ФИО и текста заявки.

- **Почему:** заявители пишут без учётной записи — их ФИО, почта и телефон приходят вместе с текстом заявки; мессенджеры — чужие серверы
- **Вместо:** согласие на форме и в автоответе на письмо; в уведомлении мессенджера — «Новая заявка №123 в очереди „Сеть“: <ссылка>»; сроки хранения — настройкой
- **Проверка:** на воротах, проверяющим
- **Источник:** решение владельца 2026-09-29 (как в Газоwiki)

## Процесс

### эталон-не-копия — принят
Битрикс КП — эталон поведения и интерфейса, но его код, вёрстка, иконки, тексты и названия в проект не копируются.

- **Почему:** код и оформление 1С-Битрикс защищены лицензией; повторять можно поведение и приёмы интерфейса, а не чужую реализацию
- **Вместо:** поведение описывается в docs/reference/ со ссылками на источники SRC-NN и реализуется заново; свои иконки (открытый набор) и свои тексты
- **Проверка:** запрет-слов: `bitrix`, `bx24`
- **Источник:** решение владельца 2026-09-29

### спека-прежде-кода — принят
Код пишется только под утверждённый план, план — под утверждённую спеку; утверждает человек.

- **Почему:** решения принимает владелец системы, а не исполнитель; иначе архитектура складывается из случайных решений по ходу кода
- **Вместо:** docs/sdd-process.md: черновик → на-проверке → утверждён, подпись с отпечатком (tools/sdd.py подписать)
- **Проверка:** на воротах, проверяющим
- **Источник:** агент Дня 20: ворота перехода, подпись под планом; проект ГИС

### тест-на-требование — принят
У каждого FR среза есть задача и тест, который его закрывает; срез сдаётся проходом в настоящем браузере, а не только тестами сервера.

- **Почему:** в курсе AI-Advent-Challenge тесты сервера не видели кнопок, зовущих несуществующие функции, и гонок двух запросов из одной страницы — это ловил только проход в браузере
- **Вместо:** tasks.md: T-NNN → FR-NNN → имя теста; Playwright-сценарий по приёмке спеки; отчёт прохода в docs/reviews/
- **Проверка:** на воротах, проверяющим
- **Источник:** решение владельца 2026-09-29; опыт Дней 13–20
