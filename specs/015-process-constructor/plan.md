# План среза 015: Конструктор процессов

План построен на подписанной SPEC-015 (отпечаток `621fafa9…`). Три развилки спеки вынесены владельцу формой
2026-11-28 (`crm-work/slice015/owner-questions-2026-11-28.md`); план следует записанным рекомендациям, а
подпись спеки их подтверждает. Независимое ревью плана выполняет модель другого семейства (OpenAI
`gpt-6.1-sol`), не DeepSeek Flash — правило владельца 2026-11-28.

## Сверка с конституцией

- **модуль-приложение.** Вся логика — в `lists`; другие приложения не импортируются. Единственная правка вне
  приложения — регистрация минутного задания в `backend/config/cron.py`. Ссылки на узлы структуры — числа, как
  у `lists.Access`; ссылки на записи и стадии — внутри `lists`.
- **настройка-без-кода.** Процесс, стадии, права, обязательные поля и расписание — данные. Начальных процессов
  нет; миграция их не создаёт.
- **права и минимум доступа.** Права стадии только сужают права списка; нечитаемая стадия скрывает запись на
  всех поверхностях; управляющий списками — единственное исключение. Новых глобальных прав нет.
- **аудит-изменений.** Настройка процесса, стадий, прав и полей, включение/выключение и переходы — в журнал
  `core.services.audit.record`; ручные изменения с автором, минутное задание — с пустым. История записи
  получает строку перехода.
- **пдн-152фз.** В журнал и аудит запусков не попадают название записи и значения полей; только номера,
  идентификаторы и названия списка/стадий. Тестовые данные синтетические.
- **sql-только-параметры.** Все выборки — ORM; фильтры и сортировка — из белого списка полей; доска использует
  оконные функции ORM, без подстановки текста.
- **стек-бэкенд / стек-интерфейс.** Django 5.2, PostgreSQL 17, HTMX, Alpine.js, RQ; новых пакетов нет. Доска —
  по образцу `servicedesk` (HTML5 drag-and-drop, без SortableJS).
- **тест-на-требование.** Каждый FR-851…892 и NFR-750…753 получает серверный, браузерный или нагрузочный тест;
  трассировка — ниже.
- **эталон-не-копия.** Берём только поведение: стадии, права, обязательные поля, запуск; вёрстку и тексты
  эталона не копируем.

## Модель данных, ограничения и индексы

### `ListProcess` (таблица `lists_listprocess`)

| Поле | Тип | Правило |
|---|---|---|
| `list` | OneToOne `List` | `on_delete=CASCADE`, `related_name="process"`; один процесс на список |
| `title` | строка 100 | пусто = название списка |
| `author` | FK `core.User` | `PROTECT`, `null`; задаётся при первом включении, меняется при повторном |
| `enabled` | да/нет | по умолчанию нет |
| `launch_mode` | `manual` / `schedule` | по умолчанию `manual` |
| `schedule_period` | `daily` / `weekly` / `monthly` | пусто при `manual` |
| `schedule_weekday` | 1…7 | только `weekly` |
| `schedule_monthday` | 1…28 | только `monthly` |
| `schedule_time` | время | по Москве; обязательно при `schedule` |
| `title_template` | строка 200 | `{дата}` подставляется |
| `created_at`, `updated_at` | время | `timezone.now` |

Ограничения: период и день согласованы (`daily` — оба пусты; `weekly` — день недели есть, день месяца пуст;
`monthly` — наоборот); при `schedule` время не пусто. Индекс — `(enabled, launch_mode)` для тика.

### `ProcessStage` (`lists_processstage`)

`process` FK CASCADE, `title` 100, `order`, `kind` `open`/`closed`. Ограничения: `(process, order)` уникален,
`(process, Lower(title))` уникален. Индекс `(process, order)`. Перестановка порядка выполняется в одной
транзакции через временные отрицательные значения, иначе уникальность `(process, order)` сработает на
промежуточном шаге.

### `ProcessStageAccess` (`lists_processstageaccess`)

`stage` FK CASCADE, `level` `read`/`edit`, `role` FK `core.Role` PROTECT null, `unit_id` число null. Одно
ограничение «ровно один субъект»; уникальность `(stage, level, role)` и `(stage, level, unit_id)`; индексы по
роли и узлу — как у `lists.Access`.

### `ProcessStageField` (`lists_processstagefield`)

`stage` FK CASCADE, `field` FK `Field` CASCADE; уникальность `(stage, field)`; индекс `(field)`.

### `Record.stage`

FK `ProcessStage` `PROTECT`, `null`, `blank`; индекс `(list, stage)`. Служба проверяет, что стадия принадлежит
процессу того же списка. `PROTECT` не даёт удалить стадию с записями; список с записями удалить нельзя
(срез 006), поэтому каскад процесса не оставляет висящих стадий.

### `StageMove` (`lists_stagemove`)

`record` FK CASCADE, `base_version`, `from_stage_key` (число, null) и `to_stage_key` (число, не null) —
неизменяемые снимки идентификаторов стадий, `from_stage` и `to_stage` FK `SET_NULL` null, `from_title` и
`to_title` строки 100 (снимок названий), `actor` FK PROTECT null, `at`. Уникальность
`(record, base_version, to_stage_key)` — ключ идемпотентности; индекс `(record, at)`. Ключ и поиск повтора
используют числовой `to_stage_key`, а не nullable FK: удаление пустой целевой стадии обнуляет `to_stage`, но
не ломает повтор. `from_stage_key` может быть пустым: запись без стадии переводится на первую/любую видимую
стадию (история — «Без стадии → X»). Снимок названий и `SET_NULL` нужны, чтобы удалить стадию без записей
(FR-854), не потеряв историю переходов: удаление пустой A после A → B не блокируется, строка перехода
остаётся читаемой по `from_title`.

### `ProcessLaunch` (`lists_processlaunch`)

`process` FK CASCADE, `period_start` дата, `status` `created`/`skipped`/`failed`, `record` FK `Record`
`SET_NULL` null, `reason` строка 200, `created_at`. Уникальность `(process, period_start)`; индекс
`(status, period_start)`.

### Миграция

`0003_process.py`: `CreateModel` шести моделей (`ListProcess`, `ProcessStage`, `ProcessStageAccess`,
`ProcessStageField`, `StageMove`, `ProcessLaunch`), `AddField` `Record.stage`, ограничения и индексы.
Обратной миграции данных нет; `RunPython` не нужен. Существующие записи получают `stage = NULL`; процессов
нет.

## Права и видимость

Единственное место решений — `lists/services/access.py`:

- `stage_scope(user, lst)` — кэш на запрос (`user._lists_stage_scope`): `None`, если процесс выключен или
  пользователь управляющий; иначе `StageScope(read=frozenset, edit=frozenset)` по стадиям списка. Пустой набор
  прав стадии наследует права списка; явный набор сужает: чтение — список читается И стадия в `read`/`edit`;
  правка — список правится И стадия в `edit`. Подразделение — цепочка узлов, как `access.scope`.
- `can_read_record(user, record)` / `can_edit_record(user, record)` — список + стадия; запись без стадии
  читается и правится по правам списка.
- `record_condition(user, lst)` — `Q(stage__isnull=True) | Q(stage_id__in=...)` или `None` для управляющего и
  выключенного процесса. Обязателен во всех выборках записей, включая независимые:
  `grid.records`, доска, `search._readable` и `search._exact_ids` (глобальное условие видимых стадий),
  `export`, `links.pinned`/`referrers`, `history.for_viewer`, `services/values` (показ ссылок и справочники
  импорта), `services/tickets.py`, `views/records._ref_items`, `views/grid._labels`,
  `views/grid.filter_values` (подсказка фильтра), `views/pickers`, `views/labels`, `imports` (стадия
  владельца и первой стадии), `archive`/bulk.
- Карточка, GET правки и история проверяют `can_read_record` **до** построения контекста (не полагаются на
  `get_record`, который эти представления не вызывают); нечитаемая стадия — 404 без названия и значений.
- Прямой адрес записи на нечитаемой стадии — 404 (`get_record` и те же проверки в представлениях).
- Ссылочные значения, история и «Закреплённое»: запись нечитаемой стадии показывается как «запись
  недоступного списка» без названия и ссылки; в подсказке выбора и подсказке фильтра её нет; этикетка и
  скачивание файла недоступны.
- Файлы: прикрепление и удаление проверяют право правки стадии (не только списка); нечитаемая запись — 404,
  нет правки стадии — отказ без отрисовки блока файлов; последний файл обязательного поля текущей стадии
  удалить нельзя (`StageRequired`). Выключенный процесс сохраняет прежнее поведение.
- Уникальность: если значение занято записью нечитаемой стадии, отказ `unique_taken` без номера и ссылки.
- Выключенный процесс: ограничений стадии нет, записи читаются и правятся по правам списка; доска и колонка
  скрыты.

## Службы и порядок вызовов

### Настройка процесса (`services/process.py`)

- `get_or_create(lst, actor)` — строка процесса создаётся при первом открытии вкладки; `author` пуст, пока
  процесс не включён.
- `save_settings(lst, actor, **data)` — проверка `lists.manage`, замок списка исключительный, проверка
  названия/режима/расписания/шаблона; включение и выключение отдельными ветками:
  - **первое/повторное включение**: автор — включивший; стадии должны существовать, быть не меньше одной
    открытой; `Record.objects.filter(list=lst, archived=False, stage__isnull=True).update(stage=first,
    version=F("version")+1, updated_by=actor, updated_at=now)`; журнал `lists.process_enabled` с числом
    переведённых и автором; истории переходов нет.
  - **выключение**: журнал `lists.process_disabled`, стадии записей не меняются.
  - **правка**: журнал `lists.process_changed` с автором.
- `add_stage` / `update_stage` / `delete_stage` / `move_stage` — проверки: название 1…100, уникальность без
  учёта регистра, не меньше одной открытой стадии, удаление последней/последней открытой запрещено, удаление
  стадии с записями запрещено (`Record.stage` — `PROTECT`), порядок пересчитывается. Перестановка идёт в
  одной транзакции через временные отрицательные значения порядка, чтобы не нарушить уникальность
  `(process, order)`; журнал `lists.process_stage_changed`.
- `save_stage_access(stage, read, edit, actor)` — роли и узлы, явный пустой набор запрещён, уровень `edit`
  включает чтение; журнал `lists.process_stage_access_changed`.
- `save_stage_fields(stage, codes, actor)` — только видимые поля того же списка; журнал
  `lists.process_stage_fields_changed`.
- `hide_field_hook(field, actor)` — при скрытии поля в схеме удаляет `ProcessStageField` этого поля во всех
  стадиях списка и пишет журнал; вызывается из `schema._set_hidden` после успешного скрытия.
- `visible_stages(lst)` — открытые и закрытые по порядку; `first_open(lst)`.

### Переход (`services/transitions.py`)

Порядок — как в SPEC-015:

1. `lock_list(shared=True)` → `select_for_update` записи.
2. Проверка текущего чтения записи (список + текущая стадия; для записи без стадии — только список;
   управляющий — исключение), иначе `Http404`.
3. Поиск `StageMove(record, base_version, to_stage_key)` — по исходному числовому ключу, до загрузки и
   проверки существования целевой стадии; найден — вернуть сохранённый результат (`200`).
4. Версия не совпала — `VersionConflict`; ожидаемая стадия не совпала — `StageChanged`.
5. Право записи текущей стадии (для записи без стадии — правка списка) и чтение целевой —
   `PermissionDenied` / `StageForbidden`.
6. Итоговые значения: `record.values` + присланные коды; отсутствие сохраняет, явная пустота удаляет; разбор
   через `values.parse`, как в `records.save`; название, если прислано, проверяется и пишется вместе с полями,
   отсутствие сохраняет прежнее; обязательные поля целевой и текущей стадии — `StageRequired`; поле «файл» —
   наличие `RecordFile`.
7. Транзакция: значения, стадия, `StageMove` (`from_stage_key` пуст для записи без стадии, `from_title` —
   «Без стадии», `to_stage_key` — идентификатор цели), `history.write(kind="stage")`, `audit.record`
   `lists.record_stage_changed` (номер, стадии, без названия и значений), `version += 1`.
8. `IntegrityError` уникального ключа — перечитать и вернуть сохранённый результат.

### Создание, правка, загрузка

- `records.create` — при включённом процессе: проверить чтение первой открытой стадии до создания; записать
  `stage=first_open`; история создания как прежде.
- `records.save` — при включённом процессе: проверить `can_edit_record` (список + стадия), а не только
  `can_edit` списка; обязательные поля стадии проверить на итоговом состоянии; очистка обязательного поля
  стадии — `StageRequired`.
- `records.create_system` — внутренний вход для планового запуска: без проверки права правки, но с разбором
  значений, уникальностью, вектором, историей; `created_by = author процесса`, `stage = first_open`.
- `imports.confirm` — до создания строк проверить чтение первой открытой стадии загружающим; `create_locked`
  получает стадию; ошибки строк прежние.
- `imports.confirm` при обновлении владельца уникального значения (`will_update`): после блокировки найденной
  записи проверить `can_edit_record` (список + её текущая стадия) и обязательные поля стадии на итоговом
  состоянии, иначе строка — ошибка без обновления через `records.update_locked`. В предпросмотре владелец
  нечитаемой стадии не раскрывается: ни номера, ни названия, только «значение уже занято».
- `archive.restore` — прежняя стадия сохраняется; если стадии нет и процесс включён — первая открытая;
  обязательные поля при восстановлении не требуются, их проверит ближайшая правка или переход.
- `services/files.attach/delete` и `views/files` — право правки стадии; удаление последнего файла
  обязательного поля текущей стадии отклоняется `StageRequired`; нечитаемая запись — 404, отказ без HTML
  блока файлов.

### Плановый запуск (`services/schedule.py`, `tasks.process_launch_tick`)

- `due(process, now_msk)` → `(period_start, due_at)` или `None`: день/неделя (понедельник)/месяц (1…28),
  время по Москве; следующая точка после `due_at` — следующий период.
- `tick()` — выбрать процессы `launch_mode=schedule`, для которых срок наступил; для каждого:
  1. вложенная транзакция: `ProcessLaunch.objects.create(process, period_start, status="skipped")`; нарушение
     уникальности — пропустить (уже запускался).
  2. процесс выключен, нет открытой стадии, обязательные поля первой стадии не заполняются умолчаниями —
     `status="skipped"`, причина, журнал `lists.process_launch_skipped`, коммит.
  3. иначе `records.create_system` в точке сохранения: заголовок по шаблону (`{дата}` → ДД.ММ.ГГГГ, пусто —
     «Название процесса — дата»), значения по умолчанию, стадия — первая открытая; `status="created"`,
     `record`; журнал `lists.process_launch_created` с пустым автором.
  4. ошибка создания — откат точки сохранения, `status="failed"`, причина, журнал `lists.process_launch_failed`;
     повтор только в следующем периоде.
- Простой: тик считает только текущий период; число пропущенных периодов с последней строки/включения
  пишется одной записью журнала `lists.process_launch_missed`; карточки за пропущенные периоды не создаются.
- Удаление списка/процесса — каскад, строки запусков удаляются; тик их не видит.

### Доска (`services/board.py`)

- `columns(lst, viewer, gp)` — стадии по порядку, которые читает зритель, плюс «Без стадии», если есть
  видимые записи без стадии. Набор — `grid.records` с `record_condition`; `preset=archive` на доске
  игнорируется (записи в архиве не показываются и не считаются), фильтры, поиск и **та же сортировка**, что
  у таблицы (`title`, поле, направление, `number` как последний ключ). Оконная функция
  `ROW_NUMBER() OVER (PARTITION BY stage_id ORDER BY <то же выражение сортировки>)` даёт первые 50,
  `COUNT(*) OVER (PARTITION BY stage_id)` — счётчик; один запрос на доску. Счётчики и страницы учитывают
  права стадии.
- `column(lst, viewer, gp, stage, offset)` — 50 записей со смещением по тому же порядку; «показать ещё»;
  прямой запрос колонки с `preset=archive` отдаёт пусто, а не архивные записи.
- `move(...)` — вызывает `transitions.move` с `base_version` и ожидаемой стадией.

### Таблица, выгрузка, поиск, связи

- `grid.read` принимает `stage` (повторяемый параметр) и `sort=stage`; `grid.records` применяет
  `record_condition`, фильтр стадий и сортировку `(stage__order, number)`; «Без стадии» — первые. Доска
  переиспользует это же выражение сортировки в оконной функции, а не `ORDER BY number`.
- `grid.columns` добавляет системный столбец «Стадия» после «Названия», не сохраняя его в `UserView`.
- `export` добавляет колонку «Стадия» и использует тот же набор и права.
- `search._readable` добавляет условие видимых стадий по читаемым спискам; точные совпадения уникальных полей
  и вектор — в том же условии.
- `links.pinned` и `referrers` фильтруют записи нечитаемых стадий; `history.for_viewer` показывает
  «запись недоступного списка»; `views/records._ref_items`, `views/grid._labels`, `pickers.record`,
  `labels.sheet` — те же права.
- `unique` предварительная проверка: владелец значения на нечитаемой стадии даёт `unique_taken` без номера и
  ссылки.

## Риски и открытые вопросы

- **Скрытие на всех поверхностях.** Легко забыть ссылочные значения, историю, «Закреплённое», подсказки и
  уникальность; тесты `test_lists_process_access` перечисляют каждую поверхность, ревью проверяет список.
- **Гонка перехода.** Уникальный ключ `(record, base_version, to_stage_key)` — единственная защита от второго
  перехода; служба ловит `IntegrityError` и возвращает сохранённый результат. Тест — 20 POST.
- **Порядок проверок.** Чтение — до любого ответа, включая повтор и «та же стадия»; иначе отзыв доступа не
  действует. Тест — повтор после отзыва и другой сотрудник без доступа.
- **Обязательные поля.** Итоговое состояние, а не только присланные значения; иначе перенос с доски с уже
  заполненными полями даст ложный отказ. Тест — перенос без значений и явная очистка.
- **Плановый запуск.** Строка периода создаётся первой; ошибка карточки не откатывает её; иначе тик
  повторит ошибку каждую минуту. Тест — `failed` и отсутствие повтора.
- **Простой.** Тик не нагоняет пропущенные периоды; иначе после отпуска появится лавина карточек. Тест —
  месяц простоя.
- **Производительность доски.** Оконная функция и один запрос; без неё 10 стадий дадут 20 запросов и провал
  NFR-750. Тест — `assertNumQueries` и `EXPLAIN`.
- **Три развилки владельца.** Ответа на форму пока нет; план следует рекомендациям. Если владелец выберет
  другой вариант, меняются FR-856, FR-860 и FR-876…878, а также модели `ListProcess`, `ProcessLaunch` и
  служба расписания; до кода это уточняется.
- **Стенд.** Миграция без сброса; данных срез не добавляет; нагрузочный заполнитель — отдельный шаг.

## Решения плана

1. `ListProcess` — one-to-one со списком; `author` пуст до первого включения, при повторном включении
   меняется на включившего.
2. Включение переводит только записи без стадии; уже назначенные стадии не сбрасываются. Массовое назначение
   повышает версию записей без строк истории; в журнале — число и автор.
3. Права стадии считаются в `access.py`, кэш на запрос; `record_condition` — обязательный фильтр всех
   выборок. Управляющий и выключенный процесс — без ограничения.
4. Переход идентифицируется `(record, base_version, to_stage_key)`; проверка чтения — до любого ответа; версия —
   до полей; итоговые значения — сохранённые плюс присланные.
5. `StageMove` — отдельная строка, а не только запись истории; ключ идемпотентности —
   `(record, base_version, to_stage_key)`, где `to_stage_key` — числовой снимок, не обнуляемый при удалении
   стадии; FK и названия — только для чтения истории.
6. Доска — один запрос с оконными функциями; колонки, счётчики и страницы по 50; без ручного порядка.
7. Расписание — `ProcessLaunch` с уникальным `(process, period_start)`; строка создаётся первой в точке
   сохранения, ошибка карточки даёт `failed`; простой не нагоняется.
8. Плановое создание идёт через `records.create_system` с автором процесса и без проверки права правки.
9. Журнал: ручные действия с автором, минутное задание с пустым; названия записей и значения полей не
   пишутся.
10. Новых точек расширения, приложений и глобальных прав нет; единственная правка вне `lists` —
    регистрация минутного задания в `config/cron.py` и две проверки `test_lists_deploy.py`.
11. Индекс стадий — `ProcessStage(process, order)`; в SPEC-015 методика называет его сокращённо
    `(stage, order)`. План проверяет фактический индекс; подписанная спека не правится.
12. Красные тесты T-15003 и T-15004 пишутся до реализации поведения; T-15005 и следующие задачи
    реализуют только то, что уже зафиксировано проверками. Общая база — последовательно, под общей
    блокировкой; после каждого этапа — независимая проверка OpenAI.
