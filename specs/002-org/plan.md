# План среза 002: оргструктура

Как реализовать SPEC-002: модели, маршруты, проверка файлов, календарь,
развёртывание и проверка. Срез строится на механизмах среза 001 (PLAN-001):
права через роли, журнал `audit.record`, письма заданием RQ, слайдер карточки,
сетка списка, стенд и приёмка Playwright. Здесь описано только новое и то, что в
срезе 001 меняется.

Технические решения плана принимал Opus, владелец их не выбирал. Они
утверждаются подписью под этим планом. Главные из них:
- **Модуль `org` и точки расширения ядра.** Дерево, членство, увольнение,
  календарь и загрузка сотрудников живут в приложении `org` (TGT-ARCH). Ядро об
  `org` не знает. Всё, что `org` добавляет на страницы ядра (фильтр
  подразделения в списке, раздел карточки, права от узлов, пункты меню, названия
  событий журнала), он регистрирует в ядре при запуске.
- **Файл производственного календаря — CSV в формате открытых данных Минтруда.**
  Набор «Производственный календарь» (7708660670-proizvcalendar) публикует
  портал data.gov.ru, по его описанию в одном файле лежат все годы. Сайт
  xmlcalendar.ru отдаёт файл того же формата на каждый год (`calendar.csv`).
  Разбор сверяется с итоговыми колонками самого файла. Проверено 2026-10-04 на
  файлах 2024–2027 с xmlcalendar.ru: число рабочих дней, нерабочих дней и часов
  при 40-часовой неделе совпало с итогами в каждом файле. Файл с data.gov.ru не
  скачан (страница набора открывается только скриптом), поэтому совпадение его
  формата с файлами xmlcalendar.ru на нём самом не проверено.
- **Своё поле выбора даты, без сторонней библиотеки.** Сетку месяца рисует
  сервер фрагментом HTMX с отметками рабочего календаря, а небольшой внешний
  скрипт открывает её и переносит дату в поле.
- **Путь файла и ClamAV — уже в срезе 002**, для фото (ADR-0007, «Последствия»).
  Хранилище файлов и их проверка — в ядре, связь с clamd — в адаптере
  `apps/integrations/clamav/`, контейнер `clamav` — в составе установки.
- **Файлы загрузки (таблица сотрудников, календарь) антивирусом не
  проверяются.** Они не сохраняются и никому не выдаются, поэтому защита
  строится на строгом разборе: предел размера, проверка формата по содержимому,
  безопасный разбор XML.

### Точки расширения ядра

Модуль `apps/core/extensions.py` хранит списки функций, которые другие
приложения регистрируют в `AppConfig.ready()`. Без зарегистрированных функций
ядро ведёт себя как после среза 001.

| Точка | Что даёт | Что регистрирует `org` |
|---|---|---|
| `menu_items` | пункты левого меню: право, адрес, название, значок, порядок | «Структура» (право `staff.view`), «Календарь» (право `staff.view` или `calendar.manage`) |
| `role_sources` | дополнительные роли записи: функция «запись → пары (роль, название источника)». `permissions_of` объединяет их с личными ролями, а карточка подписывает ими роли по источникам (FR-122) | роли узлов, где запись состоит, и их вышестоящих (FR-120). При изменении членства, ролей узла и при переносе поддерева `org` сбрасывает ключи `perms:<id>` через `permissions.forget_users` |
| `role_usage` | проверка «роль используется» перед удалением роли | «роль назначена узлу» (FR-120) |
| `audit_labels` | названия событий, полей и видов объекта журнала по-русски | события среза (раздел «Журнал» ниже) |
| `staff_directory` | фильтры, пресеты, условие поиска, колонки строк и кнопки над списком «Сотрудники» | фильтр «Подразделение» с вложенными, пресет «Без подразделения», поиск по названию узла, колонка «Подразделение», кнопка «Загрузить из таблицы» |
| `card_sections` | разделы карточки сотрудника: шаблон и контекст по правам смотрящего | «Подразделение», «Руководитель», «Подчинённые», роли по источникам, «Уволить» и «Вернуть на работу» |
| `day_marks` | отметки дней месяца для поля даты | вид дня по рабочему календарю (FR-148) |
| `home_notices` | уведомления на главной: функция «смотрящий → список уведомлений» | напоминание о загрузке календаря обладателю `calendar.manage` (FR-146) |
| `stand_reset` | очистка данных модуля командой `e2e_reset_stand` (только стенд) | структура до корня, календарь по умолчанию, загрузки |

Названия событий журнала по-прежнему хранятся в одном месте на модуль, общем для
страницы и выгрузки (PLAN-001, «Журнал по-русски»): у ядра — в `audit_labels.py`
и `audit_search.py`, у `org` — в `apps/org/audit_labels.py`.

Список «Сотрудники» и карточка коллеги открываются по `staff.view` или
`accounts.manage`. Для этого в ядре пункт меню «Сотрудники» и проверка маршрутов
списка, карточки, выдачи фото и страницы календаря принимают любое из
перечисленных в «Контрактах» прав: сейчас `MENU` и `require_permission` знают
одно право на пункт и на маршрут, а план добавляет проверку «одно из»
(`require_any_permission`). Служебные разделы карточки остаются под правами
SPEC-001 (FR-119). Так FR-118 уточняет SPEC-001 FR-004, FR-014 и FR-020: в срезе
001 список был только у `accounts.manage`. Это уточнение войдёт в следующую
версию SPEC-001.

### Запуск

Стенд и приёмка — как в PLAN-001 (`deploy/dev-up.sh`, порт 8031, Mailpit 8025).
Новое:
- служба `clamav` в основном наборе (не только в dev): образ закрепляется
  версией, базы — в томе `clamav-db`, порт 3310 только внутри сети compose,
  проверка здоровья — ответ clamd на `PING` (скрипт `clamdcheck.sh` из образа;
  имя скрипта проверяется при первом запуске стенда). Первый запуск качает базы
  (около 300 МБ) и загружает их 1–2 минуты. Worker от её здоровья не зависит:
  проверки, поставленные раньше, ждут и повторяются;
- worker: `rq worker -c config.rq_settings --with-scheduler files mail` (очередь
  `files` первой: проверка фото не ждёт писем), том `protected` смонтирован, как
  у web;
- переменные `CLAMAV_HOST` (по умолчанию `clamav`), `CLAMAV_PORT` (3310),
  `CLAMAV_TIMEOUT` (30 с) — значения по умолчанию в `docker-compose.yml`, в
  `deploy/.env.example` они перечислены закомментированными;
- зеркало баз ClamAV задаётся файлом `deploy/clamav/freshclam.conf` (смонтирован
  в контейнер). По умолчанию там `database.clamav.net`; если сеть общества к
  нему не пускает, администратор вписывает `PrivateMirror` (раздел «Риски»);
- ночные задания `rq cron` (очередь `mail`, как в срезе 001): в 03:40 стираются
  неподтверждённые предпросмотры загрузок старше суток, в 03:50 — файлы
  карантина старше 30 дней. Раз в час задание повторно ставит в очередь проверки
  фото, которые ждут дольше часа и задания в очереди не имеют.

| `CalendarUpload` (предпросмотр календаря) | `year`, `file_name`, `days` (JSONB: дата и вид), `totals`, `created_by` (на `core.User`, `PROTECT`), `created_at`, `state` (`preview` / `applied`). Неподтверждённый стирается через сутки | 145 |
| `StaffImport` (загрузка сотрудников) | `created_by` (на `core.User`, `PROTECT`), `created_at`, `file_name`, `file_format` (`csv` / `xlsx`), `state` (`preview` / `done`), `send_invites`, `rows` (JSONB), `summary` (создано, пропущено, с ошибками, создано отделов). До подтверждения в `rows` лежат разобранные строки с результатом проверки. После выполнения от строки остаются номер, почта, итог и текст причины. Неподтверждённый предпросмотр стирается через сутки | 136–142 |

Миграции `org`:
- схема;
- данные: корневой отдел «ИТ-отдел» без участников (FR-103, FR-112); права
  `org.manage` и `calendar.manage` у «Администратора портала»; строка
  `WorkCalendar` по умолчанию.

Роли базы — как в срезе 001: новые таблицы получают права `crm_app` через `ALTER
DEFAULT PRIVILEGES`. Особых прав срез не вводит, журнал по-прежнему только
дописывается.

## Ключевые механизмы

**Дерево (FR-101…109).** Все изменения структуры идут в транзакции и берут
`select_for_update` строки корня. Тот же замок берут добавление и удаление
членств и увольнение, чтобы удаление узла не разминулось с добавлением в него
человека. Так два одновременных переноса не создадут цикла. Узлов не больше 200
(NFR-101), поэтому дерево страницы читается одним запросом и собирается в
памяти.
- **Создание.** Проверяются правила видов и уникальность `name_key` среди узлов
  того же родителя (FR-102, FR-105). `path` строится от пути родителя.
- **Перенос** — смена `parent` (FR-106). Сервис до записи проверяет те же
  правила видов, что при создании (FR-102), и свободное название у нового
  родителя (FR-105) и отказывает понятным текстом. Новый родитель не может быть
  самим узлом и не может лежать внутри него: его `path` не начинается с `path`
  узла. Пути и глубины всего поддерева меняются одним `UPDATE` через ORM
  (`Concat` и `Substr` от старого пути).
- **Удаление** — только пустого узла: без участников и без вложенных (FR-107).
  Роли узла снимаются вместе с ним.
- **Корень.** Его можно переименовать; удалить и перенести нельзя ни из
  интерфейса, ни прямым запросом (FR-103).
- **Страница «Структура»** (FR-108). Слева дерево: вложенные списки, узлы
  раскрываются элементом `<details>`. Узлы пользователя выделены. Справа
  карточка узла: руководители, заместители, участники с должностью и фото, поиск
  внутри узла (запрос HTMX, без учёта регистра и «е/ё»). Карточка узла
  открывается фрагментом HTMX и имеет свой адрес; тот же адрес, открытый
  напрямую, показывает страницу целиком. При ширине меньше 768 px дерево и
  карточка идут друг под другом. Пустые состояния — по UX-13 (FR-109).

**Членство (FR-110…114).**
- **«Добавить сотрудников» в отдел.** Режим «перевести»: в одной транзакции
  удаляются членства человека во всех других отделах, а команды остаются. Режим
  «добавить как совместителя»: прежние членства не трогаются. В команду человек
  добавляется без выбора режима. Повторное добавление в тот же узел (в любом
  режиме, а также перевод из меню «…» в узел, где человек уже состоит; тогда
  прежние членства не трогаются) не создаёт второго членства: портал сообщает,
  что человек уже участник (сценарий 2.7).
- **Меню «…» участника.** «Перевести в другой отдел» снимает только это членство
  и добавляет новое (сценарий 2.4). Целью переноса может быть только узел того
  же вида: из отдела — в отдел, из команды — в команду; в карточке команды
  пункты называются «Перевести в другую команду» и «Удалить из команды» (решение
  плана). Есть ещё «Удалить из отдела» и «Уволить».
- **Отметки.** Отметка руководителя или заместителя — поле членства, поэтому она
  уходит вместе с ним при переводе, удалении и увольнении (FR-114).
  Руководителем и заместителем можно отметить только участника узла. Если
  человек уже отмечен в этом узле другой отметкой, сервис отказывает с
  пояснением, а не заменяет её молча (сценарий 3.10); сменить отметку можно,
  сначала сняв прежнюю.
- **Выбор людей.** Подсказки идут из сервиса ядра `accounts.pickable(query)`.
  Уволенных он не отдаёт (FR-127). Этот же сервис возьмут ответственные в
  следующих срезах.

**Руководитель в карточке (FR-115…117).** Для каждого членства сотрудника
правило FR-115 такое. Если сотрудник не руководитель этого узла и у узла есть
руководители — это они. Если он сам руководитель узла (даже один из нескольких)
или у узла руководителей нет — берутся руководители ближайшего вышестоящего узла
(сценарий 3.3). Выше первого уровня из набора исключается сам сотрудник, а
пустой набор ведёт ещё выше; если руководителей нет до самого корня — «не
назначен». Исключение себя выше первого уровня — решение плана: иначе
руководитель и отдела, и корня видел бы руководителем себя. Совместителю
руководители показываются по узлам: «Сеть: …; Поддержка: …». «Подчинённые» у
руководителя узла — участники этого узла и всех вложенных, без него самого и без
повторов. Дерево с отметками читается двумя запросами и собирается в памяти.
Отметка руководителя не даёт прав и не выдаёт роль «Руководитель»: в коде связи
между ними нет, это проверяет тест (FR-117).

**Права и роли узлов (FR-118…123).**
- **Действующие права.** `permissions_of` ядра объединяет права личных ролей и
  ролей из `role_sources`. `org` отдаёт роли, назначенные узлам, где человек
  состоит, и всем их вышестоящим узлам: роль, назначенная отделу, действует и на
  вложенные команды. Всё это — один запрос по путям членств.
- **Кэш прав.** Ключ кэша прежний: `perms:<id>`. Ключи сбрасываются через
  `transaction.on_commit` (и в сигналах ядра среза 001 тоже), чтобы параллельный
  запрос не записал в кэш на 12 часов права из ещё не зафиксированной
  транзакции. Добавление, перевод, удаление и увольнение сбрасывают ключ этого
  человека. Перенос и удаление узла, назначение и снятие роли узлу сбрасывают
  ключи всех участников поддерева. Смена прав роли в ядре теперь сбрасывает
  ключи всех записей: держатели роли через узлы ядру не видны, а записей не
  больше ~100. Право действует или пропадает со следующего запроса (сценарий
  9.2).
- **Ограничения.** Роль «Администратор портала» узлу не назначается (FR-121).
  Удаление роли, назначенной хотя бы одному узлу, `delete_role` отклоняет через
  `role_usage`; второй рубеж — `PROTECT` в базе (FR-120). Назначает роль узлу
  обладатель `roles.manage`.
- **Карточка.** Роли показываются группами: «лично» и «от подразделения
  <название узла, которому роль назначена>» (FR-122).
- **Проверка прав.** Каждое представление объявляет право (`require_permission`
  или проверку «одно из»). Пункты меню берутся из того же списка (FR-123).

**Увольнение и возврат (FR-124…129).**
- **Увольнение — `org.services.people.dismiss(user, actor, ip)`.** В одной
  транзакции:
  1. Сервис ядра `accounts.dismiss` проверяет запреты: уволить себя нельзя,
     последнего администратора тоже (`guard_last_admin`, FR-126).
     `guard_last_admin` теперь берёт `select_for_update` строк действующих
     администраторов, поэтому два администратора, одновременно увольняющие или
     блокирующие друг друга, не оставят портал без администратора; это закрывает
     ту же гонку и у блокировки среза 001. После проверок сервис ставит
     состояние «уволен», дату и того, кто уволил, гасит ссылки активации и
     восстановления, закрывает все сессии и снимает личные роли (FR-125).
  2. `org` удаляет все членства человека вместе с отметками.
  3. Журнал получает `user.dismissed` и по событию `membership.removed` на
     каждый узел с причиной «увольнение».

  Письма уволенному нет. Поля `blocked_from` и `blocked_reason` при увольнении
  очищаются. Уволить можно запись в состоянии «приглашён», «активна» и
  «заблокирована».
- **Вход уволенного.** Условия `state == BLOCKED` при проверке пароля и кода в
  `login.py` расширяются до «заблокирована или уволена»: иначе уволенный с
  прежним паролем пройдёт первый шаг. Свойство `User.is_active` ложно и у
  уволенной записи. Обмен ссылок и запрос восстановления уже пускают только
  приглашённую или активную запись. Везде, где срез 001 не пускает
  заблокированную запись, так же не пускается уволенная: вход с тем же общим
  отказом (FR-034), обмен ссылок, запрос восстановления (письмо не уходит),
  действующая сессия (`is_active`).
- **Возврат — `org.services.people.rehire`.** Вызывает `accounts.rehire`:
  - запись становится «приглашён»;
  - пароль делается непригодным, ключ TOTP, резервные коды и запомненные
    устройства удаляются;
  - роль — только «Сотрудник ИТ» (`roles.staff_role()`: начальная роль с этим
    неизменным названием);
  - уходит приглашение на 72 часа (`links.send_invitation`).

  История паролей остаётся, она по-прежнему не даёт повторить старый пароль.
  Журнал получает `user.rehired` и `invitation.sent` (FR-128).
- **Карточка уволенного — только для чтения** (FR-127, решение плана). Над
  уволенной записью ядро отказывает в правке профиля, блокировке, смене ролей и
  сбросе второго фактора: `accounts.update_profile`, `block`,
  `roles.set_user_roles`, `reset_second_factor` проверяют состояние. `org`
  отказывает в членстве и отметках. Остаются «Вернуть на работу» и удаление фото
  (ПДн).
- **Почта уволенного.** Она остаётся занятой (FR-129): проверка уникальности
  почты в ядре не смотрит на состояние записи.
- **Уволенные в интерфейсе.** В журнале и в истории имя уволенного выводится с
  пометкой «(уволен)» (FR-127). Подразделения его карточки пусты, роли сняты,
  остальные поля на месте.
- **Блокировка структуру не меняет** (FR-124): `block` ядра членства не трогает.

**Список «Сотрудники» и поиск (FR-130, 131).** Адрес прежний, `/staff/`.
- **Поиск.** Строка ищет вхождение в ФИО, должность, почту, телефон, внутренний
  телефон и место работы. Каждое поле сравнивается как `translate(lower(поле),
  'ё', 'е')` с так же приведённой строкой; через `staff_directory` добавляется
  условие `Exists` по названиям узлов человека.
- **Фильтр «Подразделение».** Выбор узла; берутся члены узла и всех вложенных
  (`path` начинается с пути узла).
- **Пресеты.** «В компании» — все, кроме уволенных; это пресет по умолчанию, он
  сохраняет поведение среза 001, где уволенных не было. Дальше «Уволены», «Без
  подразделения» (не уволенные без членств), «Все». У обладателя
    `accounts.manage` есть ещё «Приглашены», «Активные», «Заблокированные» и
  фильтр роли из среза 001. Пресет «Все» — параметр `state=all`: пустой `state`
  теперь значит «В компании». Отметку «уволен» коллеги видят: FR-127 требует
  пресет «Уволены» и пометку «уволен» в журнале и истории. Остальные состояния —
  «приглашён», «активна», «заблокирована» — служебные (FR-119), поэтому пресета
  «Приглашены» у коллеги нет, а в его карточке уволенного стоит только отметка
  «уволен» (решение плана).
- **Колонки.** Фото (96 px или заглушка с инициалами), ФИО, должность,
  подразделение, внутренний телефон, почта; у `accounts.manage` ещё состояние.
  На узкой ширине строка списка становится блоком, как история входов в срезе
  001 (F5).

**Карточка сотрудника, фото и новые поля (FR-132…135).**
- **Вкладки.** У карточки две вкладки (UX-09):
  - «Профиль» — фото, ФИО, должность, почта, телефоны, место работы, день и
    месяц рождения, подразделения, руководитель, подчинённые; у
    `accounts.manage` — формы правки, роли по источникам, «Уволить» и «Вернуть
    на работу»;
  - «Безопасность» — состояние, приглашение, блокировка, вход и второй фактор,
    устройства и история входов, как в срезе 001.

  Свою карточку (`/me/`) сотрудник видит с обеими вкладками. В чужой карточке
  вкладка «Безопасность» показывается, только если у смотрящего есть
  `accounts.manage` или `accounts.view_logins`. Иначе вкладки нет, а прямые
  адреса её данных отвечают 403 (FR-119). Это решение плана: оно сужает сценарий
  10.9 («вкладок две») до смотрящих с этими правами и подтверждается подписью
  под планом. Содержимое вкладки зависит от прав: состояние, приглашение и
  блокировка — у `accounts.manage`, устройства и входы — у
  `accounts.view_logins`. Пустое поле — «не заполнено».
- **Свои поля.** Внутренний телефон и место работы сотрудник правит в `/me/`,
  администратор с `accounts.manage` — в карточке (FR-133). Дату рождения вводит,
  меняет и стирает только сам сотрудник (FR-134). В форме администратора поля
  нет, а сервис правки чужой записи отклоняет `birth_date` и в прямом запросе.
  Чужую дату показывает фильтр «день и месяц», полную — только `/me/`. В журнале
  — `{"birth_date": "изменено"}` или `"очищено"`, без значений (FR-151).
- **Путь фото** (TGT-ARCH «Файлы», ADR-0007):
  1. Загрузка до 5 МБ. Pillow открывает файл и проверяет: формат по содержимому
     PNG или JPEG, не больше 40 млн точек; иначе отказ (как с логотипом в срезе
     001). Файл ложится в `incoming/`, запись `StoredFile(pending)` становится
     `photo_pending`, задание `core.tasks.scan_file` уходит в очередь `files`
     после фиксации транзакции.
  2. Задание отдаёт файл clamd. Ответ «чисто» — Pillow перекодирует файл в JPEG
     двух размеров: вписывается в квадрат 512 и 96 px с сохранением пропорций,
     без EXIF, с учётом поворота; прозрачный фон PNG заливается белым. Круглую
     рамку в списке и дереве даёт CSS (`object-fit: cover`), без обрезки файла
     (решение плана). Исходник удаляется. `photo` переключается на новый файл,
     прежнее фото удаляется с диска.
  3. Ответ «найдено» — файл переносится в `quarantine/`, статус `quarantine`,
     имя сигнатуры записывается в журнал. `photo` не меняется: остаётся прежнее
     чистое фото или заглушка. Сотрудник видит «фото не прошло проверку» и может
     загрузить другое.
  4. clamd недоступен — задание повторяется: `Retry(max=24, interval=[60, 300,
     900] + [3600] * 21)`, около суток. Дальше фото подбирает часовое задание.
     Пока проверки нет, видна заглушка или прежнее фото (NFR-105).

    Новая загрузка заменяет `photo_pending`: прежний ожидающий файл удаляется,
  а файл в карантине остаётся до ночной очистки (30 дней). Задание проверки
  перед записью итога берёт `StoredFile` и запись владельца под
  `select_for_update` и убеждается, что файл всё ещё `photo_pending` владельца в
  статусе `pending`; иначе завершается без изменений. При ответе «чисто»
  `photo_pending` обнуляется.
- **Выдача фото.** `/staff/<id>/photo/<номер файла>/<размер>/` отдаётся только
  `clean` и только вошедшему с `staff.view`, `accounts.manage` или самому
  сотруднику. web отвечает `X-Accel-Redirect` на внутреннее расположение
  `/protected/`, nginx отдаёт файл с `Content-Type: image/jpeg`,
  `X-Content-Type-Options: nosniff`, `Cache-Control: private, max-age=86400`.
  Представление выдачи сверяет, что номер файла — это действующее `photo` этого
  сотрудника в статусе `clean`; иначе 404. Номер файла в адресе меняется вместе
  с фото, поэтому кэш не мешает: страницы запрашивают новый адрес, а удалённое
  фото больше не запрашивают. Копия в кэше браузера того, кто имел право её
  видеть, живёт до суток — это допустимо (решение плана).
- **Удаление фото.** Сотрудник удаляет своё фото сам, администратор с
  `accounts.manage` — чужое (FR-132). Удаляются `photo` и `photo_pending` с их
  файлами, кроме файла в карантине. Событие — в журнал.

**Загрузка сотрудников из таблицы (FR-136…142).** Нужны оба права:
`accounts.manage` и `org.manage`.
- **Приём файла.** Не больше 1 МБ. Формат определяется по содержимому, а не по
  имени:
  - XLSX — архив ZIP с `[Content_Types].xml` и `xl/workbook.xml`. До разбора
    проверяется оглавление архива: не больше 100 частей и не больше 20 МБ в
    распакованном виде. Затем openpyxl (`read_only=True`, `data_only=True`;
    формулы не вычисляются) читает первый лист; числа и даты из ячеек приводятся
    к тексту (целое число — без «.0» и экспоненты). С установленным defusedxml
    он отвергает XML-бомбы;
  - CSV — строгое UTF-8 (с BOM или без), без нулевых байтов. Разделитель «;» или
    «,» определяется по строке заголовков.

  Строк не больше 1000 без заголовка; чтение останавливается на 1001-й, и портал
  отказывает. Файл разбирается в памяти и никуда не сохраняется (FR-141). Тип и
  размер проверяются до разбора, значения из файла попадают в запросы только
  параметрами ORM (NFR-108). Тот же порядок — у файла календаря и у фото.
- **Заголовки.** Сравниваются без учёта регистра, пробелов и «е/ё». Обязательные
  колонки — Почта, Фамилия, Имя, Должность: ФИО и должность обязательны для
  записи по SPEC-001 FR-001. Необязательные — Отчество, Телефон, Внутренний
  телефон, Место работы, Подразделение, Руководитель. Без обязательной колонки
  отказ получает весь файл. Лишние колонки (например, «Роль» или «Дата
  рождения») не читаются; предпросмотр называет их «не загружаются» (FR-138).
- **Проверка строки.**
  - Почта: формат и уникальность без учёта регистра. Сверяется со всеми записями
    портала, включая уволенные; уволенный получает подсказку «уволен: верните
    его из карточки». Повтор внутри файла — первая строка «будет создан»,
    остальные «пропущен» (FR-139).
  - Фамилия, Имя и Должность не пусты; длины в пределах полей.
  - «Руководитель» — «да», «нет» или пусто; «да» без подразделения — ошибка.
  - Путь подразделения: части через « / ». Первая часть совпадает с названием
    корня, сравнение по `name_key`. Если часть пути — существующая команда,
    строка получает ошибку (FR-138). Недостающие части станут отделами, и
    предпросмотр перечисляет их один раз (FR-137, FR-139). Отделы берутся только
    из строк «будет создан»: строки «пропущен» и с ошибкой отделов не создают и
    в список не попадают.
- **Предпросмотр.** Сохраняется в `StaffImport`; страница показывает итог по
  каждой строке. Строится синхронно в запросе: адреса проверяются одним
  запросом, дерево (≤ 200 узлов) лежит в памяти. Цель — 1000 строк за 10 с
  (NFR-103); ожидание — меньше 2 с.
- **Подтверждение.** Флажок «Отправить приглашения сразу» (FR-140). Выполнение
  идёт в запросе, в одной транзакции:
  1. Запись `StaffImport` берётся под `select_for_update`. Если она уже `done`
     (двойной щелчок, вторая вкладка), показывается прежний итог и ничего не
     выполняется. Затем строки проверяются заново: за время предпросмотра адреса
     могли занять.
  2. Каждая годная строка выполняется в своей точке сохранения (`atomic` внутри
     `atomic`): создаются недостающие отделы, запись через
     `accounts.create_user` с ролью «Сотрудник ИТ» (`full_name` — «Фамилия Имя
     Отчество»; сервис получает необязательные `internal_phone` и `workplace`),
     членство и отметка руководителя. Неожиданный отказ базы откатывает только
     эту строку, и она получает ошибку. Дерево в памяти пополняется отделами
     строки только после того, как её точка сохранения закрылась без ошибки; при
     откате дерево перечитывается из базы.
  3. Письма уходят после фиксации транзакции.

  Если выполнение прервётся, не создастся ничего, а повторная загрузка пропустит
  уже существующие адреса. Итог — «создано N, пропущено M, с ошибками K»
  (FR-139).
- **Журнал** (FR-142). Каждая запись, отдел и членство пишут обычные события
  (`user.created`, `unit.created`, `membership.added`). В конце —
  `staff_import.completed`: кто, имя файла, итоги; содержимого файла в журнале
  нет (FR-151).
- **Образец** — `/structure/import/sample.csv` и `…/sample.xlsx`: заголовки и
  две вымышленные строки.

**Рабочий календарь (FR-143…149).**
- **Формат файла** — CSV открытых данных Минтруда. Первая строка — заголовки:
  «Год/Месяц», двенадцать месяцев, «Всего рабочих дней», «Всего праздничных и
  выходных дней», «Количество рабочих часов при 40-часовой рабочей неделе» и ещё
  два столбца часов. Дальше по строке на год. Файл — UTF-8, разделитель «,»,
  ячейки месяцев в кавычках. Перевод идёт по обычной неделе пн–пт и от настройки
  рабочих дней не зависит. В ячейке месяца — нерабочие дни через запятую; «*»
  после числа — сокращённый рабочий день, «+» — перенесённый выходной. Год
  выбирает администратор, из файла берётся строка этого года. Нет строки — отказ
  «в файле нет 2027 года» (сценарий 11.3).
- **Перевод в особые дни.** Число без пометки, выпавшее на будний день, —
  праздник. Число с «+» — перенесённый выходной, с «*» — сокращённый рабочий
  день. Суббота или воскресенье, которых нет в списке месяца, — перенесённый
  рабочий день. Праздник, выпавший на субботу или воскресенье, в файле не
  отличим от обычного выходного, поэтому в календаре он показан выходным. При
  обычной неделе пн–пт для рабочего времени это ничего не меняет. Если
  администратор сделал рабочей субботу или воскресенье, такой праздник считается
  рабочим днём, пока его не поправят вручную видом «праздник»; страница загрузки
  об этом предупреждает.
- **Сверка.** Разбор пересчитывает рабочие дни, нерабочие дни и часы при
  40-часовой неделе (8 часов в день, на час меньше в сокращённый) и сравнивает
  их с итоговыми колонками строки. Расхождение — отказ: файл не того формата или
  повреждён.
- **Предпросмотр** (`CalendarUpload`). Показывает число праздничных дней в
  будни, перенесённых выходных, перенесённых рабочих и сокращённых, рабочих дней
  в году. Если у года уже есть особые дни, предупреждает, сколько из них ручных
  правок и что они будут заменены (сценарий 11.4).
- **Применение.** Особые дни этого года удаляются и вставляются заново с
  происхождением «файл». `CalendarYear` создаётся или обновляется. Дни других
  лет не трогаются. Событие `calendar.year_loaded` с прежними и новыми итогами.
- **Правка дня.** Разрешена только в загруженном году: иначе по FR-146 действуют
  одни рабочие дни недели. Виды: «обычный день» (особая отметка снимается),
  праздник, перенесённый выходной, перенесённый рабочий, сокращённый. Событие
  `calendar.day_changed` с видом «было» и «стало».
- **Неделя и часы** (FR-143). Нужен хотя бы один рабочий день недели, конец дня
  позже начала не меньше чем на 2 часа: иначе сокращённый день был бы пустым
  (решение плана). Часовой пояс — `Europe/Moscow` из настроек Django, отдельной
  настройки нет; время на страницах — по Москве, интерфейс по-русски (NFR-107).
- **Вид дня — одна функция `day_kind(date)`.** Её используют календарь, поле
  даты и проверка рабочего времени:
  - особый день берётся из `SpecialDay`;
  - иначе рабочий или выходной — по `work_weekdays`;
  - для незагруженного года — только по `work_weekdays`.

  Отметки месяца кэшируются в Valkey по ключу с номером версии календаря. Любое
  изменение календаря увеличивает номер.
- **Для других срезов** (FR-149) — `org.services.calendar`:
  - `is_working_time(moment)`: время приводится к `Europe/Moscow`; рабочий день
    и время между началом и концом дня, у сокращённого конец на час раньше;
  - `next_working_start(moment)`: ищет вперёд не дальше 400 дней, иначе `None`.

  Сроков в рабочих днях нет.
- **Напоминание** (FR-146). Обладатель `calendar.manage` видит его на главной и
  на странице календаря: весь год, если текущий год не загружен, и с 1 декабря,
  пока не загружен следующий.
- **Страница «Календарь»** (FR-147). Двенадцать месяцев сеткой, неделя с
  понедельника. Выходные, праздники, переносы и сокращённые дни отмечены цветом
  и буквой в ячейке, есть подпись для чтения с экрана и легенда. Выбор года. У
  `calendar.manage` ещё форма недели и часов, загрузка файла и правка дня по
  щелчку. На странице загрузки описан формат файла и названы места, где его
  взять.

**Поле выбора даты (FR-148).** Шаблон `widgets/date_field.html` и виджет формы
ядра `PortalDateInput`:
- текстовое поле с маской ДД.ММ.ГГГГ (сервер принимает и ГГГГ-ММ-ДД, чтобы не
  сломать прежние адреса фильтров журнала) и кнопка «Выбрать дату»;
- по кнопке HTMX загружает `/ui/date-picker/?month=ГГГГ-ММ`: сетку месяца с
  понедельника, списки месяца и года, переходы на месяц назад и вперёд. Сетку
  видят все вошедшие, право `staff.view` не нужно;
- день в сетке — кнопка с числом, а для выходного, праздника, сокращённого и
  перенесённого рабочего дня — с классом и скрытой подписью. Отметки берутся из
  `day_marks`; без `org` выходными считаются суббота и воскресенье;
- выбрать можно любой день, в том числе праздник. Выбранный день подсвечивает
  скрипт по значению поля: сама дата (например, дата рождения) в адрес запроса
  не попадает;
- скрипт `static/js/datefield.js` (внешний файл, без `eval` и встроенных
  обработчиков) открывает и закрывает сетку (обработчики навешиваются
  делегированием на `document`, чтобы работать с сеткой, пришедшей по HTMX),
  переносит дату в поле, двигает фокус стрелками, PageUp и PageDown, Home и End,
  выбирает по Enter и закрывает по Esc;
- ввод с клавиатуры в поле работает всегда.

Виджет заменяет все поля даты портала: дату рождения и поля «с» и «по» в фильтре
журнала (сейчас там `<input type="date">` в `templates/audit/list.html`; разбор
`audit_search` начинает принимать и ДД.ММ.ГГГГ). Правка дня календаря поля даты
не имеет: день выбирают щелчком в сетке года. Тест не пускает в шаблоны
`type="date"` и требует, чтобы у каждого `forms.DateField` портала был виджет
`PortalDateInput`.

## Интеграции

**ClamAV.** Адаптер `apps/integrations/clamav/` устроен так:
- `client.py` — соединение TCP с `CLAMAV_HOST:CLAMAV_PORT` и тайм-аутом
  `CLAMAV_TIMEOUT`, команды `zPING` и `zINSTREAM`. Файл уходит частями по 64 КБ
  с длиной в 4 байта (порядок big-endian), в конце — нулевая часть;
- `services.scan(path)` возвращает «чисто» или «найдено: <сигнатура>», а при
  сбое связи, тайм-ауте и ответе `… ERROR` поднимает `ScanUnavailable`. Задание
  `core.tasks.scan_file` на это исключение уходит на повтор.

Предел потока clamd (`StreamMaxLength`: по справке clamd.conf по умолчанию 100
МБ, в образце конфигурации 25 МБ) больше предела фото, менять его не нужно.
Задание и клиент не пишут в журнал ни содержимое файла, ни путь на диске. Тесты
подменяют `services.scan`; отдельный тест на стенде проверяет настоящий clamd
тестовой строкой EICAR. Её тест собирает из частей при запуске, чтобы антивирус
на машине разработки не трогал репозиторий.

**Почта.** Новых писем нет. Приглашения из загрузки (FR-140) и при возврате
(FR-128) идут механизмом SPEC-001 (`links.send_invitation`, очередь `mail`).
Уволенному писем нет (FR-125).

**Персональные данные.** Наружу срез ничего не отправляет: ClamAV работает на
той же ВМ. Фото проходит перекодирование без метаданных. Строки неподтверждённых
загрузок хранятся не дольше суток, а после выполнения от строки остаются номер,
почта и итог.

## Проверка

- **Серверные тесты** (pytest + pytest-django на PostgreSQL). Ключевые случаи:
  - дерево: правила видов; уникальность названия без учёта регистра и «е/ё»;
    цикл при переносе; пути поддерева после переноса; корень не удаляется и не
    переносится; удаление только пустого узла;

**Критерии успеха спеки и чем они проверяются.**

|---|---|

| файл на 100 сотрудников до итога за 5 минут; предпросмотр 1000 строк за 10 с | e2e на 100 строк с замером; серверный тест NFR-103 |
| повторная загрузка создаёт 0 записей, отделов и членств | серверный тест и e2e (сценарий 5.8) |

| после увольнения вход и запрос из любой прежней сессии отклоняются в 100 % случаев | серверный тест на каждый вид запроса и e2e с двумя сессиями (сценарий 7.1) |
| 100 % изменений в журнале, даты рождения нет | серверный тест перебирает действия среза и ищет значение даты во всех событиях |
