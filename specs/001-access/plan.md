# План среза 001: вход и доступ

Как реализовать SPEC-001: модели, маршруты, письма, защита, развёртывание и
проверка. Два выбора владельца от 2026-10-01 при подготовке плана:
- **защита от перебора — свой небольшой сервис** на счётчиках Valkey, а не
  django-axes. Довод Opus (не владельца): у django-axes нет счёта «разных
  записей с одного адреса», а правило ADR-0006 «адрес — при переборе разных
  записей» без него не выполнить;
- **второй фактор — django-otp со своими устройствами:** ключ TOTP хранится
  зашифрованным ключом из окружения, резервные коды — только хешем
  (NFR-011 спеки).

Остальные технические решения здесь — решения плана (Opus; поправки
проверяющего Sonnet помечены «при проверке»), они повторяют Газоwiki, где это
возможно, и утверждаются подписью под этим планом. Владелец их не выбирал.

Решения плана:
- **Встроенная админка Django выключена:** портал смотрит в интернет, а
  администрирование — свой раздел с проверкой прав и журналом.
- **Сессии в базе**, а не в куке, чтобы закрывать сессии по одной
  («Выйти со всех устройств», блокировка записи, сброс второго фактора).
- **django-rq 4.x встраивает свою панель в админку Django**, а админка
  выключена: состояние очередей смотрим командами `rq info` и журналом
  доставки писем (при проверке).
- **Статика лежит в репозитории** (`static/vendor/`), без CDN: этого требует CSP `'self'`, и ВМ
  может работать без доступа наружу.
- **HTMX без `hx-on` и без eval** (`htmx.config.allowEval = false`),
  Alpine — CSP-сборка (`@alpinejs/csp`, у неё нет `new Function`; в
  выражениях нет стрелок, шаблонных строк и глобальных объектов, логика — в
  `Alpine.data()`): CSP остаётся без `unsafe-inline` и `unsafe-eval`
  (NFR-007 спеки). Ещё HTMX по умолчанию вставляет в страницу тег `<style>` для
  индикаторов — при `style-src 'self'` его заблокирует, поэтому
  `htmx.config.includeIndicatorStyles = false` (настройка в
  `<meta name="htmx-config">`), нужные правила — в своей теме (при проверке).
- **За прокси администратора.** TLS кончается на прокси, поэтому: nginx берёт
  настоящий адрес клиента из `X-Forwarded-For` только от адреса прокси
  (`set_real_ip_from`, переменная `TRUSTED_PROXIES`), иначе блокировка по
  адресу и история входов видели бы один адрес прокси, а подделанный заголовок
  позволял бы обходить блокировку; Django получает `SECURE_PROXY_SSL_HEADER`,
  `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`, `SameSite=Lax`, HSTS,
  `X-Content-Type-Options`, `Referrer-Policy: same-origin` (для страниц ссылок —
  `no-referrer`), `TIME_ZONE = Europe/Moscow`, `LANGUAGE_CODE = ru` (NFR-007,
  NFR-010; при проверке). Страницы с вводом секретов и защищённые страницы
  отдаются с `Cache-Control: no-store`, чтобы «Назад» после выхода не показывал
  их (сценарий 10, п. 5).

### Запуск

`docker compose --profile dev up` поднимает всё, включая Mailpit. Портал
открывается на `https://127.0.0.1:8031/`, ящик Mailpit — на `:8025`. На
стенде nginx сам держит TLS с самоподписанным сертификатом (его выпускает
скрипт `deploy/dev-cert.sh`), чтобы куки `Secure`, HSTS и перенаправление на
HTTPS проверялись так же, как за прокси администратора, а не подменой
заголовков (версия 2, по вопросу TASKS-001). Playwright работает с
`ignore_https_errors`. На проде TLS держит прокси администратора, а nginx
портала слушает HTTP внутри. Порт
5000 занят сервером владельца и не используется. Первый администратор
создаётся командой `python manage.py create_first_admin --email …`: она
отказывает, если в базе уже есть учётные записи, пишет в журнал создание
записи (действующее лицо — «система») и печатает ссылку активации
(сценарий 1, письмо не нужно). Ночные задания (очистка истории входов старше
`login_history_days`, очистка просроченных ссылок и сессий) регистрируются в
`config/cron.py` для `rq cron`.

**Роли базы данных** (решение плана): `crm_owner` выполняет миграции,
`crm_app` работает в портале; web и worker подключаются под `crm_app`
(`DATABASE_URL`), миграции идут под `crm_owner` (`DATABASE_MIGRATE_URL`) при
запуске контейнера. Остальным таблицам права получает `crm_app` через
`ALTER DEFAULT PRIVILEGES FOR ROLE crm_owner … GRANT SELECT, INSERT, UPDATE,
DELETE`, а последовательностям — `USAGE`; поэтому миграция журнала выполняет
`REVOKE ALL ON core_auditevent FROM crm_app`, затем `GRANT SELECT, INSERT` и
`GRANT USAGE` на его последовательность (иначе `INSERT` не пройдёт, а права
по умолчанию дали бы `UPDATE` и `DELETE`). Владелец таблицы обходит эти права,
поэтому `crm_app` не владеет ничем. Тест проверяет, что под `crm_app`
изменить или удалить запись журнала нельзя.

## Ключевые механизмы

**Ссылки активации и восстановления (FR-008…013, 031…033).** Код — случайные
256 бит, в базе — SHA-256 (поиск) и Fernet (показ администратору и отправка).
В письме
ссылка вида `https://<портал>/activate/#<код>`. Сервер получает запрос
без кода. Свой скрипт страницы (внешний файл, CSP) читает фрагмент, стирает
его из адресной строки (`history.replaceState`) и отправляет код
POST-запросом на `/activate/exchange/`. Сервер сверяет SHA-256 кода с
`OneTimeLink`, проверяет срок и состояние и кладёт в сессию отметку «идёт
активация пользователя N». Дальше шаги мастера: профиль → пароль → TOTP →
резервные коды. Ссылка гаснет после последнего шага. Неверная, истёкшая и
использованная ссылки дают одно и то же сообщение. Запросы восстановления
считаются в Valkey: не больше 3 писем в час на адрес и 10 в час с одного IP,
сверх предела ответ прежний, письмо не уходит (сценарий 18, п. 9; пределы —
при проверке, подтверждаются подписью). Администратор увидит ссылку активации
в карточке (расшифровка пишет событие в журнал).

**Вход (FR-021, 025, 034…041).**
1. Почта и пароль.
2. Проверка блокировки записи и адреса — до проверки пароля.
   Для несуществующей записи выполняется холостая проверка хеша, чтобы по
   времени ответа нельзя было отличить её от существующей.
3. Пароль неверен — одно общее сообщение для всех причин (FR-034), неудача
   уходит в счётчики, попытка — в историю.
4. Пароль верен — если у записи нет подтверждённого второго фактора (не
   дошла до конца активации или сброшен), выдаётся ограниченная сессия:
   middleware пускает её только на страницы подключения фактора и показа
   резервных кодов (FR-021, NFR-004, сценарии 3.6 и 7.2). Иначе — шаг
   второго фактора: код TOTP или резервный код. Неверный код — такая же
   неудача в счётчиках и истории, как неверный пароль (FR-025); так же
   считаются неверные коды при подключении фактора (сценарий 3.4) и неверный
   текущий пароль при его смене (сценарий 16.4).
5. Код верен — вход, `UserSession`, распознавание устройства по куке. Новое
   устройство (не первый вход после активации) — письмо. Счётчик неудач
   записи обнуляется.

**Сервис блокировки (ADR-0006).** Ключи Valkey с временем жизни:
- `fail:acct:<id>` — неудачи записи подряд (срок жизни — сутки от последней
  неудачи, при проверке; успешный вход удаляет ключ);
- `lock:acct:<id>` — запись заблокирована на `account_lock_minutes`;
- `fail:ip:<ip>` — неудачи с адреса в окне `ip_lock_window_minutes`;
- `accts:ip:<ip>` — множество хешей логинов, которые перебирали с адреса;
- `lock:ip:<ip>` — адрес заблокирован.

В `fail:ip` не считаются отказы по уже заблокированной записи (результат
`locked`): иначе повторы по одной заблокированной записи набирали бы порог.
Счётчики меняются атомарно (скрипт Lua или `MULTI`: `INCR`/`SADD` + `EXPIRE`).
Адрес блокируется, когда `fail:ip` ≥ `ip_lock_limit` **и** в `accts:ip` не
меньше `ip_lock_min_accounts` разных записей. Минимум разных записей
(3 по умолчанию) — решение плана: ADR-0006 и спека его не задают.
Попытки входа в несуществующие записи тоже считаются по их хешу. Блокировка
и её снятие пишутся в журнал. Снять блокировку раньше срока (FR-038) можно
действием «Снять блокировку входа» в карточке сотрудника и на странице
`/staff/locks/` (список заблокированных адресов и записей; право
`accounts.manage`): ключи `lock:*` и `fail:*` удаляются, событие — в журнал. Письмо о блокировке записи (FR-037) уходит
один раз на блокировку. Если Valkey потеряет данные, счётчики просто
обнулятся, а события уже записаны в журнале.

**Сессии и бездействие (FR-028…030).** Время бездействия запоминается в
сессии при её создании (значение `idle_timeout_minutes` на тот момент):
изменённая политика действует для новых сессий, как требует сценарий 10.2
спеки (решение Opus по находке проверки). Промежуточное ПО продлевает
сессию на это время при каждом запросе и закрывает её по бездействию. «Выйти со всех устройств», смена пароля, сброс второго
фактора и блокировка записи удаляют сессии по `UserSession`.

**Права (FR-014…020).** Декоратор и миксин `require_permission(code)`
стоят на каждом представлении. Меню строится из того же списка прав.
Объединение прав ролей кэшируется в Valkey по ключу `perms:<id>`; при
изменении ролей или их назначения ключи затронутых держателей удаляются, и
право действует со следующего запроса (сценарий 12.2); потеря Valkey ведёт
лишь к пересчёту из базы. Права начальных ролей (FR-020): у «Администратора
портала» все семь, у «Руководителя» и «Сотрудника ИТ» ни одного — их раздел
«Безопасность» и профиль требуют только входа. Свой второй фактор
администратор сбросить не может (FR-024), профиль сотрудник правит только в
части телефона и контактов (FR-006), удаления учётных записей нет (FR-005). Защита последнего администратора — в сервисе ролей (FR-019).

**Журнал (FR-044…047).** `core.services.audit.record(...)` вызывается из
сервисов, не из представлений; состав событий — FR-044 целиком, включая
неудачные попытки входа, запрос восстановления, выход со всех устройств и
доставку писем (смена статуса `MailMessage`). Внешний ключ `actor` — `PROTECT`
(пользователи не удаляются; `SET_NULL` был бы `UPDATE` таблицы журнала). Пароли, ключи и коды в «было/стало» не
попадают: у полей с такими данными стоит отметка «скрыть». Список журнала —
сетка UX-04 с пресетами «Сегодня», «Вход и доступ», «Права и роли», «Настройки» (как в
сценарии 13 спеки) и выгрузкой CSV; в ячейках, начинающихся с `=`, `+`, `-`, `@`,
перед значением ставится апостроф (защита от формул Excel).

**Оболочка и интерфейс (FR-050, 051; UX-01…04, 11, 12).**
- Левое меню показывает только разделы, доступные по правам; режим
  «только значки» запоминается в `localStorage`.
- Карточка сотрудника открывается слайдером (UX-03): HTMX подгружает
  фрагмент в боковую панель и меняет адрес. Тот же адрес открывается и
  обычной страницей.
- «Безопасность» в профиле собрана в одном слайдере (UX-12).

## Интеграции

**Исходящая почта (ADR-0005, FR-052…055).** `integrations.mail.services.send(template, to, context)`:
1. создаёт `MailMessage` со статусом `queued`;
2. ставит задание RQ в очередь `mail` после фиксации транзакции
   (`transaction.on_commit`; в django-rq 4.x режим `on_db_commit`), в задание
   уходит только номер письма: коды ссылок в Valkey не попадают;
3. задание рендерит шаблон (русский, с названием портала) и отправляет по
   SMTP. Повторы: `Retry(max=11, interval=[60, 300, 900, 3600] + [10800] * 7)`,
   то есть 1, 5, 15, 60 минут, затем семь раз по 3 часа — последняя попытка
   примерно через 22 часа 20 минут (TGT-NFR NFR-06, до 24 часов). Паузы
   работают только если рабочий процесс запущен с `--with-scheduler`. После
   последней неудачи обработчик `on_failure` ставит `failed` (тест проверяет,
   что обработчик не срабатывает после промежуточных неудач), каждая попытка пишет `MailAttempt`, и это
   видно в журнале доставки и в карточке сотрудника (FR-009).

Шесть писем: приглашение, восстановление пароля, блокировка записи, вход с
нового устройства, сброс второго фактора, смена пароля.

Параметры — `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`,
`SMTP_FROM`, `SMTP_SECURITY` (`starttls` / `ssl` / `none`), `PORTAL_URL`
(адрес для ссылок) — только в окружении. Для разработки и тестов — Mailpit.

**Окружение целиком** (версия 2, по вопросу TASKS-001). Все секреты и
параметры установки — переменные окружения, в репозитории только
`deploy/.env.example` с заглушками:
- `DJANGO_SECRET_KEY`;
- `FIELD_ENCRYPTION_KEYS` — ключи Fernet через запятую (первый шифрует,
  остальные расшифровывают — смена ключа через `MultiFernet`); ими
  шифруются ключ TOTP и код ссылки. Новый ключ ставится первым, затем
  команда `python manage.py rotate_field_keys` перешифровывает
  `EncryptedTOTPDevice.key_encrypted` и `OneTimeLink.code_encrypted`
  (`MultiFernet.rotate()`), и только после неё старый ключ убирается из
  списка (по находке проверки версии 2);
- `BACKUP_CODE_PEPPER` — секрет HMAC резервных кодов;
- `DATABASE_URL` (роль `crm_app`) и `DATABASE_MIGRATE_URL` (роль
  `crm_owner`, только для миграций); `VALKEY_URL`;
- `PORTAL_URL`; из него выводятся `ALLOWED_HOSTS` и
  `CSRF_TRUSTED_ORIGINS`, отдельно их задавать не нужно;
- `TRUSTED_PROXIES` — адреса прокси администратора;
- параметры SMTP выше.

**Персональные данные.** Письма уходят только на рабочую почту сотрудника.
В письмах нет паролей и кодов второго фактора. Ссылка с кодом есть только в
приглашении и в восстановлении пароля.

## Проверка

- **Модульные и интеграционные тесты** — pytest + pytest-django на
  PostgreSQL в контейнере. Ключевые случаи:
  - ссылки: одноразовость, сроки, гашение прежней, код не принимается
    GET-запросом;
  - блокировка: 5 неудач одной записи; 20 неудач по одной записи с адреса
    не блокируют адрес; 20 неудач по 3+ записям — блокируют;
  - коды: TOTP с допуском ±1 шаг, повтор того же кода отклоняется,
    резервный код одноразов;
  - политика паролей; объединение прав ролей; защита последнего
    администратора;
  - журнал: роль `crm_app` не может изменить запись; секретов в журнале нет;
  - письма: статусы, повторы, отсутствие тела в базе.
- **Конституция** — `tools/test_constitution.py` и `sdd.py проверить` по
  `backend/` и `deploy/`.
- **Проход в браузере** — Playwright (Python) по приёмке сценариев 1–18
  спеки: письма читаются через API Mailpit. Проверяются заголовки (CSP,
  HSTS, куки) и то, что в журнале доступа nginx нет кодов из ссылок
  (NFR-007). Ширина 360 px — для входа, активации и «Безопасности».
  Автоматически — Chromium, Firefox и Edge (Playwright запускает
  установленный Edge через `channel="msedge"`; без него проект Edge
  пропускается с пометкой). Яндекс.Браузер (NFR-009) Playwright официально не
  ведёт, поэтому в конце среза человек проходит по нему и по Edge короткий
  ручной список: вход, активация, «Безопасность», карточка сотрудника
  (версия 2, по вопросу TASKS-001; уточнено при повторной проверке).
- **Одна команда проверки** — `tools/verify.sh`: тесты, `sdd.py проверить`,
  `tools/test_constitution.py`, сканер секретов. Pre-commit дополнительно
  запускает быстрые тесты конституции (версия 2).
- **Скорость (NFR-002)** — короткий прогон locust (MIT) на 100
  пользователей по списку сотрудников, журналу и истории входов: p95 не
  больше 500 мс.

Какой тест закрывает какую FR — в tasks.md (TASKS-001).

## Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Потеря ключа шифрования полей — второй фактор у всех перестаёт работать, а действующие ссылки активации нельзя показать администратору | низкая | ключ в окружении и в резервной копии у администратора; `MultiFernet` и команда `rotate_field_keys` для смены ключа; инструкция «потерян ключ — сброс второго фактора всем и перевыпуск неиспользованных ссылок через администратора» |
| Расхождение часов ВМ и телефонов — коды TOTP не проходят | средняя | допуск ±1 шаг (30 с), NTP на ВМ — в инструкции развёртывания |
| Обновление django-otp ломает наследников `Device` | низкая | версия закреплена, тесты устройств; обновление — через pip-audit и прогон тестов |
| Письма уходят в спам почтового сервера общества | средняя | SPF и DKIM для адреса отправителя — у администратора почты; журнал доставки показывает ошибки SMTP |
| Alpine CSP-сборка не поддерживает часть выражений | средняя | состояние на Alpine держим простым; сложная логика — в серверных фрагментах HTMX |

| Журнал только растёт: перебор создаёт много событий о неудачных входах | низкая | блокировка адреса ограничивает поток; рост следить в нагрузочном прогоне |
| Valkey теряет данные — счётчики блокировки обнуляются | низкая | допустимо: блокировки и события уже в журнале; Valkey с AOF |
