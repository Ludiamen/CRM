# План среза 001: вход и доступ

Как реализовать SPEC-001: модели, маршруты, письма, защита, развёртывание и
проверка. Два выбора владельца от 2026-10-01 при подготовке плана:
- **защита от перебора — свой небольшой сервис** на счётчиках Valkey, а не
  django-axes. Довод Opus (не владельца): у django-axes нет счёта «разных
  записей с одного адреса», а правило ADR-0006 «адрес — при переборе разных
  записей» без него не выполнить;
- **второй фактор — django-otp со своими устройствами:** ключ TOTP хранится
  зашифрованным ключом из окружения, резервные коды — только хешем
  (NFR-011 спеки).

Остальные технические решения здесь — решения плана (Opus; поправки
проверяющего Sonnet помечены «при проверке»), они повторяют Газоwiki, где это
возможно, и утверждаются подписью под этим планом. Владелец их не выбирал.

Решения плана:
- **Встроенная админка Django выключена:** портал смотрит в интернет, а
  администрирование — свой раздел с проверкой прав и журналом.
- **Сессии в базе**, а не в куке, чтобы закрывать сессии по одной
  («Выйти со всех устройств», блокировка записи, сброс второго фактора).
- **django-rq 4.x встраивает свою панель в админку Django**, а админка
  выключена: состояние очередей смотрим командами `rq info` и журналом
  доставки писем (при проверке).
- **Статика лежит в репозитории** (`static/vendor/`), без CDN: этого требует CSP `'self'`, и ВМ
  может работать без доступа наружу.
- **HTMX без `hx-on` и без eval** (`htmx.config.allowEval = false`),
  Alpine — CSP-сборка (`@alpinejs/csp`, у неё нет `new Function`; в
  выражениях нет стрелок, шаблонных строк и глобальных объектов, логика — в
  `Alpine.data()`): CSP остаётся без `unsafe-inline` и `unsafe-eval`
  (NFR-007 спеки). Ещё HTMX по умолчанию вставляет в страницу тег `<style>` для
  индикаторов — при `style-src 'self'` его заблокирует, поэтому
  `htmx.config.includeIndicatorStyles = false` (настройка в
  `<meta name="htmx-config">`), нужные правила — в своей теме (при проверке).
- **За прокси администратора.** TLS кончается на прокси, поэтому: nginx берёт
  настоящий адрес клиента из `X-Forwarded-For` только от адреса прокси
  (`set_real_ip_from`, переменная `TRUSTED_PROXIES`), иначе блокировка по
  адресу и история входов видели бы один адрес прокси, а подделанный заголовок
  позволял бы обходить блокировку; Django получает `SECURE_PROXY_SSL_HEADER`,
  `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`, `SameSite=Lax`, HSTS,
  `X-Content-Type-Options`, `Referrer-Policy: same-origin` на всех страницах
  (код ссылки живёт во фрагменте адреса и в Referer не уходит; версия 3),
  `TIME_ZONE = Europe/Moscow`, `LANGUAGE_CODE = ru` (NFR-007,
  NFR-010; при проверке). Страницы с вводом секретов и защищённые страницы
  отдаются с `Cache-Control: no-store`, чтобы «Назад» после выхода не показывал
  их (сценарий 10, п. 5).

### Запуск

`deploy/dev-up.sh` (`docker compose --profile dev up -d --build`) поднимает
всё, включая Mailpit. Портал
открывается на `https://127.0.0.1:8031/`, ящик Mailpit — на `:8025`. На
стенде nginx сам держит TLS с самоподписанным сертификатом (его выпускает
скрипт `deploy/dev-cert.sh`), чтобы куки `Secure`, HSTS и перенаправление на
HTTPS проверялись так же, как за прокси администратора, а не подменой
заголовков (версия 2, по вопросу TASKS-001). Playwright работает с
`ignore_https_errors`. На проде TLS держит прокси администратора, а nginx
портала слушает HTTP внутри. Порт
5000 занят сервером владельца и не используется. Первый администратор
создаётся командой `python manage.py create_first_admin --email …`: она
отказывает, если в базе уже есть учётные записи, пишет в журнал создание
записи (действующее лицо — «система») и печатает ссылку активации
(сценарий 1, письмо не нужно). Ночные задания (очистка истории входов старше
`login_history_days`, очистка просроченных ссылок и сессий) регистрируются в
`config/cron.py` для `rq cron`.

**Роли базы данных** (решение плана): `crm_owner` выполняет миграции,
`crm_app` работает в портале; web, worker и scheduler подключаются под
`crm_app` (`DATABASE_URL`), миграции идут под `crm_owner`
(`DATABASE_MIGRATE_URL`) в разовой службе `migrate` (версия 3). Остальным таблицам права получает `crm_app` через
`ALTER DEFAULT PRIVILEGES FOR ROLE crm_owner … GRANT SELECT, INSERT, UPDATE,
DELETE`, а последовательностям — `USAGE`; поэтому миграция журнала выполняет
`REVOKE ALL ON core_auditevent FROM crm_app`, затем `GRANT SELECT, INSERT` и
`GRANT USAGE` на его последовательность (иначе `INSERT` не пройдёт, а права
по умолчанию дали бы `UPDATE` и `DELETE`). Владелец таблицы обходит эти права,
поэтому `crm_app` не владеет ничем. Тест проверяет, что под `crm_app`
изменить или удалить запись журнала нельзя.

## Ключевые механизмы

**Ссылки активации и восстановления (FR-008…013, 031…033).** Код — случайные
256 бит, в базе — SHA-256 (поиск) и Fernet (показ администратору и отправка).
В письме
ссылка вида `https://<портал>/activate/#<код>`. Сервер получает запрос
без кода. Свой скрипт страницы (внешний файл, CSP) читает фрагмент, стирает
его из адресной строки (`history.replaceState`) и отправляет код
POST-запросом на `/activate/exchange/`. Сервер сверяет SHA-256 кода с
`OneTimeLink`, проверяет срок и состояние и кладёт в сессию отметку «идёт
активация пользователя N». Дальше шаги мастера: профиль → пароль → TOTP →
резервные коды. Ссылка гаснет после последнего шага. Неверная, истёкшая и
использованная ссылки дают одно и то же сообщение. Запросы восстановления
считаются в Valkey: не больше 3 писем в час на адрес и 10 в час с одного IP,
сверх предела ответ прежний, письмо не уходит (сценарий 18, п. 9; пределы —
при проверке, подтверждаются подписью). Администратор увидит ссылку активации
в карточке (расшифровка пишет событие в журнал).

**Вход (FR-021, 025, 034…041).**
1. Почта и пароль.
2. Проверка блокировки записи и адреса — до проверки пароля.
   Для несуществующей записи выполняется холостая проверка хеша, чтобы по
   времени ответа нельзя было отличить её от существующей.
3. Пароль неверен — одно общее сообщение для всех причин (FR-034), неудача
   уходит в счётчики, попытка — в историю.
4. Пароль верен — если у записи нет подтверждённого второго фактора (не
   дошла до конца активации или сброшен), выдаётся ограниченная сессия:
   middleware пускает её только на страницы подключения фактора и показа
   резервных кодов (FR-021, NFR-004, сценарии 3.6 и 7.2). Иначе — шаг
   второго фактора: код TOTP или резервный код. Неверный код — такая же
   неудача в счётчиках и истории, как неверный пароль (FR-025); так же
   считаются неверные коды при подключении фактора (сценарий 3.4) и неверный
   текущий пароль при его смене (сценарий 16.4).
5. Код верен — вход, `UserSession`, распознавание устройства по куке. Новое
   устройство (не первый вход после активации) — письмо. Счётчик неудач
   записи обнуляется.

**Сервис блокировки (ADR-0006).** Ключи Valkey с временем жизни:
- `fail:acct:<id>` — неудачи записи подряд (срок жизни — сутки от последней
  неудачи, при проверке; успешный вход удаляет ключ);
- `lock:acct:<id>` — запись заблокирована на `account_lock_minutes`;
- `fail:ip:<ip>` — неудачи с адреса в окне `ip_lock_window_minutes`;
- `accts:ip:<ip>` — множество хешей логинов, которые перебирали с адреса;
- `lock:ip:<ip>` — адрес заблокирован.

В `fail:ip` не считаются отказы по уже заблокированной записи (результат
`locked`): иначе повторы по одной заблокированной записи набирали бы порог.
Счётчики меняются атомарно (скрипт Lua или `MULTI`: `INCR`/`SADD` + `EXPIRE`).
Адрес блокируется, когда `fail:ip` ≥ `ip_lock_limit` **и** в `accts:ip` не
меньше `ip_lock_min_accounts` разных записей. Минимум разных записей
(3 по умолчанию) — решение плана: ADR-0006 и спека его не задают.
Попытки входа в несуществующие записи тоже считаются по их хешу. Блокировка
и её снятие пишутся в журнал. Снять блокировку раньше срока (FR-038) можно
действием «Снять блокировку входа» в карточке сотрудника и на странице
`/staff/locks/` (список заблокированных адресов и записей; право
`accounts.manage`): ключи `lock:*` и `fail:*` удаляются, событие — в журнал. Письмо о блокировке записи (FR-037) уходит
один раз на блокировку. Если Valkey потеряет данные, счётчики просто
обнулятся, а события уже записаны в журнале.

**Сессии и бездействие (FR-028…030).** Время бездействия запоминается в
сессии при её создании (значение `idle_timeout_minutes` на тот момент):
изменённая политика действует для новых сессий, как требует сценарий 10.2
спеки (решение Opus по находке проверки). Промежуточное ПО продлевает
сессию на это время при каждом запросе и закрывает её по бездействию. «Выйти со всех устройств», смена пароля, сброс второго
фактора и блокировка записи удаляют сессии по `UserSession`.

**Права (FR-014…020).** Декоратор и миксин `require_permission(code)`
стоят на каждом представлении. Меню строится из того же списка прав.
Объединение прав ролей кэшируется в Valkey по ключу `perms:<id>`; при
изменении ролей или их назначения ключи затронутых держателей удаляются, и
право действует со следующего запроса (сценарий 12.2); потеря Valkey ведёт
лишь к пересчёту из базы. Права начальных ролей (FR-020): у «Администратора
портала» все семь, у «Руководителя» и «Сотрудника ИТ» ни одного — их раздел
«Безопасность» и профиль требуют только входа. Свой второй фактор
администратор сбросить не может (FR-024), профиль сотрудник правит только в
части телефона и контактов (FR-006), удаления учётных записей нет (FR-005). Защита последнего администратора — в сервисе ролей (FR-019).

**Журнал (FR-044…047).** `core.services.audit.record(...)` вызывается из
сервисов, не из представлений; состав событий — FR-044 целиком, включая
неудачные попытки входа, запрос восстановления, выход со всех устройств и
доставку писем (смена статуса `MailMessage`). Внешний ключ `actor` — `PROTECT`
(пользователи не удаляются; `SET_NULL` был бы `UPDATE` таблицы журнала). Пароли, ключи и коды в «было/стало» не
попадают: у полей с такими данными стоит отметка «скрыть». Список журнала —
сетка UX-04 с пресетами «Сегодня», «Вход и доступ», «Права и роли», «Настройки» (как в
сценарии 13 спеки) и выгрузкой CSV; в ячейках, начинающихся с `=`, `+`, `-`, `@`, табуляции или возврата
каретки, перед значением ставится апостроф (защита от формул Excel).

**Оболочка и интерфейс (FR-050, 051; UX-01…04, 11, 12).**
- Левое меню показывает только разделы, доступные по правам; режим
  «только значки» запоминается в `localStorage`.
- Карточка сотрудника открывается слайдером (UX-03): HTMX подгружает
  фрагмент в боковую панель и меняет адрес. Тот же адрес открывается и
  обычной страницей.
- «Безопасность» в профиле собрана в одном слайдере (UX-12).

## Интеграции

**Исходящая почта (ADR-0005, FR-052…055).** `integrations.mail.services.send(template, to, context, *, related_user=None)`:
1. создаёт `MailMessage` со статусом `queued`;
2. ставит задание RQ в очередь `mail` после фиксации транзакции
   (`transaction.on_commit`; в django-rq 4.x режим `on_db_commit`), в задание
   уходит единственным аргументом номер письма: коды ссылок в Valkey не
   попадают (прочий контекст письма без секретов — в `job.meta`, см.
   «Уточнения версии 3»);
3. задание рендерит шаблон (русский, с названием портала) и отправляет по
   SMTP. Повторы: `Retry(max=11, interval=[60, 300, 900, 3600] + [10800] * 7)`,
   то есть 1, 5, 15, 60 минут, затем семь раз по 3 часа — последняя попытка
   примерно через 22 часа 20 минут (TGT-NFR NFR-06, до 24 часов). Паузы
   работают только если рабочий процесс запущен с `--with-scheduler`. После
   последней неудачи обработчик `on_failure` ставит `failed` (тест проверяет,
   что обработчик не срабатывает после промежуточных неудач), каждая попытка пишет `MailAttempt`, и это
   видно в журнале доставки и в карточке сотрудника (FR-009).

Шесть писем: приглашение, восстановление пароля, блокировка записи, вход с
нового устройства, сброс второго фактора, смена пароля.

Параметры — `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`,
`SMTP_FROM`, `SMTP_SECURITY` (`starttls` / `ssl` / `none`), `PORTAL_URL`
(адрес для ссылок) — только в окружении. Для разработки и тестов — Mailpit.

**Окружение целиком** (версия 2, по вопросу TASKS-001). Все секреты и
параметры установки — переменные окружения, в репозитории только
`deploy/.env.example` с заглушками:
- `DJANGO_SECRET_KEY`;
- `FIELD_ENCRYPTION_KEYS` — ключи Fernet через запятую (первый шифрует,
  остальные расшифровывают — смена ключа через `MultiFernet`); ими
  шифруются ключ TOTP и код ссылки. Новый ключ ставится первым, затем
  команда `python manage.py rotate_field_keys` перешифровывает
  `EncryptedTOTPDevice.key_encrypted` и `OneTimeLink.code_encrypted`
  (`MultiFernet.rotate()`), и только после неё старый ключ убирается из
  списка (по находке проверки версии 2);
- `BACKUP_CODE_PEPPER` — секрет HMAC резервных кодов;
- `DATABASE_URL` (роль `crm_app`) и `DATABASE_MIGRATE_URL` (роль
  `crm_owner`, только для миграций); `VALKEY_URL`;
- `PORTAL_URL`; из него выводятся `ALLOWED_HOSTS` и
  `CSRF_TRUSTED_ORIGINS`, отдельно их задавать не нужно;
- `TRUSTED_PROXIES` — адреса и сети прокси администратора; подсеть compose
  `CRM_SUBNET` добавляется к ним всегда (версия 3);
- параметры SMTP выше.

**Персональные данные.** Письма уходят только на рабочую почту сотрудника.
В письмах нет паролей и кодов второго фактора. Ссылка с кодом есть только в
приглашении и в восстановлении пароля.

## Проверка

- **Модульные и интеграционные тесты** — pytest + pytest-django на
  PostgreSQL в контейнере. Ключевые случаи:
  - ссылки: одноразовость, сроки, гашение прежней, код не принимается
    GET-запросом;
  - блокировка: 5 неудач одной записи блокируют запись, но не адрес;
    20 неудач по разным записям за окно блокируют адрес (при значениях по
    умолчанию это перебор четырёх и более записей: отказы по уже
    заблокированной записи в счёт адреса не идут; правило адреса тесты

- **Конституция** — `tools/test_constitution.py` и `sdd.py проверить` по

- **Проход в браузере** — Playwright (Python) по приёмке сценариев 1–18

## Уточнения версии 3 (по ходу выполнения среза)

Решения, которые план версии 2 не задавал и которые приняты при выполнении
среза. Если ниже сказано иначе, чем в разделах выше, действует этот раздел.
Подробности и тесты — `backend/tests/CONTRACT.md`, ход работы —
`docs/reviews/TASKS-001.md`. Принимал Opus, кроме двух решений, выбранных
владельцем: конституция версии 2 (сторонние библиотеки вне проверки) и
порядок отметок задач (SDD-PROCESS версии 3).

### Безопасность и вход
- **Границы настроек безопасности** — значение вне границ — отказ формы с
  названием нарушенной границы. По длине и истории паролей, бездействию,
  числу неудач и сроку блокировки записи, сроку блокировки адреса
  границы только ужесточают относительно утверждённых значений. Пороги
  адреса `ip_lock_limit`, `ip_lock_min_accounts`, `ip_lock_window_minutes`
  (FR-036: «порог и окно — настройка») в границах таблицы можно менять в обе
  стороны, в том числе ослаблять (при проверке: прежняя фраза «ослаблять не
  может» противоречила таблице). Решение Opus: так и оставить — NFR-006 и
  FR-036 прямо называют числа адреса настройкой, а поднять порог нужно, когда
  несколько сотрудников выходят в сеть через один адрес (филиал за NAT);
  пределы таблицы не дают выключить правило совсем:

  | Поле | По умолчанию | Допустимо |
  |---|---|---|
  | `password_min_length` | 12 | 12…128 |
  | `password_history` | 5 | 5…24 |
  | `password_max_age_days` | выключено | выключено или 30…365 |
  | `idle_timeout_minutes` | 60 | 5…60 |
  | `account_lock_limit` | 5 | 3…5 |
  | `account_lock_minutes` | 15 | 15…1440 |
  | `ip_lock_limit` | 20 | 5…100 |
  | `ip_lock_min_accounts` | 3 | 2…20 |
  | `ip_lock_window_minutes` | 15 | 5…60 |
  | `ip_lock_minutes` | 15 | 15…1440 |
  | `login_history_days` | 365 | 30…365 |
- **Порог адреса при значениях по умолчанию**: отказы по уже заблокированной
  записи в счёт адреса не идут, поэтому адрес блокируется при переборе
  четырёх и более записей; каждая запись при этом защищена своей
  блокировкой. Отказы `locked` и `ip_locked` пишутся и в историю входов, и в
  журнал (`login.failed` с результатом) — FR-044.
- **Цепочка прокси**: прокси администратора → наш nginx → Django. Один
  список `TRUSTED_PROXIES` (адреса и сети CIDR) содержит адреса прокси
  администратора; к нему всегда добавляется подсеть compose `CRM_SUBNET`.
  nginx: `set_real_ip_from` по каждому элементу (собирает `nginx-render.sh`;
  пустой список и `0.0.0.0/0` отвергаются), `real_ip_recursive on`, в Django
  уходит `X-Forwarded-For $remote_addr`. Django по тому же списку берёт
  последний недоверенный адрес из заголовка.
- **Политика реферера везде `same-origin`**: код ссылки живёт только во
  фрагменте адреса и в Referer не уходит. Проверка CSRF — стандартная Django
  без исключений, `Origin: null` отвергается всегда.
- **Вход по паролю без подключённого второго фактора** даёт ограниченную
  сессию и событие `login.success` с `via=password`; ограничение снимается,
  а устройство запоминается, только когда фактор подключён и сохранение
  резервных кодов подтверждено. Страница входа не повторяет
  введённую почту (одинаковый ответ на любой отказ, FR-034).
- **Резервные коды**: при вводе дефисы, пробелы и регистр не важны; набор
  выпускается при показе страницы кодов — до «Я сохранил» перезагрузка
  выпускает новый набор, после — повторный показ невозможен.
- **Учётные записи**: почта уникальна без учёта регистра (`Lower(email)`);
  разблокировка возвращает прежнее состояние (`User.blocked_from`: `invited`
  остаётся `invited`, ссылка при блокировке погашена).
- **Опасные действия** — блокировка, сброс второго фактора, удаление роли,
  выпуск новых резервных кодов — в форме имеют обязательный флажок
  подтверждения (`confirm`, атрибут `required` в разметке). Сервер этот флажок
  у этих четырёх действий не проверяет: это защита от случайного нажатия, а
  не от запроса в обход формы (при проверке: прежняя фраза «выполняются только
  с отмеченным флажком» не соответствовала коду). Флажок «Я сохранил коды» при
  первом показе резервных кодов сервер проверяет. Решение Opus: так и
  оставить — спека требует, чтобы человек подтвердил действие в интерфейсе;
  запрос в обход формы может послать только обладатель права, и он защищён
  CSRF; ни один приёмочный тест на проверку флажка сервером не опирается.

### Журнал и администрирование
- Событие `link.revealed` пишется при каждом открытии карточки
  приглашённого, где показана ссылка активации.
- Право «просматривать чужие входы» без права управлять учётными записями
  открывает `/staff/<id>/logins/` отдельной страницей, устройства — только
  для чтения.
- Выгрузка журнала в CSV — вся выборка без ограничения строк, UTF-8 с BOM,
  защита от формул: апостроф перед `=`, `+`, `-`, `@`, табуляцией и
  возвратом каретки. Пресет «Настройки» — события `security_settings.*` и
  `portal_settings.*`.

### Почта и фоновые задания
- `send(template, to, context, *, related_user=None)`; код ссылки в задание
  не передаётся — рабочий процесс берёт его из `OneTimeLink`; остальной
  контекст письма без секретов (имя, время, браузер, адрес) едет в
  `job.meta` задания, позиционный аргумент задания один — номер письма (при
  проверке); ссылка,
  погашенная до отправки, даёт письму `failed` без повторов; отправка всегда
  по SMTP; `failed` ставится, когда повторы исчерпаны; у письма заголовок
  `X-Portal-Template` (имя шаблона, без персональных данных).
- **Контекст письма в Valkey.** В `job.meta` лежат имя, время, браузер,
  платформа и адрес IP — то, что и так уходит в письмо. Удачное задание живёт
  60 секунд, неудачное — 7 дней (`FAILED_JOB_TTL`), затем Valkey его удаляет;
  Valkey виден только в сети compose (порт наружу не открыт), его файл AOF
  лежит в томе `valkey-data`. Решение Opus по находке проверки: допустимо,
  переносить контекст в базу не нужно — срок короче срока истории входов
  (FR-039), а коды ссылок и секреты в Valkey не попадают.
- `config/rq_settings.py`; рабочий процесс — `rq worker -c config.rq_settings
  --with-scheduler mail`, ночные задания — `rq cron config.cron -c
  config.rq_settings` (очередь `mail`, 03:10, 03:20, 03:30).
- `MIGRATION_MODULES = {"django_rq": None}`: миграции django_rq под ролью
  `crm_app` падали на пустой базе.

### Интерфейс и файлы
- `/media/` отдаёт только PNG и JPEG с `nosniff`, остальное — 404. Это
  держат и Django (на стенде без nginx), и nginx: файлы `.png`, `.jpg`,
  `.jpeg` отдаются с типом по расширению, всё прочее под `/media/` — 404.
  Решение Opus по находке проверки: прежде nginx отдавал каталог целиком, и
  ограничение держалось только на проверке файла при загрузке.
- Слайдер начинается под верхней панелью и не перекрывает её; в верхней
  панели — ссылки и кнопка «Выйти» без выпадающего меню; кнопки, которые не
  отправляют форму, — без `type="submit"`.

### Развёртывание и стенд
- `deploy/Dockerfile` со стадиями приложения и nginx; `entrypoint.sh`
  выполняет миграции под `crm_owner` только у службы с `RUN_MIGRATIONS=1`;
  `healthcheck.py` — проверка здоровья.
- **Учётные данные владельца схемы** (`DATABASE_MIGRATE_URL`) получают только
  разовая служба `migrate` (выполняет миграции и завершается; web ждёт её
  успешного завершения), `standtools` профиля dev и тестовая служба `test` (профиль test). У web, worker и scheduler
  переменная пуста. Решение Opus по находке проверки: иначе взлом процесса
  портала давал бы права владельца и обходил запрет роли `crm_app` менять и
  удалять записи журнала (инвариант «аудит-изменений»).
- Два конфига nginx: `nginx.conf` — свой TLS для стенда, `nginx.prod.conf` —
  HTTP за прокси администратора; выбор — `NGINX_CONF` и `NGINX_PORT`. На
  стенде HTTP перенаправляется на HTTPS на том же порту (`error_page 497`).
- Подсеть compose — `CRM_SUBNET` (по умолчанию `172.31.77.0/24`); MTU —
  `DOCKER_MTU` (по умолчанию 1500; на машине разработки 1360 из-за VPN);
  сборка образа с `network: host`.
- Стенд одной командой — `deploy/dev-up.sh`. Флаг `E2E_STAND=1` есть только у
  служебной службы `standtools` профиля dev; команда `e2e_reset_stand`
  работает только с ним и под владельцем схемы. Она стирает данные стенда,
  включая журнал; на рабочем портале её не запустить (без флага — отказ), и
  инвариант «аудит-изменений» к стенду приёмки не относится.
- Окружение дополнено: `POSTGRES_PASSWORD`, `CRM_OWNER_PASSWORD`,
  `CRM_APP_PASSWORD`, `DOCKER_MTU`, `CRM_SUBNET`, `NGINX_CONF`, `NGINX_PORT`, `NGINX_HEALTH_URL` (адрес проверки
  здоровья nginx), `WEB_WORKERS` (число рабочих gunicorn, по умолчанию 4);
  значения по умолчанию есть в `docker-compose.yml`; в `.env.example` стоят
  пароли ролей, `DOCKER_MTU` и закомментированные `NGINX_CONF`,
  `NGINX_HEALTH_URL`, а `CRM_SUBNET`, `NGINX_PORT`, `WEB_WORKERS` не
  перечислены (при проверке).

### Сторонние библиотеки и проверки
- Bootstrap 5.3.8, HTMX 2.0.11, Alpine.js CSP 3.17.4 — версии и sha256 в
  `backend/static/vendor/VERSIONS.md`; `tools/verify_vendor.py` сверяет их с
  реестром npm и не пускает в каталог ничего лишнего (входит в
  `tools/verify.sh`); каталог вне проверки по конституции версии 2 (она ждёт подписи владельца).
- Тесты: `django_db(transaction=True)` недоступен (у `crm_app` нет
  `TRUNCATE`) — вместо него `django_capture_on_commit_callbacks`; приёмка
  Playwright идёт кругами по браузерам со сбросом стенда между ними;
  контракт имён для реализации — `backend/tests/CONTRACT.md`.
- `tools/check_secrets.py`: путь страницы и адрес без учётных данных —
  не секрет; пароль в адресе базы ловится по-прежнему.

## Уточнения версии 4 (этап 4, проверка среза)

Решения этапа 4 (T-300…T-306). Если ниже сказано иначе, чем в разделах выше,
действует этот раздел. Ход работы и замеры — `docs/reviews/TASKS-001.md`.

- **Модель нагрузки NFR-002** (решение владельца 2026-10-03). Требование не
  задаёт, как часто сотрудник действует и как быстро все входят, а результат
  зависит от этого сильнее всего. Критерий: 100 вошедших сотрудников, вход по
  одному в секунду, пауза между действиями 5–15 с, замер после того, как
  вошли все (`--reset-stats`), 6 минут; p95 каждой из четырёх страниц (список
  сотрудников, его фрагмент HTMX, журнал, история входов) не больше 500 мс,
  ошибок нет. Прогон с паузой 1–3 с и входом 10 в секунду (около 50 запросов
  в секунду) — замер ёмкости стенда, не критерий. Учётные записи для прогона
  готовит `backend/tests/load/prepare_users.py` (только при `E2E_STAND=1`).
- **Пул соединений PostgreSQL** (решение владельца 2026-10-03 по предложению
  Opus). Под ASGI Django советует не держать постоянные соединения, а брать
  пул драйвера; без него каждый запрос открывал новое соединение (новый
  процесс PostgreSQL и проверка пароля SCRAM). `psycopg-pool` (LGPL-3),
  `OPTIONS["pool"] = True` у алиаса `default` при `DATABASE_POOL=1`;
  переменная задана только у web (`docker-compose.yml`). У worker и scheduler
  пула нет: задания RQ исполняются в процессах, порождённых fork-ом.
- **gunicorn**: `--no-control-socket`. Управляющий сокет утилиты `gunicornc`
  (gunicorn 25.1+) по умолчанию создаётся в `$HOME/.gunicorn`, куда
  пользователю `portal` писать нельзя, и не нужен: процессами управляет
  compose.
- **Журнал**: шаг «профиль» мастера активации пишет `user.updated` с «было» и
  «стало», как правка своего профиля (FR-044; находка проверки инвариантов
  T-305).
- **Сборка на машине разработки**: если BuildKit с `network: host` не находит
  имена (2026-10-03: в `/etc/resolv.conf` хоста только `127.0.0.53`), образ
  собирается через bridge: `docker build --network default -f
  deploy/Dockerfile --target app -t crm-portal:local .`, затем
  `docker compose --profile dev up -d` без `--build`.

## Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Потеря ключа шифрования полей — второй фактор у всех перестаёт работать, а действующие ссылки активации нельзя показать администратору | низкая | ключ в окружении и в резервной копии у администратора; `MultiFernet` и команда `rotate_field_keys` для смены ключа; инструкция «потерян ключ — сброс второго фактора всем и перевыпуск неиспользованных ссылок через администратора» |
