# Задачи среза 004

Формат строки: `- [ ] T-NNNN [P] [исполнитель] описание — путь или тест — (FR-NNN)`.
`[P]` — можно делать параллельно с соседними задачами. Исполнитель — haiku / sonnet / opus / человек (по разделу
«Разделение работы между моделями» в docs/sdd-process.md). Задачи собраны из PLAN-004 и SPEC-004 (11 сценариев,
FR-301…345, NFR-301…312). Задач вне плана здесь нет. Решения, которых план не принимал, собраны в разделе «Решения
Opus по задачам» в конце файла.

Как читать и исполнять:
- **Нумерация.** Номера среза 004 четырёхзначные: Этап 1 — T-4001…, Этап 2 — T-4100…, Этап 3 — T-4200…, Этап 4 —
  T-4300…. Требования среза нумеруются с трёх сотен (FR-301…).
- **Порядок.** Этапы идут подряд. Внутри этапа задача без `[P]` начинается, когда закончены все предыдущие, а
  задачи с `[P]` не зависят от соседей и не правят общих с ними файлов.
- **Тест-на-требование.** В Этапе 2 у каждого теста в скобках стоит FR или NFR, который он закрывает. Запись
  `файл::имя_теста` и есть связь T-NNNN → FR → тест. Приёмка сценариев 1–11 — сценарии Playwright
  `backend/tests/e2e/test_eNN_*.py`.
- **Красный прежде зелёного.** Задачи Этапа 3 не начинаются, пока не сделан красный прогон T-4160: тесты сначала
  падают, и это записано. Тест не ослабляют, чтобы он прошёл. Правят код, а правка теста допускается только с
  причиной в отчёте.
- **Регрессия срезов 001–003.** После каждой партии Этапа 3 прогоняется весь серверный набор. Тесты и инструменты
  прежних срезов меняются только по перечню T-4138. Если упадёт другой тест прежнего среза, его не ослабляют:
  исполнитель останавливается, решение принимает Opus и записывает его в отчёт. Правку любого теста система
  разрешений останавливает — до правки спросить владельца с диффом, по одному тесту.
- **Границы модулей.** `apps/notify` не импортирует `apps.servicedesk` и из `apps.org` берёт только
  `apps.org.services.calendar`; ядро, `org` и `servicedesk` не импортируют `apps.notify`. Виды уведомлений модули
  регистрируют в точке ядра `notification_kinds`, события идут шиной `apps/core/events.py` (план: «Точки расширения
  ядра и шина событий»).
- **Размер.** Одна задача — не больше полудня работы одного исполнителя. Задание агенту — не больше ~50 вызовов.
  Файл тестов — не больше ~25 тестов; большее делится на задачи.
- **Общие файлы тестов.** `tests/CONTRACT-004.md` и `tests/support_notify.py` пишет только T-4100,
  `tests/e2e/helpers_notify.py` — только T-4140. Параллельные исполнители держат свои помощники внутри своего файла
  теста, а общие файлы не правят.
- **Общие файлы кода** (Этап 3) — у каждого один автор за раз; задачи, которые их правят, идут без `[P]` (раздел
  «Решения Opus по задачам», п. 9).
- **Секреты — только `***`** (в коде, документах, отчётах, выводе команд). Это правило ставится в задание каждому
  исполнителю. Токены ботов и ключи VAPID — только в `deploy/.env`; в тестах — сгенерированные на месте значения.
- **Если задание расходится с планом,** исполнитель останавливается и спрашивает Opus. Решение сначала вписывается
  в раздел «Решения Opus по задачам», и только потом меняется код.
- Ссылки на разделы плана — в названии задачи или в `(план: …)`.
