# План среза 005: база знаний и сквозной поиск

Как реализовать SPEC-005: статьи в Markdown с безопасным выводом, черновики и публикация, история с сравнением,
восстановлением и защитой от одновременной правки, корзина с ночной очисткой, рубрики деревом и свободные теги,
вложения и картинки в тексте, комментарии, «Статья из решения» и связь статей с заявками, предупреждение о
персональных данных, уведомления базы знаний, журнал и сквозной поиск по заявкам, статьям, сотрудникам и
подразделениям из верхней панели. Срез строится на механизмах срезов 001–004 (PLAN-001…PLAN-004): права через роли,
журнал `audit.record`, точки расширения ядра и шина событий, файлы с проверкой ClamAV и выдачей `X-Accel-Redirect`,
полнотекстовый поиск заявок, каталог видов уведомлений, стенд и приёмка Playwright. Здесь описано только новое и то,
что в прежних срезах меняется.

Технические решения плана принимал Opus, владелец их не выбирал. Они утверждаются подписью под этим планом. Там, где
спека оставила решение плану («способ определяет план», «решает план»), решение помечено «решение плана». Факты
проверены до черновика запуском и чтением исходников (файлы фактов `crm-work/slice005/plan/facts/F1…F4`, сводка
`crm-work/slice005/facts.md`); замеры — «замер 2026-10-18» на временном PostgreSQL 17 машины, занятой другими задачами.

Главные решения:
- **Два новых приложения: `knowledge` (статьи) и `search` (сквозной поиск)** — как в TGT-ARCH. `search` не знает
  модулей: модули регистрируют поставщиков в новой точке ядра `search_providers` (FR-445). Заявки поставляет
  `servicedesk` (обёртка над существующим поиском среза 003), статьи — `knowledge`, сотрудников — ядро (справочник
  живёт в `core`, названия подразделений сотрудника добавляет существующая точка `staff_directory`), подразделения —
  `org` (FR-445).
- **Markdown — `markdown-it-py` 4.2.0, белый список HTML — `nh3` 0.3.7** (обе MIT; bleach не поддерживается с
  2026-06-05 — F1). Сырой HTML выключен, ссылки и картинки — через свои обработчики; готовый HTML и «чистый текст» для
  индекса считаются при сохранении и хранятся в статье и версии, страница статьи берёт готовое (F1: патологический
  текст на 200 000 знаков рендерится до 5,4 с — показ не должен зависеть от этого).
- **Поиск статей — два вектора и два шага**: малый вектор (заголовок и теги) находит и ранжирует совпадения в заголовке,
  полный (A заголовок, B теги, C первые 100 000 знаков текста) добирает совпадения только в тексте с потолком 300
  кандидатов. Ранжирование полным вектором на частых словах давало p95 0,6–0,94 с, отбор по полному с рангом по малому —
  0,62–0,67 с, отбор и ранг по малому — 4–13 мс, потолок 300 кандидатов — 28–53 мс (F2 Ф8). Число «найдено» на странице
  результатов подгружается отдельным запросом; по заявкам — с потолком «1000+» (точный счёт 2,3–2,6 с, с потолком —
  p95 0,57 с, F2 Ф9).
- **Общее — в ядро**: модель и служба комментария (`core.Comment`, FR-426), проверки загрузки файлов (перенос из
  `servicedesk`, FR-424), определение формата картинки и общий ответ выдачи файла, подпись сотрудника с «уволен».
  Новая точка ядра `ticket_card_parts` — для раздела «Статьи», кнопки «Статья из решения» и инструмента «Ссылка на
  статью» в карточке заявки (FR-432): `servicedesk` не импортирует `knowledge`.
- **Уведомления**: три вида `knowledge` в каталоге `notify`; единственная правка `notify` — признак вида «склеивать»
  (`coalesce`) и ветка в `dispatch.create`: пока у получателя есть непрочитанное уведомление того же вида о том же
  объекте, новое не создаётся (FR-435). «Одно уведомление получателю на событие» (Д14) обеспечивает сам `knowledge`
  в правилах своих видов, без правки `notify`.
- **Обычные синхронные представления**, как во всём портале: под ASGI у каждого запроса свой поток, а долгий рендер
  ограничивают пределы текста и готовый HTML при показе.
- **Без новых служб**: ночная очистка корзины — одна запись в `config/cron.py`; новые зависимости Python — три строки, из них одна транзитивная (`mdurl`).

### Точки расширения ядра и шина событий
- **Новая точка `search_providers`** (решение плана, FR-445): запись `SearchProvider(key, title, order, search,
  available)`; `available(user) -> bool` — показывать ли группу пользователю; `search(user, parsed, limit, offset) -> list[SearchRow]`
  и `count(user, parsed) -> (число, больше потолка)` (подсчёт — отдельным запросом страницы результатов); строка `SearchRow(title, subtitle, url, template, context)`;
  `parsed` — `ParsedQuery` (разбор запроса в `search.parse`: слова, номер, подсказка). Поставщики: `servicedesk` — «Заявки» (порядок 10), `knowledge` — «Статьи»
  (20), ядро — «Сотрудники» (30), `org` — «Подразделения» (40). Следующие срезы добавят свои записи.
- **Новая точка `ticket_card_parts`** (решение плана, FR-432, FR-433): запись `TicketCardPart(key, kind, order,
  render)`, где `kind` — `section` (раздел карточки), `closed_action` (кнопка у закрытой заявки) или `comment_tool`
  (кнопка в форме внутреннего комментария); `render(request, ticket_ref) -> str | None` — фрагмент или ничего.
  `ticket_ref` — номер заявки и признаки, нужные модулю (закрыта ли с решением), без модели `Ticket`. Карточка
  вызывает записи точки; нет записей (модуль выключен) — нет разделов и кнопок, карточка работает (FR-433).
- **Существующие точки**: `menu_items` («База знаний», видна всем — F3 Ф10), `top_bar_items` (строка поиска,
  `search`, порядок перед колокольчиком), `notification_kinds` (три вида `knowledge`), `audit_labels`, `file_purposes`
  (назначение `knowledge` — что делать после проверки ClamAV), `stand_reset`.
- **События шины** (публикует `knowledge`, после фиксации транзакции): `knowledge.article_published`
  (`article_id`, `actor_id`, `rubric_id`), `knowledge.article_changed` (`article_id`, `actor_id`, `rubric_id` — только
  сохранение опубликованной статьи), `knowledge.comment_added` (`article_id`, `comment_id`, `actor_id`). Подписчики —
  виды уведомлений `knowledge` в `notify`.

### Права среза
`knowledge.edit` «Редактирование базы знаний», `knowledge.manage` «Управление базой знаний» (FR-406). Миграция данных
`knowledge 0002` создаёт права и выдаёт их встроенным ролям по названию (`is_builtin=True`; у роли кода нет; роль ищется через `filter().first()`, нет роли — пропуск без ошибки) — и новой установке, и существующей при обновлении (Д9;
по образцу `notify 0002` — F3 Ф8): «Администратор портала» — оба, «Сотрудник ИТ» — `knowledge.edit`. Чтение
опубликованных статей и поиск прав не требуют (вошедший сотрудник); группы «Сотрудники» и «Подразделения» — право
`staff.view` (SPEC-002 FR-118), «Заявки» — видимость заявок (SPEC-003).

### Запуск
Службы прежние: web (gunicorn + uvicorn-worker), worker (`files` — проверка вложений статей той же очередью),
worker-mail, worker-notify, scheduler (`rq cron` — новая запись, при обновлении службу перезапускают: модуль читается при старте), nginx (выдача файлов статей через тот же внутренний
`location /protected/attachments/`; новый `location ~ ^/kb/[0-9]+/files/$` с `client_max_body_size 55m`, как у форм
заявок: общий предел тела 6 МБ не пропустит файл 20 МБ, а файл больше 20 МБ должен дойти до Django и получить причину
отказа; правка в `deploy/nginx.conf` и `deploy/nginx.prod.conf`; директивы `proxy_*` в новом `location` повторены, как у
`= /request/`, — из `location /` они не наследуются). Новых томов нет: файлы статей лежат в томе `protected` и попадают в резервную копию и
восстановление без правок `backup.sh` и `RESTORE.md` (F4 Ф4, NFR-413).

Почему готовый HTML хранится: патологический текст на 200 000 знаков рендерится до 5,4 с (F1), обычная статья — миллисекунды;
показ статьи и версии не должен зависеть от содержимого. Перерисовка при смене правил вывода — команда
`kb_rerender` (все статьи и версии, порциями), запуск — в инструкции обновления, если правила меняются.

Почему векторы пусты у черновиков и статей в корзине: тогда условие «не найден» (FR-444, FR-447) держит сам индекс, а не
фильтр, который можно забыть; при публикации и возврате опубликованной статьи векторы считаются заново.

Права роли приложения в базе — как в срезе 004: новые таблицы получают права через `ALTER DEFAULT PRIVILEGES`, своих
`GRANT` не нужно.

### Как статья ссылается на вложение

Кнопка «Картинка» вставляет разметку `![имя](att:N)`, где `N` — номер `ArticleFile` (FR-423); ссылка на вложение —
`[имя](att:N)` (кнопка «Вставить ссылку» в списке вложений). Схема `att:` — только внутренняя запись текста: при рендере
обработчики `render.py` превращают её в адрес картинки `/kb/<номер статьи>/images/N/` или файла
`/kb/<номер статьи>/files/N/`, если вложение `N` принадлежит этой статье, а иначе выводят текст «[вложение недоступно:
имя]» (F1 Ф5: 36 проб; прямой путь `/kb/…` в разметке и внешние адреса картинок тоже дают заглушку). В готовом HTML
остаётся `<img src="/kb/<id>/images/N/" alt="…" loading="lazy">` независимо от состояния проверки: состояние меняется
после сохранения, и HTML от него не зависит. Оба представления при каждом запросе проверяют право на статью (FR-409):
- `/kb/<id>/images/N/` — «чистая» картинка отдаётся для показа (`X-Accel-Redirect` в защищённый том, тип — из
  `image_format`, не из браузера; `nosniff`); «проверяется» — заглушка «проверяется»; строки `ArticleFile` с этим номером
  нет — заглушка «вложение удалено»; карантин или вложение не картинка — заглушка «недоступно» (SVG из статики портала,
  FR-423, сценарий 5 п. 10);
- `/kb/<id>/files/N/` — «чистый» файл скачиванием (`Content-Disposition: attachment`, как вложения заявок); в остальных
  состояниях и для удалённого — тот же ответ, что у несуществующего.

Недоступная статья (чужой черновик, статья в корзине для не-управляющего) по обоим адресам даёт ответ несуществующего, а
не заглушку: это выдача файла, а не страница статьи, поэтому 410 «Статья удалена» здесь не отдаётся (ПД2). Если автор вручную впишет `att:N` вложения, загруженного позже сохранения, ссылка оживёт при следующем
сохранении (HTML считается при сохранении).

## Ключевые механизмы

### Рендер Markdown и безопасный вывод (FR-402, FR-403, NFR-403, NFR-405, NFR-406)

`render.render(text, files) -> Rendered(html, plain)` — одна функция для сохранения, версии и предпросмотра; `files` —
словарь `N → (имя, image_format)` вложений этой статьи, полученный до вызова (рендер в базу не ходит). Устройство:
основа — то, что прошло 36 проб F1 Ф5; отличия плана (адреса `/kb/<id>/images/N/` и `/kb/<id>/files/N/`, схема `att:N`
у ссылок, выравнивание классами, обёртка `kb-scroll`, `maxNesting`, фильтр `class`) в тех пробах не участвовали и
проверяются набором тестов раздела «Проверка»:
- `MarkdownIt("commonmark", {"html": False, "linkify": False, "maxNesting": 20}).enable("table")`: сырой HTML выводится
  текстом, автоссылок без `<…>` нет;
- `validateLink` пропускает только `http`, `https`, `mailto`, пути от корня (`/…`, но не `//…` и не `/\…`, без пробелов
  и управляющих знаков) и для вложений — `att:N` (FR-402, Д6);
- правило `link_open`: внешней ссылке — `rel="noopener noreferrer"` и `target="_blank"`; `att:N` → адрес файла
  (раздел «Как статья ссылается на вложение»);
- правило `image`: только `att:N` своей статьи → `<img … loading="lazy">`, иначе текст-заглушка;
- выравнивание столбцов таблицы — классом (`kb-al-left|center|right`), не атрибутом `style`: CSP без `unsafe-inline`
  запрещает встроенные стили (F1 Ф6);
- таблица и блок кода оборачиваются в `<div class="kb-scroll">` с `overflow-x: auto` (NFR-406, Д7);
- затем `nh3.clean` с белым списком тегов и атрибутов, `url_schemes={http, https, mailto}`, `link_rel=None` (иначе nh3
  запрещает свой `rel` — F1 Ф5) и фильтром атрибутов, который второй раз проверяет `href` и `src` (адреса вложений —
  только `^/kb/<id статьи>/(images|files)/\d+/$`; прочие `href` — только `http`, `https`, `mailto` и пути от корня, но
  не `//` и не `/\`; `src` — только адрес картинки этой статьи) и `class` (только `kb-*`). Две линии защиты страхуют одна
  другую.

`plain` — текст из токенов того же разбора (текст, код, подписи картинок; без адресов ссылок), обрезанный до 100 000
знаков (F1 Ф9; FR-443). Заголовок в `plain` не входит: у него свой вес в векторе.

**Где выполняется рендер.** Готовые `html` и `plain` считаются при сохранении и хранятся в статье и версии; показ статьи,
версии и истории рендер не вызывает. Обычная статья рендерится за десятки миллисекунд, а патологический текст на
200 000 знаков — до 5,4 с (F1 Ф7). Представления предпросмотра и сохранения — обычные синхронные, как всё в портале
(решение плана): под ASGI Django выполняет каждый запрос в своём потоке (`ThreadSensitiveContext`), поэтому долгий рендер
задерживает только свой запрос; вынос рендера в другой поток ничего не дал бы — `markdown-it-py` держит GIL.
Предпросмотр (FR-403) — POST по нажатию на вкладку «Предпросмотр», а не при каждом вводе (F1 Ф10);
`hx-sync="this:replace"` отменяет незавершённый запрос; одновременно у сотрудника идёт не больше одного предпросмотра:
замок Valkey `kb:preview:<user_id>` ставится на время рендера с пределом 10 с и снимается в `finally` сразу после ответа;
второй одновременный запрос получает «Предпросмотр уже готовится». NFR-403 (≤ 1 с на 200 000 знаков) проверяется на
обычном тексте такого объёма (F1: 0,73 с). Решение плана: для патологических входов (например, 200 000 открывающих
скобок — 5,4 с) срок не обещается; защита — предел текста, `maxNesting`, замок на сотрудника и готовый HTML при показе
(раздел «Риски»; отмечено для владельца).

Комментарии (FR-425) не рендерятся: текст экранируется шаблоном и выводится с сохранением переносов строк (`linebreaksbr`
после экранирования), ссылки остаются текстом.

### Создание, сохранение и публикация (FR-401, FR-404, FR-408, FR-410, FR-413, FR-447)

Все записи — служба `articles` в транзакции с `select_for_update` строки статьи; представления только разбирают форму.

- **Создание** (`create`): право `knowledge.edit` или `knowledge.manage`; первая кнопка «Сохранить черновик» создаёт
  статью в состоянии `draft` и версию 1 одной транзакцией; журнал «создание статьи» (FR-438). Адрес статьи — `/kb/<id>/`
  по номеру строки (FR-404); заголовок и рубрика в адрес не входят. До первого сохранения у формы нет номера статьи,
  поэтому кнопки «Вложить» и «Картинка» неактивны с подсказкой «Сохраните черновик» (FR-422, Д20).
- **Проверки формы**: заголовок 1–200 знаков; текст до 200 000; рубрика существует; теги — раздел «Рубрики, теги, главная»;
  комментарий к правке до 200. Ошибки — у полей, введённое остаётся в форме.
- **Сохранение** (`save(user, article_id, base_version, form, confirm_pdn)`; `base_version` и `confirm_pdn` — скрытые поля
  форм правки и публикации), по порядку под замком строки; отказы на запрос HTMX — ответ 200 с формой и сообщением (ПД2):
  1. статья в корзине — отказ «Статья удалена», текст формы остаётся (FR-413, Д3);
  2. нет права править: черновик — автор с правом `knowledge.edit` или управляющий; опубликованная — любой с
     `knowledge.edit` (FR-407);
  3. выбранной рубрики больше нет — отказ у поля рубрики (Д3); строка рубрики берётся `select_for_update`, чтобы удаление
     рубрики не успело между проверкой и записью;
  4. `article.version_no != base_version` — отказ «Статью уже изменил Имя Фамилия в ЧЧ:ММ» со ссылкой на сравнение
     версий `base_version` и текущей; введённый текст остаётся, скрытое поле формы получает текущий номер, поэтому
     повторное сохранение после просмотра проходит (FR-413);
  5. заголовок, текст, рубрика и набор тегов совпадают с текущими — «Изменений нет», версии нет (FR-410);
  6. опубликованная статья и найдены похожие на ПДн строки без `confirm_pdn` — предупреждение (раздел «Защита от ПДн»);
  7. иначе — новая версия `version_no + 1` (снимок полей, `html`, имя рубрики, теги), поля статьи, `updated_by/at`,
     векторы поиска, если статья опубликована (FR-447); событие `knowledge.article_changed` после фиксации — только для
     опубликованной статьи (черновики никого не уведомляют, FR-435).
- **Публикация** (`publish`) — кнопка «Опубликовать» в форме правки или на странице черновика: автор с правом
  `knowledge.edit` или управляющий (FR-408). Текст формы сохраняется по шагам 1–5; если он изменён — новая версия и
  публикация, если нет — публикация без версии (Д4). Перед публикацией — проверка ПДн (шаг 6 действует и для черновика).
  Состояние `published`, `published_at` — время первой публикации; `updated_at` и `updated_by` — время и кто опубликовал
  (и при публикации без версии: иначе давний черновик не попал бы в «Новые и изменённые», сценарий 1 п. 6); векторы
  поиска, журнал «публикация», событие
  `knowledge.article_published`. Обратного перехода в черновик нет (FR-408): в интерфейсе такой кнопки нет, служба
  такого действия не имеет.

Сравнение «изменилось ли» — по значениям формы после приведения (теги — отсортированный набор строчных, текст —
с переводами строк `\n`), чтобы перевод строк браузера `\r\n` не давал ложной версии.

### История, сравнение, восстановление, удаление версии (FR-411, FR-412, FR-414, FR-449)

- **Видимость.** История и версии видны тем, кто видит статью (раздел «Права и видимость»), со всеми версиями,
  включая период черновика (FR-411, Д5). У статьи в корзине история видна только управляющему.
- **История** `/kb/<id>/history/`: версии по номеру вниз (номер, автор с пометкой «уволен», время, комментарий), флажки,
  «Сравнить выбранные версии» — GET `/kb/<id>/compare/?v=N&v=M` (форма с флажками `v`; ровно две версии, иначе — подсказка
  «Отметьте две версии», в том числе при одной или четырёх; старший номер — «стало»).
- **Сравнение** — `diff.compare(old, new)`: заголовок, рубрика (по снимку `rubric_name`) и теги — отдельными строками
  «было / стало»; текст — построчно `SequenceMatcher(None, a, b, autojunk=True).get_opcodes()` (F1 Ф8: свой вывод быстр,
  `HtmlDiff` на крупной правке не завершается). Удалённая строка — `<div class="kb-diff-del">− <del>…</del></div>`,
  добавленная — `kb-diff-add` с «+»; текст экранируется. Неизменённые участки сворачиваются до 3 строк контекста с
  кнопкой «Показать N строк» (раскрытие без запроса — скрытые строки уже в разметке, `<details>`). Если изменённых строк
  больше 2 000, показываются первые 2 000 и строка «Ещё N изменений не показано»: это держит ответ в пределах NFR-402 на
  крайних правках.
- **Просмотр версии** `/kb/<id>/versions/<N>/`: готовый `html` версии, заголовок, рубрика, теги; кнопки «Восстановить
  эту версию» (`can_change`, статья не в корзине, версия не текущая) и «Удалить версию» (управляющий, версия не
  текущая).
- **Восстановление** (`versions.restore`): под замком строки — та же цепочка, что у сохранения (шаги 1, 2, 5–7), с
  полями версии; рубрика версии удалена (`rubric` пусто) — статья остаётся в текущей рубрике (FR-412); комментарий
  «Восстановлено из версии N». У опубликованной статьи восстановление — это сохранение, поэтому проверка ПДн действует и
  здесь (решение плана, расширение FR-431: возврат версии с вычищенными данными вернул бы их, предупреждение уместно).
  Прежние версии не меняются.
- **Удаление версии** (`versions.delete`): только управляющий; текущую (`number == version_no`) удалить нельзя —
  отказ; строка версии удаляется, номера остальных не меняются; журнал «удаление версии статьи» (номер и заголовок
  статьи, номер версии, FR-438). Ссылка на удалённую версию даёт ответ несуществующего. Сравнение, в котором одна из
  версий удалена, — подсказка «Версия удалена».

### Корзина и ночная очистка (FR-415…FR-417, NFR-410)

- **В корзину** (`trash`, управляющий, с подтверждением): `state_before_trash = state`, `state = trash`, `deleted_at`,
  `deleted_by`, векторы поиска — пусто (FR-447); журнал «удаление в корзину». Уведомлений нет (FR-435).
- **Скрытие.** Статья в корзине выпадает из главной, рубрик, страниц тегов, «Новых и изменённых», поиска и выбора для
  привязки, потому что все эти запросы берут только `published` (и `draft` для своих списков). Комментарии, вложения и
  связи с заявками остаются строками, но их показ и выдача проверяют состояние статьи (Д13).
- **По старой ссылке** `/kb/<id>/` и любым адресам страниц статьи (история, версии, правка): управляющему — статья с
  пометкой «в корзине» и кнопками «Вернуть» и «Удалить навсегда»; текст и картинки видны, а комментарии, список вложений
  и связанные заявки скрыты (Д13); остальным — страница «Статья удалена» без заголовка и текста, ответ 410 (FR-409,
  FR-415). Несуществующая статья — обычный ответ 404. Выдача файлов и картинок статьи в корзине не-управляющему — ответ
  несуществующего (это не страница статьи, раздел «Как статья ссылается на вложение»).
- **Корзина** `/kb/trash/` (управляющий): заголовок, рубрика, дата удаления, кто удалил; по дате удаления вниз, по 50,
  «Показать ещё» — `?offset=`.
- **Вернуть** (`restore`): `state = state_before_trash`, очистка полей удаления; опубликованной — векторы заново;
  журнал «возврат». Рубрика существует всегда: `PROTECT` не даёт её удалить (FR-416, FR-419). Уведомлений нет.
- **Удалить навсегда** (`purge(article, actor, by_term=False)`), одна транзакция:
  `comments.delete_for("knowledge.article:<id>")`, строки `ArticleFile` и `StoredFile`, версии и связи (каскад),
  статья; журнал «удаление навсегда» (номер и заголовок; `by_term` — вручную или по сроку). Файлы с диска стираются
  после фиксации (`transaction.on_commit`); отсутствующий файл не ошибка (запись в журнал приложения без имени файла).
  Строки тегов здесь не удаляются (их чистит ночное задание, ниже).
- **Ночная очистка** `knowledge.tasks.purge_trash` — запись в `config/cron.py`: `cron="45 23 * * *"` (02:45 по Москве;
  минута свободна — рядом 23:40 `notify_retention` и 23:50 `purge_orphan_files`), очередь `maintenance`,
    `job_timeout=600`, как очистки срезов 003 и 004 (F4 Ф1, Ф2): номера статей `state = trash` и
  `deleted_at < сейчас − trash_days` по возрастанию номера порциями по 100 (следующая порция — после последнего
  обработанного номера); каждая статья — отдельная транзакция с `select_for_update(skip_locked=True)` и повторной
  проверкой состояния и срока, затем `purge(…, actor=None, by_term=True)`. Сбой одной статьи пишется в журнал приложения
  (номер статьи и класс исключения), обход продолжается; если сбои были, задание после обхода завершается ошибкой.
  Повторный запуск не находит уже удалённых и журнала не пишет; статья, которую успели вернуть, пропускается (NFR-410).
  В конце — теги без единой статьи удаляются под исключительным замком тегов
  (`pg_advisory_xact_lock(hashtextextended('knowledge.tags', 0))`); сохранение статьи с тегами берёт тот же ключ
  разделяемым замком (`pg_advisory_xact_lock_shared`), поэтому тег, который сейчас привязывается, не исчезнет.
- **Срок корзины** — страница `/kb/settings/` (управляющий): 7–365, по умолчанию 90; изменение — журнал «было / стало»
  (FR-417, FR-438).

### Права и видимость (FR-405…FR-409, Д8)

`access.py` — единственное место решений; представления и поставщики поиска зовут только его:
- `can_edit(user)` — право `knowledge.edit` или `knowledge.manage`; `can_manage(user)` — `knowledge.manage`
  (`permissions.has_permission`, кэш прав ядра);
- `visible_articles(user)` — набор, который видит сотрудник: опубликованные; плюс свои черновики, если `can_edit`; плюс
  все черновики, если `can_manage` (в том числе уволенного автора — Д8); статьи в корзине не входят;
- `get_for(user, id)` — статья или исключение: нет или не видна — `Http404`; в корзине — управляющему статья, остальным
  своё исключение `ArticleGone`. Декоратор представлений страниц базы знаний превращает его в
  `render_page(request, "knowledge/gone.html", status=410)` — ответом представления, а не новым обработчиком ошибок (F3
  Ф11); у Django нет `handler410`;
- `can_change(user, article)`, `can_publish(user, article)` — по таблице FR-407.

Все представления — обычные синхронные, `@login_required`, проверка в начале и повторно в службе под замком (кнопка могла
устареть, FR-409). Показ страницы статьи публикует событие ядра `object.viewed` с `object_ref = "knowledge.article:<id>"`
(подписчик `notify.reading.on_object_viewed` уже есть, F3 Ф7): иначе непрочитанное уведомление о статье, открытой не из
колокольчика, навсегда глушило бы следующие склеиваемые уведомления (FR-435).
Пункт меню «База знаний» — `menu_items` с пустыми `permissions` и `visible = lambda user: True` (F3 Ф10, FR-405).
Чтение, комментарии и поиск прав не требуют.

### Рубрики, теги, главная (FR-418…FR-421, FR-437)

- **Рубрики** (`rubrics.py`, управляющий): создать, переименовать, перенести, удалить; страница `/kb/rubrics/` с деревом.
  Все записи дерева — в одной транзакции под замком `pg_advisory_xact_lock(hashtextextended('knowledge.rubrics', 0))`:
  глубина и потомки считаются под ним, поэтому два встречных переноса не дают цикла. Название — 1–100 знаков без пробелов
  по краям. Создание: родитель на третьем уровне — отказ «Не глубже трёх уровней» у поля родителя. Перенос: новый родитель не может быть самой рубрикой или её потомком; глубина нового места плюс высота поддерева ≤ 3;
  «Общее» не переносится под другую рубрику; при переносе `depth` поддерева пересчитывается той же транзакцией (дерево —
  сотни строк, обход в памяти). Удаление: есть подрубрики или статьи (в том числе в корзине) — отказ «Сначала перенесите»;
  «Общее» — отказ (FR-419); подписки на рубрику уходят каскадом (FR-437). Совпадение названия у соседей без учёта
  регистра — отказ у поля (ограничение базы — страховка). Журнал: создание, переименование, перенос (было / стало, путь),
  удаление (FR-438). Порядок — по названию (`Lower(name)`).
- **Теги** (`tags.normalize`): поле через запятую; каждый тег — без пробелов по краям, внутренние пробелы — один, строчные;
  пустые выбрасываются, повторы склеиваются; больше 10 тегов или тег длиннее 40 знаков — отказ у поля (FR-420). Подсказка
  `/kb/tags/suggest/?q=` — до 10 тегов опубликованных статей, начинающихся с введённого (параметр запроса, `istartswith`).
  Страница тега `/kb/tags/?name=<имя>` (имя — параметром запроса: тег может содержать `/`, `?`, `#`) — опубликованные
  статьи с тегом по времени правки, по 20 с «Показать ещё» (`&offset=`); тег без опубликованных статей — 404.
- **Главная** `/kb/`: дерево рубрик с числом опубликованных статей рубрики вместе с подрубриками (один запрос с
  группировкой по рубрике и сложение в памяти); «Новые и изменённые» — 10 опубликованных по `updated_at` вниз; «Мои
  черновики» (если `can_edit`); управляющему — «Черновики» всех и ссылка «Корзина»; кнопка «Новая статья» (если
  `can_edit`). Пустая база — пояснение со ссылкой «Новая статья» по праву (FR-421).
- **Страница рубрики** `/kb/rubrics/<id>/`: опубликованные статьи рубрики и подрубрик по времени правки, по 20 с «Показать
  ещё» (`?offset=`); кнопка «Подписаться / Отписаться» (`subscriptions.toggle`, сам сотрудник, FR-437).

### Вложения и картинки; проверки файлов в ядре (FR-422…FR-424, NFR-404, NFR-411)

**Перенос в ядро** (FR-424, решение плана). Новый модуль `core/services/uploads.py` берёт из
`servicedesk/services/attachments.py` части без моделей сервис-деска (F3 Ф3):
- `is_executable(name, data)`, `is_encrypted_archive(data)`, список расширений;
- `reject_reason(name, data, size, max_file) -> "too_big" | "executable" | "encrypted" | ""`;
- `detect_image(data) -> "png" | "jpeg" | "gif" | "webp" | ""` (Pillow, `Image.open(…).verify()` с перехватом
  `Image.DecompressionBombError` и пределом числа точек, как у фото в `files._check`; формат — по содержимому, не по
  расширению и не по типу из браузера — F3 Ф3);
- `store(data, name, purpose) -> StoredFile` — строка (`owner` пусто, как у вложений заявок), файл в `incoming/<id>`
  (`files.attachment_path`), `enqueue_scan` после фиксации;
- `move(stored, status, signature="") -> list` — перенос между `incoming/`, `attachments/` и `quarantine/` после проверки;
  возвращает прежний путь для стирания после фиксации (как `_move` в `servicedesk`; обработчики `file_purposes` отдают
  этот список ядру).

`servicedesk` оставляет свои пределы (10 файлов, 50 МБ на письмо), коды `Attachment.Rejected` и `ServiceDeskError`:
`reason_of` переводит коды ядра в свои, а прежние имена (`attachments.is_executable` и другие) остаются реэкспортом.
Поэтому тесты среза 003 проходят без правок; это проверяет полный прогон (раздел «Проверка»).

**Файлы статьи** (`knowledge/services/files.py`):
- `attach(user, article_id, upload)`: под замком статьи проверяет, что статья сохранена и не в корзине, у сотрудника есть
  право её править (FR-407), файлов меньше 20, размер ≤ 20 МБ и `reject_reason` пуст (FR-422). Затем `uploads.store(…,
  purpose="knowledge")` и строка `ArticleFile` с `image_format` по содержимому. Отказы — у кнопки «Вложить» ответом 200 с
  сообщением; тексты новые, в стиле среза 003 (решение плана): «Файл больше 20 МБ», «Исполняемые файлы не принимаются»,
  «Архивы с паролем не принимаются», «У статьи уже 20 файлов».
- `remove(user, file_id)`: то же право; строка `ArticleFile` и `StoredFile` удаляются, файл с диска — после фиксации.
  Разметка `att:N` в тексте остаётся и показывает заглушку «вложение удалено» (сценарий 5 п. 10). Журнал не пишется
  (FR-438 удаление вложения не называет).
- `FilePurpose("knowledge", still_waiting, clean, found)` в точке `file_purposes`: `still_waiting` — строка `ArticleFile`
  есть и файл `pending`; `clean(stored)` — `uploads.move` в `attachments/`; `found(stored, signature)` — как у вложений
  заявок: сигнатура `Heuristics.Encrypted.*` — отказ «архив с паролем» (строки `ArticleFile` и `StoredFile` удаляются),
  иначе `uploads.move` в карантин. Основная проверка архива с паролем — при загрузке по содержимому, поэтому автор видит
  причину сразу (сценарий 5 п. 5). Без этой записи файл остался бы «проверяется» навсегда (F3 Ф2). Повторы при
  недоступном ClamAV (до 24 попыток, до суток) и часовой подбор зависших — общие механизмы ядра; сбой антивируса не
  трогает статью (NFR-411). Карантин старше 30 суток стирает прежнее задание ядра `purge_quarantine`: оно берёт путь
  через `files.attachment_path`, и файлы статей лежат по тем же путям.
- Список вложений под формой правки и на странице статьи: имя, размер, состояние («проверяется» — без ссылки; «в
  карантине» — без ссылки); кнопки «Картинка» (для `image_format`) и «Вставить ссылку» вставляют `![имя](att:N)` или
  `[имя](att:N)` в позицию курсора (`kb-editor.js`).
- Выдача — раздел «Как статья ссылается на вложение»; общий ответ `X-Accel-Redirect` — `core/services/file_response.py`
  через прежний `location /protected/attachments/`: заголовки `nosniff`, `Cache-Control: no-store`; у скачивания — имя в
  `filename*=UTF-8''…` и `attachment`, у показа картинки — без `Content-Disposition`, с типом из `image_format` (F3 Ф4;
  что nginx сохраняет тип ответа Django при `X-Accel-Redirect`, проверяет e2e — раздел «Риски»).

### Комментарии (FR-425, FR-426)

Служба ядра `core/services/comments.py`: `add(author, object_ref, text)` (текст без пробелов по краям, 1–4000 знаков),
`list_for(object_ref)` (по `created_at`, `id`; автор и фото одним запросом), `delete(comment)`,
`delete_for(object_ref)`. Ядро не знает, что такое статья: можно ли комментировать и видеть, решает модуль.

`knowledge`: блок комментариев — только под опубликованной статьёй; под черновиком и статьёй в корзине его нет, а POST к
ним — ответ несуществующего (FR-425, Д13). Оставить может любой сотрудник; «Удалить» — автор комментария или управляющий.
Удаление чужого — журнал «удаление чужого комментария» (номер и заголовок статьи, без текста, FR-438). После фиксации —
событие `knowledge.comment_added`. Автор подписан `{% person_name %}`: ФИО, у уволенного — «(уволен)» (Д8). Новый
комментарий добавляется в конец списка ответом HTMX, без перезагрузки страницы.

### Связь с заявками и карточка заявки (FR-427, FR-429, FR-430, FR-432, FR-433)

**Публичная служба `servicedesk`** (`services/public.py`) — единственное, что `knowledge` вызывает у сервис-деска:
- `ticket_brief(user, number) -> TicketBrief | None` — номер, тема, состояние, признак «закрыта с решением» и текст решения
  (`Ticket.resolution`), если заявку видит `user` (`access.visible_tickets`), иначе `None`;
- `briefs(user, numbers) -> dict[int, TicketBrief]` — то же для списка, одним запросом.

`knowledge` вызывает их, только если приложение `servicedesk` установлено (`apps.is_installed`); без него разделы и
кнопки про заявки не показываются.

**Встраивание в карточку** (FR-432, решение плана). `servicedesk` в `ticket_card._context` собирает
`TicketRef(number, closed, has_resolution)` и для каждой записи точки `ticket_card_parts` вызывает
`render(request, ref)`: `section` — на месте после блока «Вложения» (независимо от того, есть ли у заявки вложения);
`closed_action` — рядом с кнопкой «Открыть заново»; `comment_tool` — под полем формы «Внутренний комментарий». Если
запись бросает исключение, оно пишется в журнал приложения, а карточка рисуется без этой части. Нет записей (модуль
выключен или не установлен) — нет частей; карточка и лента работают как в срезе 003 (FR-433). `servicedesk` не
импортирует `knowledge`.

**Записи `knowledge`** в точке:
- `section` «Статьи» (FR-429): связанные статьи: опубликованные — всем, кто видит заявку (карточку уже проверил
  `servicedesk`); черновики — автору и управляющему; статьи в корзине — никому. Рядом — кто и когда привязал (Д22). Кнопки
  «Привязать статью» (поле с подсказкой по заголовкам опубликованных статей — `/kb/pick/?q=`, до 10, тот же поиск, что у
  группы «Статьи») и «Отвязать» — при `can_edit`. POST `/kb/links/` (статья должна быть опубликованной, иначе ответ
  несуществующего) и `/kb/links/<id>/delete/` повторно проверяют `ticket_brief(user, number)` и право; журнал не пишется
  (FR-438).
- `closed_action` «Статья из решения» (FR-427): при `ref.closed and ref.has_resolution` и `can_edit`. POST
  `/kb/from-ticket/<number>/`: `ticket_brief` (нет или не видна — 404; не закрыта с решением — отказ). Проверка и
  создание идут одной транзакцией под `pg_advisory_xact_lock(hashtextextended('knowledge.from_ticket:<номер>:<сотрудник>',
  0))`: двойное нажатие не создаёт два черновика (Д12). Если есть черновик этого сотрудника, связанный с заявкой и
  созданный из решения (`TicketLink.from_resolution`, `Article.from_ticket`), — открывается он с сообщением «Черновик по
  этой заявке уже создан». Иначе создаётся черновик: заголовок — `pdn.mask_plain(тема)[:200]`, текст —
  `pdn.mask_resolution(решение)`, рубрика «Общее», связь с `from_resolution=True`, версия 1 с комментарием «Создано из
  заявки #N», журнал «создание статьи». Затем открывается редактор. Данных заявителя, адресов и переписки служба не
  берёт: `TicketBrief` их не содержит.
- `comment_tool` «Ссылка на статью» (FR-430): подсказка `/kb/pick/` (её может вызвать любой вошедший: опубликованные
  статьи читают все, права «Редактирование» FR-430 не требует); выбор вставляет текст «Заголовок: <полный адрес статьи>»
  (`request.build_absolute_uri("/kb/<id>/")`) в поле комментария (`static/js/kb-link.js`, подключается в
  `_assets.html`). Лента выводит комментарий простым текстом без разметки, поэтому вставляется адрес, а не Markdown; запись
  ленты остаётся записью ленты.

**Связанные заявки на странице статьи** (FR-429): номера из `TicketLink`, затем `briefs(user, numbers)` — показываются
только видимые смотрящему («#N Тема»). У статьи в корзине список скрыт и у управляющего (Д13). Связь не трогает
обезличивание заявки: оно не удаляет заявку и не стирает тему и номер (F3 Ф6). Связь удаляется только удалением статьи
навсегда (каскад).

### Защита от ПДн (FR-428, FR-431)

`pdn.py` — шаблоны (решение плана, FR-428 «точные шаблоны определяет план»):
- почта: `(?<![\w.+-])[\w.+-]+@[\w-]+(?:\.[\w-]+)*\.[^\W\d_]{2,}(?![\w-])` — буквы любого алфавита, поэтому находит и
  адреса в зоне `.рф`;
- телефон: `(?<![\d+])(?:\+7|8)[ \t\-()]*(?:\d[ \t\-()]*){9}\d(?!\d)` — `+7` или `8` и ещё 10 цифр, между ними пробелы,
  табуляция, дефисы и скобки, без перевода строки (Д11; точки не допускаются).

Две функции — для двух разных случаев:
- `find(title, text) -> list[str]` — предупреждение по статье (Markdown). Обход токенов markdown-it, как у `plain` (F1
  Ф9), с пропуском `code_inline`, `fence` и `code_block`; между токенами, блоками, ячейками таблицы и строками ставится
  перевод строки (иначе соседние слова склеиваются с адресом: «Контактivan@example.ru»); к склейке добавляются адреса
  ссылок `mailto:…` (адрес виден в HTML). Второй реализации грамматики Markdown нет. Заголовок статьи — простой текст,
  проверяется целиком. Найденное — без повторов, до 20 строк. Используется перед публикацией, при сохранении
  опубликованной статьи и при восстановлении версии в ней. Если что-то найдено и в форме нет `confirm_pdn`, ответ —
  фрагмент предупреждения со списком и кнопками «Вернуться к правке» и «Опубликовать всё равно» (у опубликованной —
  «Сохранить всё равно»). Вторая кнопка отправляет ту же форму с `confirm_pdn=1` (FR-431). В журнал найденное не пишется.
- `mask_plain(text)` и `mask_resolution(text)` — «Статья из решения» (FR-428): тема и решение заявки — простой текст, не
  Markdown. Перевод строк `\r\n` приводится к `\n`, затем шаблоны заменяются через `re.sub` прямо в исходном тексте.
  `mask_plain` (тема) скрывает всё найденное. `mask_resolution` (решение — будущий текст статьи) пропускает строки внутри
  ограждений ```` ``` ```` и `~~~` и участки в обратных кавычках на остальных строках (построчный проход; отступ в 4
  пробела кодом не считается — это строже правила, а не мягче).

Ложные срабатывания допустимы — это только предупреждение. Номера из 10 цифр без `+7` или `8`, короткие внутренние номера
и ФИО шаблоны не ловят (FR-428).

### Уведомления базы знаний (FR-434…FR-437)

**Правка `notify`** (FR-435, решение плана). У записи вида в ядре — поле `coalesce` (по умолчанию ложь).
`dispatch.create` для вида с `coalesce` до создания первой записи — одним проходом перед циклом черновиков, по возрастанию
ключа — берёт транзакционные замки `pg_advisory_xact_lock(hashtextextended('<user_id>:<код вида>:<object_ref>', 0))`
(устойчивый хэш на стороне базы, не `hash()` Python, который в каждом процессе свой). Затем в цикле, если у получателя
есть `Notification` того же вида с тем же `object_ref` и `read_at` пусто, черновик пропускается: нет записи, доставок и
всплывающего окна. Порядок записей и доставок остаётся порядком черновиков; `held_users` для `plan_digest` обходятся по
возрастанию `user_id`. Замки нужны потому, что два события об одной статье могут обрабатываться одновременно в двух
процессах: записи создаёт тот процесс, что опубликовал событие (web или рабочий RQ, PLAN-004), и замок живёт до конца
его транзакции. Единый порядок взятия исключает взаимную блокировку, при которой шина только записала бы ошибку в журнал
и уведомления события пропали бы. Частичный уникальный индекс не подходит: условие «вид склеивается» живёт в коде, а не
в таблице. Виды сервис-деска и безопасности `coalesce` не ставят, их поведение не меняется (SPEC-004 FR-306 для них в
силе). «Прочитано» по статье ставит событие `object.viewed` при показе статьи (раздел «Права и видимость»).

**Виды** (`knowledge/notify_kinds.py`, точка `notification_kinds`; каналы по умолчанию — «На портале» и «Почта», FR-434):

| Вид | Код | События | Получатель | Текст на портале и в письме / во внешних каналах |

| Новый комментарий к моей статье | `knowledge.comment_on_my_article` | `knowledge.comment_added` | автор статьи, если не он автор комментария | «Новый комментарий к вашей статье «Заголовок»» / «Новый комментарий к вашей статье» |
| Мою статью изменили | `knowledge.my_article_changed` | `knowledge.article_changed` | автор статьи, если сохранил другой | «Вашу статью «Заголовок» изменил Имя Фамилия» / «Вашу статью изменили» |

- `coalesce=True`; `object_ref = "knowledge.article:<id>"`; ссылка — `/kb/<id>/` (у комментария — с якорем
  `#comments`).

  рубрики и имя того, кто изменил статью, в нём обрезаются до 100 знаков с «…», как тема заявки в срезе 004 (ФИО в ядре —
  до 255 знаков, без обрезки текст вышел бы за 300 и запись не создалась бы; решение плана).
- «Одно событие — одно уведомление» (Д14) обеспечивают правила `build` без правки `notify`. На `article_changed` автор

- `available(user)` для строк таблицы «Мои уведомления» (Д15): для «Нового комментария» и «Мою статью изменили» — у

- Возврат из корзины, удаление и черновики событий не публикуют (FR-435).

**Подписка** (FR-437): `RubricSubscription`; кнопка на странице рубрики. Подписку видит и меняет только сам сотрудник.

### Сквозной поиск (FR-439…FR-447, NFR-401)

**Разбор** — `search/parse.py: parse(q) -> ParsedQuery(words, number, raw, hint)` (свой; разбор списка заявок не
меняется — F2 Ф3):
1. пробелы по краям убираются; длина больше 200 — `hint="long"` («Запрос не длиннее 200 знаков», поиск не идёт; поле
   ввода имеет `maxlength="200"`); длина меньше 2 — `hint="short"`;
2. слова — `\w+` в нижнем регистре; число `#\d+` (вся строка) или `\d{2,}` (вся строка), не больше 2 147 483 647 (как в
   `servicedesk.search`), — `number`;
3. слова короче 2 знаков отбрасываются; остаются первые 8;
4. нет слов и нет `number` — `hint="short"` («5», «а б» — подсказка; «#5», «15» — заявка по номеру; Д17);
5. `raw = " & ".join(f"{w}:*")` — уходит параметром в `to_tsquery('russian', %s)` (`SearchQuery(…, search_type="raw")`).
   Служебных знаков tsquery в словах `\w+` нет (F2 Ф4); стоп-слово выпадает само (F2 Ф3); «ё» и «е» сводит конфигурация
   `russian` (F2 Ф4). Теги, подсказка тегов, названия рубрик и выбор статьи для привязки тоже идут в запросы только
   параметрами ORM (NFR-408).

**Сборка** — `search/services.py`: для каждой записи `search_providers` по `order`, если `available(user)`, вызывает
`search(user, parsed, limit, offset)`; на странице результатов число группы даёт `count(user, parsed)` отдельным
запросом. Пустые группы не показываются (FR-440). Ошибка одного поставщика пишется в
журнал приложения — только ключ группы и класс исключения (текст ошибки базы и трассировка могут содержать фрагмент
запроса, поэтому `log.exception` не используется); группа не показывается, остальные работают. Строка запроса нигде не
сохраняется и не логируется: у gunicorn журнала доступа нет, журнал nginx пишет путь без параметров (`$uri`,
`deploy/nginx.conf`), `django.request` пишет только путь (FR-446; проверка — тест с меткой-словом в журнале приложения).

**Адреса** (`search/views.py`, `@login_required`, GET):
- `/search/popup/?q=` — фрагмент: по 5 строк в группе, без подсчёта, внизу «Все результаты»; на короткий
  запрос выдача пуста и подсказки не показывает (Enter ведёт на страницу результатов, сценарий 10 п. 2);
- `/search/?q=` — страница: по 20 строк в группе (FR-442); число найденного у каждой группы подгружается отдельным
  запросом `/search/count/?q=&group=<key>` (HTMX, `hx-trigger="load"`) после строк, поэтому страница не ждёт счёта —
  решение плана (счёт заявок с правами до 1001 стоит p95 0,57 с, F2 Ф9);
- `/search/more/?q=&group=<key>&offset=N` — следующие 20 строк группы (кнопка «Показать ещё» дописывает их HTMX); у
  заявок смещение считается по основному запросу без строки заявки по номеру.
Короткий или длинный запрос на странице результатов — подсказка, поставщики не вызываются. Пусто — «Ничего не найдено».

**Строка поиска** (FR-439, FR-440): `TopBarItem(key="search", order=5, template="search/_bar.html", context=lambda
request: {})` — слева от колокольчика (у него `order=10`). `<input type="search" name="q" maxlength="200"
hx-get="/search/popup/" hx-trigger="input changed delay:300ms, search" hx-sync="this:replace">` (F2).
`static/js/search.js`: стрелки, Enter (выбранная строка или страница результатов), Esc (закрыть выдачу и
`stopPropagation`: обработчик на поле срабатывает раньше общего обработчика `htmx-glue.js` на `document` в фазе
всплытия, поэтому слайдер не закрывается — F2), закрытие по щелчку вне. Порог 2 знака проверяют и браузер, и сервер.

**Поставщики:**

**Статьи — два шага** (решение плана). Векторы: `search_head = setweight(to_tsvector('russian', title), 'A') ||
setweight(to_tsvector('russian', теги через пробел), 'B')`; `search_full = search_head || setweight(to_tsvector('russian',
plain), 'C')`. Шаг 1 находит и ранжирует совпадения в заголовке и тегах по малому вектору; шаг 2 добирает статьи, где слова
есть только в тексте, по полному вектору с потолком 300 кандидатов и порядком по времени правки. Совпадения в заголовке
всегда выше (FR-443). Замеры F2 Ф8 (синтетика, частые слова, p95): ранг по полному вектору — 0,6–0,94 с; отбор по полному
с рангом по малому — 0,62–0,67 с; отбор и ранг по малому — 4–13 мс; потолок 300 кандидатов — 28–53 мс. Цена — порядок
внутри шага 2 не по точности совпадения, а по новизне, и при очень частом слове в шаг 2 попадают не все совпадения (до
300). Замер на `fill_articles.py` с настоящими словами — задача Этапа 1. Векторы считает служба `articles` при публикации,
сохранении опубликованной и возврате опубликованной; в остальных состояниях векторы пусты (FR-447). Выдача на страницу
и «Показать ещё» идут по склейке шагов (сначала шаг 1, затем шаг 2).

**Сотрудники.** Вектор строится в запросе, без хранимого столбца (решение плана): полей шесть, записей сотен, а мест, где
меняются поля и членство, больше десяти в двух приложениях (F2 Ф13). Хранимый столбец потребовал бы правок во всех них
или триггера. Состав вектора: ФИО, должность, почта как есть и с заменой `@ . _ / -` на пробелы (почта находится целиком
и по частям — Д10), телефоны как есть и только цифрами, внутренний телефон, место работы. Каждое слово ищется отдельным
условием, поэтому стоп-слово дало бы пустой запрос и обнулило выдачу: слова, у которых
`numnode(to_tsquery('russian', слово:*)) = 0`, отбрасываются одним запросом до поиска, как в остальных группах они
выпадают сами. Названия подразделений берутся из записи `staff_directory` модуля `org` (`_unit_search`, подстрока — как
в справочнике, FR-130); слово перед вызовом приводится так, как ждёт эта запись (нижний регистр, «ё» → «е»). Без `org` —
только поля ядра. Замер на 300 и 3 000 сотрудниках — задача Этапа 1 (раздел «Риски»).

Решение плана: справочник ищет всю строку подстрокой по полям (F2 Ф5), а сквозной поиск — каждое слово по началу слова
(FR-443, Д18). Поля и отбор те же, что в справочнике, а способ совпадения — как у остальных групп. Следствие: часть номера
телефона из середины («345» в «+7 912 345-67-89») может не найтись, хотя справочник её находит. Начало номера, номер
цифрами целиком и с `+7` или `8` находятся (токен «только цифры»).

Строки (FR-441): заявка — «#N Тема», состояние, очередь, адрес как в списке заявок; статья — заголовок, рубрика,
`/kb/<id>/`; сотрудник — ФИО, должность, подразделение (колонка `unit` записи `staff_directory`, шаблон
`org/_staff_unit_cell.html`), фото (`files.photo_url(user, 96)`), карточка `/staff/<id>/`; подразделение — название,
путь (названия предков через « / »; `Unit.path` хранит цепочку номеров, названия предков собираются одним запросом на
страницу), `/structure/<id>/`.

## Контракты

Формы — POST с CSRF. Запрос HTMX получает фрагмент, обычный — полную страницу. Отказ с сообщением на запрос HTMX — код
200 с фрагментом ошибки: HTMX не вставляет ответы 4xx (урок PLAN-003); так же отвечают POST-действия над статьёй, которая
тем временем ушла в корзину («Статья удалена»). Нет права на действие — 403. Недоступная статья (чужой черновик), версия,
вложение, связь — 404, как несуществующие (FR-409). Страница статьи в корзине для не-управляющего — 410 «Статья удалена»
(FR-415); выдача её файлов и картинок — 404. Все адреса — только для вошедших (`@login_required`); номера в путях — с
конвертером `<int:…>`, поэтому `/kb/new/`, `/kb/trash/`, `/kb/settings/`, `/kb/pick/` не путаются с `/kb/<id>/`.

| Путь | Метод | Кто | Что делает | FR |
|---|---|---|---|---|

## Интеграции

Новых внешних систем нет. ClamAV — прежний адаптер ядра и очередь `files` (FR-424). Сеть общества и интернет срезу не
нужны: рендер, поиск и проверки работают на сервере портала. Внешние картинки в статьях не загружаются (FR-402), поэтому
адреса сотрудников не уходят третьим сторонам при чтении статьи.

**Персональные данные.** Во внешние каналы уведомлений — только событие и ссылка (FR-436). Поисковые запросы не
хранятся ни в базе, ни в журнале событий, ни в журнале приложения (FR-446); журнал nginx пишет путь без строки запроса
(`$uri`). Журнал событий хранит номер и заголовок статьи без текста (FR-438). Тексты статей, версий и комментариев хранятся
до удаления статьи навсегда (FR-448); вычищенные персональные данные из прежних версий убирает управляющий (FR-449).

  восстанавливает права ролей (F3 Ф10). Команды приёмки (F4 Ф9): `e2e_kb_trash_shift --days N` (сдвигает `deleted_at`) и
  `e2e_kb_purge` (выполняет ночную очистку сразу). Вложения проверяются через ClamAV стенда (EICAR — карантин; замер
«проверяется → чистый» не дольше 1 минуты, NFR-404); картинка статьи показывается через настоящий nginx
(`naturalWidth > 0`, тип ответа `image/png`). Пауза
  ввода 300 ± 100 мс — замер времени от последнего ввода до запроса в браузере. Ширина 360 px — главная, статья с широкой
  таблицей и длинным кодом, форма с предпросмотром, история, сравнение, корзина, строка поиска и страница результатов
  (NFR-406).
- **Ручной проход владельца** — критерий «статья за 5 минут» с замером.
- **Скорость** (NFR-401, NFR-402, NFR-412) — locust по модели нагрузки владельца, как T-3304 и T-4304: 100 вошедших,
  вход по одному в секунду, пауза 5–15 с; данные — 110 000 заявок (`fill_tickets.py`) и 5 000 статей
  (`fill_articles.py`, тексты из словаря настоящих слов, теги, рубрики). Новый класс `KnowledgeUser`: главная, рубрика,
  статья, история, сравнение, комментарий, всплывающая выдача, страница результатов и подсчёт групп на частых, редких и
  смешанных словах; часть пользователей — учётки без прав базы знаний и без «Все заявки», чтобы замер учёл фильтры
  видимости (прежние нагрузочные учётки — администраторы, F4 Ф6).
  Страницы срезов 001–004 — из прежнего набора. p95 страниц ≤ 500 мс, поиска ≤ 1 с, ошибок нет.
- **Резервная копия** (NFR-413): копия и восстановление на стенде; статья с картинкой и вложением после восстановления
  показывается и скачивается.

**Критерии успеха спеки и чем они проверяются.**

| Критерий | Проверка |
|---|---|
| статья с кнопками и предпросмотром за 5 минут | ручной проход владельца с замером |
| «Статья из решения» без данных заявителя, почта и телефоны — «[скрыто]» | серверные тесты `from-ticket` и `pdn`; e2e сценария 4 |
| 0 скриптов и внешних картинок в статьях и комментариях | серверный набор проб рендера; e2e: статья с пробами, в браузере нет выполнения (флаг на `window`) и запросов на чужие адреса |
| каждое сохранение — версия, восстановление добавляет версию | серверные тесты статьи и истории; e2e сценария 3 |
| 0 затёртых чужих правок | серверный тест гонки; e2e сценария 3 двумя контекстами |
| 0 черновиков и корзины в поиске, привязке, рубриках | серверные тесты корзины и поиска; e2e сценариев 8 и 10 |
| 0 уведомлений тем, кто не видит статью; 0 заголовков во внешних каналах | серверные тесты получателей и текстов; e2e сценария 9 (Telegram учебной службы) |
| одна строка находит статью, заявку, коллегу, подразделение; ≤ 1 с | e2e сценария 10; locust |
| 0 невидимых заявок в выдаче | серверный тест прав группы «Заявки»; e2e сценария 10 |
| 0 чужих черновиков и корзины у невправе | серверная таблица прав; e2e сценария 11 |
| ≤ 500 мс при 100 пользователях; 360 px | locust; e2e на узкой ширине |
| удаление, возврат, срок корзины | серверные тесты корзины; e2e сценария 8 с `e2e_kb_trash_shift` и `e2e_kb_purge` |
| права и роли без кода | e2e сценария 11 (выдача права роли в интерфейсе) |
| одно уведомление на событие; свои виды в «Мои уведомления» | серверные тесты `coalesce` и Д14, `available`; e2e сценария 9 |
| удаление версии с ПДн, текущую нельзя | серверный тест; e2e сценария 3 |
| правка при удалённой статье или рубрике не теряет текст | серверный тест; e2e сценария 3 |
| нагрузочный прогон; файлы в копии | locust; восстановление на стенде |
| модуль «База знаний» выключен — остальное работает (сценарий 10 п. 16) | серверный тест без приложения `knowledge` (стенд один, e2e это не переключает) |

Какой тест закрывает какую FR — в TASKS-005.

## Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Поиск статей на настоящих текстах окажется медленнее замера (данные F2 синтетические) | средняя | два шага: малый вектор (F2 Ф8, 4–13 мс) и потолок 300 кандидатов для текста (28–53 мс); замер на `fill_articles.py` с настоящими словами в Этапе 1; при превышении — потолок кандидатов ниже |
| Страница результатов медленнее 1 с из-за подсчёта заявок (с потолком и видимостью p95 0,57 с, F2 Ф9) | средняя | число подгружается отдельным запросом после строк; locust меряет страницу и подсчёт отдельно; запасной ход — потолок «200+» |
| Патологический Markdown на 200 000 знаков (до 5,4 с рендера) | низкая (пишут сотрудники с правом) | срок NFR-403 для него не обещается (решение плана); рендер занимает только свой запрос, но держит GIL процесса; `maxNesting`; один предпросмотр на сотрудника; показ берёт готовый HTML |
| nginx при `X-Accel-Redirect` заменит тип картинки на `application/octet-stream` (F3 Ф4, не проверено запуском) | низкая (фото сотрудника работает так же, но с другим `default_type`) | e2e «картинка показывается» через настоящий nginx в первой задаче выдачи; запасной ход — отдельный `internal` `location` для картинок статей |
| Перенос проверок вложений в ядро сломает поведение вложений заявок | низкая | реэкспорт прежних имён; тесты среза 003 на вложения без правок — условие готовности задачи |
| Поиск сотрудников без хранимого вектора замедлится при росте справочника | низкая (сотни записей; F2: единицы мс) | замер на 300 и 3 000 сотрудниках в Этапе 1; при превышении 100 мс — хранимый столбец с обновлением в службах ядра |
| Склейка уведомлений (FR-435) отступает от SPEC-004 FR-306 | известно | только для видов с `coalesce`; виды срезов 003–004 не меняются; отмечено в «Что владельцу знать» SPEC-005 |
| Число «найдено» по заявкам — «1000+», а не точное | известно | точный счёт стоит 2,3–2,6 с (F2); подпись «1000+» в выдаче; в отчёте плана для владельца |
| Esc в строке поиска закроет открытый слайдер карточки | средняя | обработчик на поле срабатывает раньше обработчика `document` (фаза всплытия) и вызывает `stopPropagation`; e2e: поиск поверх открытой карточки |
| Уникальность рубрики с выражением `Lower("name")` и `nulls_distinct` поведёт себя иначе на настоящей базе (SQL сгенерирован без базы) | низкая | первая задача модели применяет миграцию на PostgreSQL 17; запасной ход — поле `name_key`, как у `org.Unit` |
| Регулярное выражение телефона даст ложные срабатывания на номерах инвентаря | средняя | это только предупреждение (FR-428); пример в тестах; правило уточняется по жалобам |
| Разметка карточки заявки в тестах среза 003 сверяется целиком | средняя | точка без записей ничего не выводит; если тест упадёт — правка с разрешения владельца (раздел «Проверка») |
