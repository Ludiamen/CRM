# Задачи среза 005

Формат строки: `- [ ] T-NNNN [P] [исполнитель] описание — путь или тест — (FR-NNN)`.
`[P]` — можно делать параллельно с соседними задачами. Исполнитель — haiku / sonnet / opus / человек (по разделу
«Разделение работы между моделями» в docs/sdd-process.md). Задачи собраны из PLAN-005 и SPEC-005 (11 сценариев,
FR-401…449, NFR-401…413). Задач вне плана здесь нет. Решения, которых план не принимал, собраны в разделе «Решения
Opus по задачам» в конце файла.

Как читать и исполнять:
- **Нумерация.** Номера среза 005 четырёхзначные: Этап 1 — T-5001…, Этап 2 — T-5100…, Этап 3 — T-5200…, Этап 4 —
  T-5300…. Требования среза нумеруются с четырёх сотен (FR-401…).
- **Порядок.** Этапы идут подряд. Внутри этапа задача без `[P]` начинается, когда закончены все предыдущие, а задачи с
  `[P]` не зависят от соседей и не правят общих с ними файлов.
- **Тест-на-требование.** В Этапе 2 у каждого теста в скобках стоит FR или NFR, который он закрывает. Запись
  `файл::имя_теста` и есть связь T-NNNN → FR → тест. Приёмка сценариев 1–11 — сценарии Playwright
  `backend/tests/e2e/test_kNN_*.py`.
- **Красный прежде зелёного.** Задачи Этапа 3 не начинаются, пока не сделан красный прогон T-5160: тесты сначала падают,
  и это записано. Тест не ослабляют, чтобы он прошёл. Правят код, а правка теста допускается только с причиной в отчёте.
- **Регрессия срезов 001–004.** После каждой партии Этапа 3 прогоняется весь серверный набор. Тесты и инструменты
  прежних срезов меняются только по перечню T-5138. Если упадёт другой тест прежнего среза, его не ослабляют:
  исполнитель останавливается, решение принимает Opus и записывает его в отчёт. Правку любого теста система разрешений
  останавливает — до правки спросить владельца с диффом, по одному тесту.
- **Границы модулей.** `knowledge` и `search` не импортируют модели `servicedesk`, `org`, `notify`; `knowledge` зовёт у
  сервис-деска только `servicedesk.services.public`; `search` модулей не знает; `core`, `org`, `servicedesk` не
  импортируют `knowledge` и `search`. Группы поиска модули регистрируют в точке ядра `search_providers`, части карточки
  заявки — в `ticket_card_parts`, виды уведомлений — в `notification_kinds` (план: «Точки расширения ядра и шина
  событий»).
- **Размер.** Одна задача — не больше полудня работы одного исполнителя. Задание агенту — не больше ~50 вызовов. Файл
  тестов — не больше ~25 тестов; большее делится на задачи.
- **Общие файлы тестов.** `tests/CONTRACT-005.md` пишет только T-5100, `tests/support_kb.py` — только T-5101,
  `tests/e2e/helpers_kb.py` — только T-5140. Параллельные исполнители держат свои помощники внутри своего файла теста, а общие файлы не правят.
- **Общие файлы кода** (Этап 3) — у каждого один автор за раз; задачи, которые их правят, идут без `[P]`.
- **Секреты — только `***`** (в коде, документах, отчётах, выводе команд). Это правило ставится в задание каждому
  исполнителю. Новых секретов срез не вводит.
- **Если задание расходится с планом,** исполнитель останавливается и спрашивает Opus. Решение сначала вписывается в
  раздел «Решения Opus по задачам», и только потом меняется код.
- Ссылки на разделы плана — в названии задачи или в `(план: …)`.
